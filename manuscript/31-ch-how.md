# how: 코드가 어떻게 동작하는가

![탐정이 기계 설계도를 확대경으로 살피고 로봇들이 사건 파일을 가져오는 일러스트. 뒤의 증거판에 /how와 /why 표지가 붙어 있다](images/understanding.jpg)

## how {#skill-how}

원문: {{src:skills/how/SKILL.md}} {{src:skills/how/references/explorer-prompt.md}} {{src:skills/how/references/explainer-prompt.md}} {{src:docs/guide/03-understand.md}}

> 코드베이스를 탐색해 "X는 어떻게 동작하는가"에 답합니다. 서브시스템에 막 투입된 시니어 엔지니어에게 설명하는 수준의 아키텍처 설명을 만듭니다.

### 언제 쓰는가

원문의 `description`은 세 가지를 트리거로 듭니다. "how does X work", 무언가를 바꾸기 전의 코드 워크스루, 그리고 배치와 소유권, 계층에 관한 질문("이건 어디에 두어야 하나", "어느 패키지가 소유하나", "이 계층이 맞나")입니다. 서브시스템 구조, 런타임 흐름, 온보딩용 멘탈 모델을 설명합니다. 동기(왜)는 `why`의 일입니다.

프런트매터에 `disable-model-invocation: true`가 있어서, 사용자가 `/how`로 직접 부르거나 `poteto-mode` 같은 다른 워크플로가 부릅니다. `poteto-mode`는 사소하지 않은 변경, 아키텍처 결정, "확실한가?"에서 `how`를 부릅니다. Investigation, Bug fix, Perf issue, Hillclimb, Feature, Refactoring 플레이북이 각자의 단계에서 `how`를 부릅니다.

안내서는 원인이 흐릴 때 수정이 아니라 조사부터 하라고 합니다.

```text
/poteto-mode 백그라운드 잡이 몇 시간마다 시간 초과하는 이유를 조사해 줘. 우리가 아는 것, 쓴 데이터, 가장 나은 가설을 줘. 아직 코드는 바꾸지 마.
```

"아직 코드는 바꾸지 마"는 [Investigation](playbooks-work.md#playbook-investigation)으로 보냅니다. 그 플레이북이 `/how`를 돌리고, 동기를 물으면 `/why`를 더하며, 인용한 설명을 돌려줍니다. 선택지 사이면 트레이드오프 표가 있는 추천을 줍니다. "쓴 데이터"를 물으면 에이전트가 증거와 추측을 가릅니다. 조사가 수정을 가리키면 수정을 새 작업으로 시작합니다.

### 동작 방식

설명의 목표는 작업하는 멘탈 모델을 세우기에 충분하되, 주석 달린 소스처럼 읽히지 않을 만큼만 자세하게 쓰는 것입니다. 각 서브에이전트를 띄울 때는 `pstack-models.mdc` 규칙(rule)에서 그 역할의 줄을 읽어 `model`로 씁니다. 규칙이나 줄이 없으면 기본값을 쓰고, 값이 `auto` 또는 `inherit-parent`면 `model`을 비웁니다. Task 도구가 슬러그를 거부하면 기본값을 쓰고 그 사실을 알립니다. 기본값도 거부하면 오류 메시지에서 같은 계열의 가장 가까운 유효 슬러그를 씁니다.

1. **복잡도를 평가합니다.** 범위가 모호하면 해석을 밝히고 탐색합니다. 사용자가 방향을 바꿀 수 있습니다.
   - **단순**(모듈 하나, 작은 유틸리티, "함수 X는 어떻게 동작하나" 같은 좁은 질문): 탐색자(explorer)를 쓰지 않습니다. 설명자(explainer) 하나가 한 번에 탐색하고 설명합니다.
   - **복잡**(여러 파일이나 서비스에 걸친 서브시스템, 교차 기능, 아키텍처 전체 개요): 병렬 탐색자를 먼저 띄우고 설명자에게 넘깁니다.
   - 애매하면 단순 경로를 택합니다.
2. **탐색(복잡한 질문만).** 질문을 서로 다른 조각인 탐색 각도 2~4개로 나누고, 탐색자를 한 메시지에 모두 띄웁니다. `subagent_type`은 `generalPurpose`, 모델은 `how explorer` 줄(기본 `grok-4.7-xhigh-fast`), `readonly: true`입니다. 각 탐색자는 `references/explorer-prompt.md`에 자기 각도를 채운 프롬프트를 받습니다.
3. **직접 설명(단순한 질문).** Task 서브에이전트 하나가 탐색과 설명을 한 번에 합니다. 모델은 `how explainer` 줄(기본 `claude-opus-5-5-xhigh`)이고 `readonly: true`입니다. 프롬프트는 `references/explainer-prompt.md`에서 탐색자 결과 절을 뺀 것입니다.
4. **종합(복잡한 질문만).** 모든 탐색자가 돌아오면 서브에이전트 하나가 그 결과를 하나의 설명으로 종합합니다. 모델은 `how explainer` 줄이고 프롬프트에는 모든 탐색자의 결과가 들어갑니다.
5. **제시.** 설명자의 출력을 사용자에게 보여 줍니다. 명료성이나 대화 맥락을 위한 가벼운 편집은 괜찮고 대폭 다시 쓰지는 않습니다.

#### 탐색자 프롬프트

탐색자에게는 사실을 모으라고 지시합니다. 다른 에이전트가 사람이 읽을 설명을 쓰므로 산문보다 철저함과 정확성을 우선합니다. 다른 탐색자들이 같은 서브시스템의 다른 조각을 병렬로 조사하므로, 전부 다루려 하지 않고 자기 각도를 깊게 파라고 합니다. Glob으로 파일을 찾고 Grep으로 핵심 심볼을 찾고 Read로 실제 구현을 읽습니다. 이름을 보고 추측하지 않고 코드를 읽습니다. 순서는 다섯 단계입니다.

1. **진입점을 찾습니다.** 무엇이 이 동작을 촉발하는지(사용자 동작, API 호출, 스케줄된 작업).
2. **흐름을 추적합니다.** 진입점에서 호출 사슬을 따라가며 각 함수를 읽고 데이터가 어떻게 흐르고 변환되는지 파악합니다.
3. **핵심 추상화를 그립니다.** 중심이 되는 타입, 인터페이스, 서비스, 클래스와 그것이 무엇을 나타내고 왜 있는지.
4. **경계를 찾습니다.** 이 서브시스템이 다른 것과 만나는 곳. 무엇이 들어가고 나오는지.
5. **자명하지 않은 것을 찾습니다.** 놀라운 것, 역사적 유물로 보이는 것, 신입이 오해할 만한 것.

전체 그림을 얼버무리지 않고 설명할 수 있을 때까지 탐색하고, 추적하지 못한 부분은 그렇다고 분명히 말합니다("X가 Y와 어떻게 이어지는지 알아내지 못했다"가 지어낸 것보다 낫습니다). 탐색자의 출력은 다음 구조를 씁니다. 사실적이고 구체적이며 정확한 파일 경로, 함수 이름, 타입 이름, 줄 번호를 밝힙니다.

| 출력 절 | 내용 |
| --- | --- |
| Components Found | 핵심 타입, 서비스, 클래스, 추상화. 이름, 파일 경로, 한 문장 설명 |
| Flow | 실행 흐름을 단계별로. 어떤 함수가 어느 파일에서 무엇을 하고 다음에 무엇을 부르는지, 단계 사이로 흐르는 데이터 |
| Files Read | 탐색하며 읽은 모든 파일 |
| Boundaries | 이 서브시스템이 코드베이스의 다른 부분과 이어지는 곳, 입력과 출력 |
| Non-Obvious Things | 놀랍거나 역사적 이유가 있거나 틀리기 쉬운 것 |
| Open Questions | 끝까지 추적하거나 이해하지 못한 것. 빈틈을 솔직하게 |

#### 설명자 프롬프트

설명자는 시니어 엔지니어를 위한 아키텍처 설명을 씁니다. 탐색자들의 결과는 일부 겹치고 가끔 모순됩니다. 겹치는 서술은 합치고, 모순은 코드를 직접 확인해 해결하고, 조각들을 하나의 그림으로 만듭니다. 읽기 전용으로 코드베이스를 확인할 수 있으므로 빈틈을 채우는 데 Read, Grep, Glob을 쓰되, 처음부터 다시 탐색할 필요는 없습니다. 출력 형식은 질문에 맞게 조정하며, 해당하지 않는 절은 뺍니다.

| 절 | 내용 |
| --- | --- |
| Overview | 1~2문단. 이것이 무엇이고 무엇을 하며 왜 있는지. 이것만 읽고 계속 읽을지 결정할 수 있어야 합니다 |
| Key Concepts | 나머지를 따라가는 데 필요한 중요한 타입, 서비스, 추상화. 간단한 정의만 |
| How It Works | 설명의 핵심이자 가장 긴 절. 무엇이 촉발하고 단계마다 무엇이 일어나며 데이터가 어디로 가고 결정 지점이 어디인지. 의사코드가 아니라 산문으로, 구체적 파일과 함수를 언급하되 필수적인 스니펫이 아니면 큰 코드 블록은 넣지 않습니다. 여러 컴포넌트가 오가거나 데이터가 단계를 거쳐 변환되면 다이어그램을 씁니다 (구조적 흐름은 mermaid, 단순한 관계는 ASCII). 다이어그램은 장식이 아니라 명료하게 하는 용도입니다 |
| Where Things Live | 일을 시작하려면 알아야 할 파일과 디렉터리의 간단한 지도 |
| Gotchas | 자명하지 않은 것, 놀라운 동작, 역사적 맥락, 함정. 언급할 것이 없으면 뺍니다 |

소통 스타일 지침도 있습니다. 추상에 대한 추상이 아니라 구체적 언어를 씁니다("서비스가 클라이언트에 위임한다"가 아니라 "`UserService`가 `AuthClient.refresh()`를 호출한다"). 복잡한 것은 왜 복잡한지를 설명하고, 단순한 것은 부풀리지 않습니다. 도움이 되는 비유가 있으면 쓰고 없으면 억지로 만들지 않습니다. 탐색자가 표시한 열린 질문과 빈틈은 숨기지 않고 인정합니다.

### 사용 예

```text
/how 알림 중복은 어떻게 제거하나요? 구독자를 조회할 때 N+1이 생기나요?
```

실제로 궁금한 질문을 그대로 묻습니다. `/how`는 시니어 엔지니어를 온보딩하듯이 런타임 흐름, 핵심 타입, 자명하지 않은 부분을 답합니다. 큰 서브시스템이면 읽기 전용 탐색자를 2~4개 먼저 띄우고, 좁은 질문이면 그냥 읽고 설명합니다.

### 함정과 주의점

- 범위가 모호하면 해석을 밝히고 진행합니다. 다른 곳을 탐색하고 있다면 사용자가 바로 방향을 돌릴 수 있게 하기 위해서입니다.
- 복잡도가 애매하면 단순 경로를 택하고 탐색자를 띄우지 않습니다.
- 설명자의 출력을 대폭 다시 쓰지 않습니다.
- 안내서는 "에이전트가 어차피 코드를 읽을 텐데"라며 이 스킬을 건너뛰지 말라고 경고합니다. 추적된 모델 없이 편집에 들어간 에이전트는 첫 번째 그럴듯한 자리에서 증상을 고치기 쉽습니다.
- 동기와 역사를 묻는 질문은 `how`가 아니라 `why`의 몫입니다.

### 관련 스킬

동기를 묻는다면 [`why`](why.md#skill-why), 둘을 엮은 설명은 [`teach`](teach-recall.md#skill-teach)입니다. `poteto-mode`의 [Investigation](playbooks-work.md#playbook-investigation) 플레이북이 바로 이 스킬의 출력 형식을 씁니다.

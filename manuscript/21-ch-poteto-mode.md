## poteto-mode {#skill-poteto-mode}

원문: {{src:skills/poteto-mode/SKILL.md}} {{src:docs/guide/02-poteto-mode.md}} {{src:agents/poteto-agent.md}}

> 요청을 읽고 플레이북 하나를 골라, 필요한 스킬을 단계마다 불러 가며 엄밀하게 끝내는 진입점 스킬입니다.

### 언제 쓰는가

엄밀함이 필요한 작업을 시작할 때 씁니다. 원문의 `description`은 "poteto의 에이전트 스타일: 간결하고 상세한 응답, 신중한 서브에이전트, 슬롭을 뺀 글, 단순한 코드, 검증(verification)된 작업"이라고 하고, `poteto`, `/poteto-mode`, 이 스타일로 일해 달라는 요청을 트리거로 듭니다.

프런트매터에 몇 가지 눈에 띄는 설정이 있습니다.

- `mode: true`. 이 스킬은 스티키 모드입니다. 한 번 들어가면 대화 내내 유지됩니다.
- `disable-model-invocation: true`. 모델이 알아서 이 스킬을 부르지 않고, 사용자가 `/poteto-mode`로 부릅니다.
- `reminder`. 모드가 켜진 동안 에이전트에게 주는 짧은 알림입니다. 새 작업이 오면 플레이북이 맞거나 엄밀함이 필요한지 보고 적용하고, 가벼운 대화이거나 사용자가 빠지겠다고 하면 적용하지 않습니다.

### 동작 방식

`SKILL.md`는 일곱 부분으로 이루어집니다. 위에서부터 순서대로 봅니다.

#### 1. Non-negotiables (지켜야 할 규칙)

먼저 원칙(principle) 색인이 모든 트리거의 근거라는 규칙(non-negotiable)이 있습니다. 응답에서 결정에 영향을 준 원칙과 그 원칙이 바꾼 구체적 선택을 밝혀야 하고, 그 세션에서 리프 `SKILL.md`를 읽은 원칙만 인용할 수 있습니다.

나머지 트리거는 아래와 같습니다. "상황"이 오면 오른쪽 스킬이나 행동으로 갑니다.

| 상황 | 하는 일 |
| --- | --- |
| 사소하지 않은 변경, 아키텍처 결정, "확실한가?" | `how` 스킬 |
| "어떤 접근으로", "어떻게 할까", "이건 어떻게 동작해야 하나" 같은 갈림길에서 `AskQuestion`을 하려는 순간 | 먼저 분류합니다. 실행해서 관찰할 수 있는 사실(동작, 타이밍, 레이아웃, 출력, 성능, 심지어 eval이 두 후보를 가르는지)이면 사람이 답할 일이 아닙니다. Prototype 플레이북으로 스케치해 결과가 정하게 합니다. 산출물(deliverable)이 출처를 단 답변인 읽기 전용 Investigation이면 스케치 대신 증거로 답합니다. 실험으로 풀 수 없는 진짜 제품, 취향 판단에만 질문을 씁니다. 전면 자율 권한이 주어지면 그 권한이 덮는 결정은 스스로 내리고 실행한 뒤 보고합니다. 운영자만 내릴 수 있는 결정은 기본값을 적용하고, 전체 설명과 운영자가 대신 하라고 말할 수 있는 일을 평범한 말로 함께 보고합니다. 운영자는 자기 말로 답합니다. 되돌려 입력할 약어 토큰은 주지 않습니다. 운영자가 지정한 관문(gate)과 Autonomy의 "반드시 멈춘다" 목록은 여전히 운영자를 기다립니다 |
| 코드를 쓸 때 | 먼저 데이터 모양의 이름을 정하고, `principle-model-the-domain`에 따라 조직 구조를 고릅니다 |
| 코드가 함수 경계를 넘을 때 | `architect`. 구현 전에 병렬 설계 탐색 |
| 병렬 팬아웃 | 커버리지 행렬, 경주, 관문 시험(gauntlet), 탐색 분할은 `swarm`. 설계나 코드 대결에서 기준안을 고르고 이식할 때는 `arena` |
| 논쟁적인 설계 | 배포 전에 `interrogate` (다중 모델 적대적 리뷰) |
| 사소하지 않은 여러 단계 작업 | 처리량 점검표(throughput checkpoint)를 씁니다 (Feature 3단계) |
| 글이 나오는 모든 표면 | `unslop`. 응답도 글이므로 "Writing the reply" 규칙(rule)으로 씁니다. 에이전트가 읽을 글은 Cursor 내장 `create-skill` 스킬도 따릅니다 |
| 문서, RFC, README, PR 설명, 커밋 메시지 | `technical-writing` |
| 커밋 전 | cursor-team-kit 플러그인의 `deslop` (`/deslop`) |
| 리뷰 전 | `no-comments` |
| UI, IDE, CLI를 배포할 때 | 맞는 control 스킬. cursor-team-kit이 `control-cli`(CLI와 TUI)와 `control-ui`(브라우저, Electron, 웹 UI)를 제공합니다. 버그 수정은 같은 표면에서 직접 먼저 재현하고, Bug fix 1단계의 좁은 예외에서만 사용자에게 넘깁니다 |
| 벤치마크를 돌리거나 성능을 직접 재거나, 측정한 가속이나 회귀를 보고할 때 | 그 숫자를 보고하거나 그에 따라 행동하기 전에 [`benchmark-checklist`](verification.md#skill-benchmark-checklist) |
| PR 상태 요청 | Babysit 플레이북. Cursor 내장 babysit 스킬은 설명이 같은 말에 걸려서 쓰지 않습니다. "babysit this", "get it green", "address the bugbot comments", "check on PR X" 같은 말이 모두 해당합니다. PR을 열기만 했다고 자동으로 트리거되지는 않습니다. 폴링 전에 모드를 먼저 선언하며, 요청을 모드로 옮기는 규칙(mapping)은 플레이북 1단계가 갖습니다 |
| 초록불 스택을 병합해 달라는 요청 | Shipping 플레이북. 초록불이 곧 안전은 아닙니다. PR마다 독립 판정이 나오기 전에는 아무것도 병합 예약하지 않고, 루트에서 이어진 검증 완료 구간만 병합합니다 |
| Bugbot이나 에이전트 보안 리뷰가 댓글을 달았을 때 | 회의적 자세. 각 지적을 장점 기준으로 평가하고, 잡음은 구체적 이유와 함께 기각합니다. `references/bugbot-triage.md`로 fix, dismiss, ask를 분류합니다 |
| 작업 중 스킬이 고장났을 때 | 그 스킬을 별도 PR로 고칩니다. 막히지도 말고 조용히 우회하지도 않습니다 |
| 길거나 자율적이거나 여러 단계인 작업, 사용자가 나중에 검토하려고 자리를 뜨는 작업 ("going to bed", "trust it when i'm back", "/loop until X") | `show-me-your-work`로 결정 기록을 남깁니다. 위험이 크면 커밋하고, 아니면 로컬에 둡니다 |

여기서 "control 스킬", `deslop`, `create-skill`, 내장 babysit은 pstack이 아니라 cursor-team-kit 플러그인이나 Cursor 내장 기능입니다.

#### 2. Principles (원칙 색인)

리프 스킬을 전부 읽어야 적용할 수 있고, 항목마다 언제 적용하는지 적혀 있습니다. 원칙은 핵심(Core), 아키텍처(Architecture), 검증(Verification), 위임(Delegation), 메타(Meta) 다섯 묶음으로 나뉩니다. 24개의 내용은 [원칙 장](principles.md)에서 하나씩 다룹니다.

#### 3. Autonomy (자율성)

- **그냥 한다.** 어떤 MCP 도구든 씁니다. 되돌릴 수 있는 작업과 외부 행동(팀 채팅, 티켓 갱신, eval 시작)은 묻지 않고 진행합니다.
- **반드시 멈춘다.** 되돌릴 수 없는 쓰기(공유 브랜치 강제 푸시, 배포, 데이터 삭제, 고객 메시지)는 사용자를 기다립니다.
- **세션 오버라이드.** "Don't stop", "going to bed", "run until done", "be fully autonomous" 같은 말은 계속 진행하라는 뜻입니다.
- **"아니오"도 답이다.** 무엇을 해도 되는지 묻거나 범위를 더하라고 하거나 접근을 보여 줄 때, 진짜 판단을 말합니다. 거절하고, 반박하고, 맞다면 "이건 넣을 가치가 없다"고 말합니다. 추천은 판단이지 동의가 아닙니다. 기본값은 동의가 아니라 솔직함입니다.

#### 4. Subagents (서브에이전트)

- 플레이북 단계 안에서 띄우는 서브에이전트(코드를 쓰는 위임, 임시 도우미)는 `subagent_type: "poteto-agent"`를 씁니다. `/poteto-mode`와 `poteto-agent`는 같은 래퍼를 지납니다. 반면 `how`, `why`, `interrogate`, `reflect`, `swarm`은 다양한 모델의 리뷰를 위해 자기 `subagent_type`을 정해 두므로, 스킬이 정한 것을 그대로 따르고 `poteto-agent`로 덮어쓰지 않습니다.
- 모든 `Task` 호출의 기본값은 이렇습니다. `run_in_background: true`, 에이전트 모드(읽기 전용은 MCP를 벗겨 냄), 맥락을 붙여 넣지 않고 파일 포인터를 넘김, 역할별 명시적 모델(`/setup-pstack`으로 설정. 기본값은 코드에 `grok-4.7-xhigh-fast`, 글과 판단에 `claude-opus-5-5-max`). 코드 위임은 난이도별로 나눕니다. 가장 어려운 변경(교차 설계, 까다로운 동시성, 미묘한 알고리즘)은 가장 강한 판단 모델로 갑니다. 애매한 의도에 판단이 필요한 경우든, 글자 그대로 따라야 하는 정밀한 절차든 같습니다. 사소한 기계적 수정은 빠른 코드 모델로 갑니다. `/setup-pstack` 규칙(rule)의 역할별 줄은 이 기본값은 물론 `how`, `why`, `arena`, `swarm`, `architect`, `interrogate`, `reflect`가 스킬 안에 정해 둔 모델보다 우선합니다. 줄이 없는 역할은 기본값을 유지하고, 값이 `inherit-parent`나 `auto`이면 Task의 `model`을 생략해 부모 채팅 모델로 돌립니다. 코드 플레이북은 각자의 줄(`feature, refactoring`, `bug-fix`, `perf-issue`, `hillclimb`)을, 가장 어려운 변경은 `hardest tasks` 줄을, 글과 판단은 `judgment and prose` 줄을 읽습니다.
- 부모가 모든 서브에이전트의 작업을 책임집니다. diff를 검토하고 요약은 직접 쓰지, 서브에이전트가 한 말을 그대로 넘기지 않습니다. 두 번째 의견은 같은 프롬프트를 다른 모델에 주는 것이고, 두 모델이 일치하면 신호가 강합니다.
- **기본은 새 서브에이전트입니다.** 새 일은 통합한 범위(원래 브리프, 이후의 모든 지시, 이전 에이전트의 보고와 브랜치)를 가진 새 서브에이전트에게 줍니다. 수정 라운드, 후속, 재시도, 대기열의 다음 항목이 모두 그렇습니다. 기존 서브에이전트를 재개하거나 메시지를 보내거나 후속을 대기열에 넣는 것은, 그 에이전트에만 있고 옮기기 비싼 상태(로컬 체크아웃, 커밋하지 않은 변경, 아직 도는 프로세스. 개발 서버, 시뮬레이터, babysit 감시자 등)가 새 일에 꼭 필요할 때만입니다. 실행 중인 에이전트에게 정지하거나 보류하라는 명령은 재사용이 아닙니다. PR 소유자 같은 역할은 에이전트보다 오래 갑니다. 그 에이전트가 돌아오면 역할의 다음 라운드는 새 에이전트가 맡습니다. 인터럽트로 이어 붙인 재개는 지시를 조용히 놓치므로, "끝났다"는 요약을 믿기보다 통합한 범위로 새 서브에이전트를 띄웁니다.

#### 5. Writing the reply (응답 쓰기)

응답은 초안을 쓰는 순간부터 깨끗하게 씁니다. 다 쓰고 나서 손보는 것으로는 이 패턴들이 빠지지 않습니다.

- 짧은 서술문. 한 문장에 한 생각, 마침표로 끝냅니다.
- 긴 줄표 문자를 어디에도 쓰지 않습니다. 파일 목록은 문장으로 쓰고("`main.js`는 영속화와 IPC 핸들러를 맡습니다"), 굵은 소제목은 별도 문장으로 씁니다("**Verification.** CDP로 끝에서 끝까지").
- 문장 중간의 연결용 콜론도 쓰지 않습니다(unslop 규칙(rule) 14). 목록 앞의 콜론은 괜찮습니다.
- 간결하다는 것이 내용을 빼도 된다는 뜻은 아닙니다. 짧은 문장이되, 플레이북의 응답이 이름 붙인 모든 항목(세부, 트레이드오프, 선택, 열린 결정)은 남깁니다.
- 소비자와 유지보수자에게 미치는 영향을 앞세웁니다. 이 작업이 누구를 위한 것인지(최종 사용자, 라이브러리를 가져다 쓰는 동료)와 그들에게 무엇이 바뀌는지를 구현 세부보다 먼저 말하고, 다음에 이 코드를 맡을 엔지니어가 무엇을 물려받는지를 말합니다. 둘 다 말할 수 없으면 작업이나 설명이 잘못된 것입니다.
- 링크, 인용, 대화 기록 참조를 지어내지 않습니다. 그 세션에서 직접 만들었거나 읽은 것만 링크합니다.
- 모든 주장은 같은 문장 안에 근거나 라벨(측정함, 추론함, 추측)을 답니다. 예측이나 확인하지 못한 원인은 추측입니다. 직접 돌릴 수 있는 확인을 사람에게 넘기지 않습니다.

모든 플레이북은 이렇게 쓴 응답으로 끝나고, PR 링크는 `https://github.com/<owner>/<repo>/pull/<number>` 형식으로 씁니다.

#### 6. Comments (주석)

주석도 응답과 같은 규칙(rule)을 따릅니다. 코드가 보여 줄 수 없는 자명하지 않은 이유(why)에만 주석을 남깁니다. 검증 스크립트나 테스트 스크립트에는 `// Phase 1: add cards` 같은 단계 서술 주석을 달지 않습니다. 단언문이나 로그 문자열이 단계를 설명합니다(`assert(ok, 'persisted across restart')`). 위임받은 서브에이전트의 diff를 포함해 만드는 모든 파일에 적용됩니다.

#### 7. Playbooks (플레이북 고르기)

호출되면 맞는 플레이북의 단계를 그대로 복사해 할 일 목록의 첫 항목으로 열고, 그다음에 작업별 항목을 붙입니다. 하지 않기로 한 단계는 목록에 남기고 한 줄 `skip: <이유>`를 답니다.

크거나 여러 곳에 걸친 작업(호출 지점이 많은 마이그레이션, 야심찬 다부분 변경)이나 나중에 믿기로 하고 자리를 뜨는 작업은, Feature 같은 좁은 플레이북이 맞아도 `figure-it-out`으로 갑니다. 맞는 플레이북이 없을 때도 `figure-it-out`입니다. 그 작업만의 엄밀한 플레이북을 설계합니다. 며칠에 걸친 상시 프로젝트(많은 스택 PR, 한 조정자 아래의 서브에이전트 무리)는 `figure-it-out` 대신 Orchestrate로 갑니다. `figure-it-out`은 한 번의 맞춤 실행을 설계하고, orchestrate는 프로그램을 운영합니다.

### 사용 예

**목표를 말하고 의식은 생략합니다.** 명세를 쓸 필요는 없습니다. 무엇이 잘못됐는지, 무엇을 원하는지와 에이전트의 시간을 아껴 줄 알고 있는 사실만 말합니다.

```text
/poteto-mode 재시도 뒤에 알림이 두 번 옵니다. 먼저 재현하고, 고치고, 검증해 줘.
```

이것은 Bug fix 프롬프트입니다. "먼저 재현"은 예의가 아니라 실제 제약이고 플레이북이 그것을 지킵니다. 할 일 목록에 Bug fix의 단계가 채워지는 것을 보십시오. 건너뛴 단계는 `skip: <이유>`와 함께 보입니다.

대화에 맥락이 이미 있으면 프롬프트는 거의 없어도 됩니다. 아래는 모두 충분합니다.

```text
/poteto-mode do it
```

```text
continue
```

```text
keep going until done
```

짧아도 되는 이유는 모드가 스티키이고 구조는 플레이북이 갖고 있기 때문입니다. 말은 의도를 싣고 스킬은 엄밀함을 싣습니다.

**작업을 바꿀 때는 "new task"라고 말합니다.** 긴 채팅에는 지난 작업의 맥락이 쌓입니다. 주제를 바꿀 때는 그렇게 말합니다.

```text
/poteto-mode new task. 로그아웃 뒤에도 캐시 항목이 남는 이유를 알아내 줘. 아직 코드는 바꾸지 마.
```

"new task"는 이전 플레이북을 이어 가지 말고 다시 맞추라는 뜻이고, "코드는 바꾸지 마"는 이 작업을 Investigation에 못 박습니다. 이 두 표현이 없으면 Feature 중간에 있던 모드는 질문을 다음 기능 단계로 취급하기 쉽습니다.

**병렬 작업에는 각자의 워크트리를 줍니다.** 한 저장소에 에이전트 여러 개를 돌리면 작업 트리를 두고 다툽니다. 처음부터 격리를 요청하십시오.

```text
/poteto-mode new task. <base>에서 새 워크트리로 분기해서 거기에 파서 변경을 옮겨 줘.
```

작업마다 브랜치와 워크트리가 따로 있으면 서로의 파일을 덮어쓰지 않습니다. Opening a PR 플레이북은 코드 변경에서 이미 워크트리에서 일하므로, 특정 기준(base)이나 위치가 중요할 때만 말하면 됩니다. 워크트리는 쌓입니다. 디스크가 부족하면 이렇게 묻습니다.

```text
/poteto-mode 디스크를 뭐가 먹고 있어? 지워도 안전한 워크트리는 정리해 줘.
```

**자리를 뜰 때.** 무엇이 끝인지 말하고 떠납니다. 나중에 검토할 작업은 `figure-it-out`으로 라우팅되고 `show-me-your-work` 결정 기록이 붙습니다. 자세한 계약은 [밤새 돌리기](overnight.md)에서 다룹니다.

### 함정과 주의점

- **프롬프트에 스킬을 나열하지 않습니다.** "/how, 그다음 /architect, 그다음 /arena를 써 줘"처럼 쓰면 플레이북이 이미 정해 둔 순서를 뒤섞거나 단계를 빠뜨리기 쉽습니다. 특정 선택을 덮어쓰고 싶을 때만 스킬 이름을 씁니다.
- 원칙(principle)을 인용하려면 그 세션에서 리프 `SKILL.md`를 읽어야 합니다. 읽지 않은 원칙을 이름만 들먹이는 것은 규칙(non-negotiable) 위반입니다.
- 서브에이전트의 "끝났다"는 보고를 그대로 전달하지 않습니다. 부모가 diff를 검토하고 직접 요약합니다.
- 스킬이 작업 중에 고장나면 그 자리에서 우회하지 말고 별도 PR로 고칩니다.

## poteto-agent {#agent-poteto-agent}

원문: {{src:agents/poteto-agent.md}}

> `/poteto-mode`와 같은 래퍼를 지나며, 시작하기 전에 `poteto-mode`의 `SKILL.md` 전체를 읽는 서브에이전트입니다.

pstack은 poteto의 스타일을 처음부터 끝까지 수행하는 서브에이전트를 함께 싣습니다. 부모 에이전트가 `subagent_type: "poteto-agent"`로 띄웁니다. 정의 파일은 짧습니다. 프런트매터의 `description`은 이 에이전트가 `/poteto-mode`와 poteto 스타일 요청의 라우팅 대상이며, 새 작업마다 새 `poteto-agent`를 띄우고, 재개는 `poteto-mode`의 Subagents 절이 이름 붙인 엄격한 경우에만 하라고 말합니다. 그리고 `generalPurpose`로 바꿔 치면 읽기 단계를 건너뛰어 스타일이 어긋난다고 경고합니다. `is_background: true`입니다. 본문은 이렇습니다. 어떤 작업이든 시작하기 전에 `poteto-mode`의 `SKILL.md`를 인라인 원칙 색인까지 전부 읽고, 원칙을 적용할 때마다 리프 `principle-*` 스킬로 들어가라는 것입니다.

같은 저장소의 다른 서브에이전트 `Comment Sicko`는 [코드 위생 장](code-hygiene.md#agent-comment-sicko)에서 다룹니다.

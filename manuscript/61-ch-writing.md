# 글쓰기: unslop과 technical-writing

## unslop {#skill-unslop}

원문: {{src:skills/unslop/SKILL.md}} {{src:docs/guide/05-build-and-clean.md}}

> 어떤 글에서든 AI가 쓴 티를 걷어 냅니다. 원문의 `description`은 "Cut AI tells from any writing."입니다.

### 언제 쓰는가

글이 나오는 모든 곳입니다. `poteto-mode`는 응답을 포함한 모든 글에 이 스킬을 요구하므로, 응답도 이 스킬의 규칙(rule)으로 씁니다. `technical-writing`은 자신이 건드리는 모든 문서에 이 스킬을 적용하라고 하고, `teach`, `recall`, `blast-radius`, `automate-me`, `show-me-your-work`와 Investigation 플레이북도 결과물을 이 스킬을 거쳐 쓰라고 합니다. 안내서는 Opening a PR 플레이북이 커밋마다 `/deslop`을 돌리고, `poteto-mode`가 PR 설명과 커밋 본문에 `/unslop`을 적용한다고 적습니다. 사용자는 대상과 추가 규칙을 줄 수 있습니다.

```text
/unslop 읽기 문서 변경분에서, 긴 줄표는 쓰지 마
```

스킬은 짧은 지시("unslop that, tighten it")도 잘 알아듣는다고 안내서는 적습니다. 코드의 슬롭은 `/deslop`(cursor-team-kit)이, 글의 슬롭은 `/unslop`이 맡고, 주석은 `/no-comments`가 그것을 쓰지 않은 리뷰어에게 넘깁니다.

### 동작 방식

과정은 둘입니다. 아래 패턴을 스캔하고, 다시 씁니다. 의미를 보존하고 의도한 톤에 맞춥니다. 규칙 번호는 다른 스킬이 인용하는 안정된 식별자이며, 삭제된 규칙은 빈 번호로 남습니다. 그래서 번호가 연속하지 않습니다. 규칙마다 한 줄입니다.

| 규칙 | 내용 |
| --- | --- |
| 3 | 사실을 더하지 않는 꼬리 "-ing" 구문("highlighting...", "ensuring...")을 쓰지 않습니다 |
| 5 | 모호한 출처("experts believe")를 쓰지 않습니다. 출처를 밝히거나 지웁니다 |
| 7 | AI 어휘를 쓰지 않습니다. additionally, crucial, delve, enhance, foster, landscape, pivotal, showcase, testament, underscore, vibrant |
| 8 | "serves as", "stands as", "boasts", "features"가 아니라 "is"나 "has"라고 씁니다 |
| 9 | "not just X, but Y"를 쓰지 않습니다. 요점을 말합니다 |
| 10 | 생각을 억지로 셋씩 묶지 않습니다 |
| 11 | 대상 하나에 이름 하나를 쓰고, 그 이름을 반복합니다 |
| 12 | X와 Y가 실제 척도 위에 있지 않으면 "from X to Y"를 쓰지 않습니다 |
| 13 | 긴 줄표, 짧은 줄표, 줄표로 쓴 하이픈을 쓰지 않고, 그 자리에 괄호도 쓰지 않습니다. 마침표나 쉼표를 씁니다 |
| 14 | 콜론은 목록이나 예 앞에만 둡니다. 문장 중간의 연결어로는 쓰지 않습니다 |
| 15 | 고유명사나 약어마다 굵게 하지 않습니다 |
| 16 | 줄의 내용을 되풀이하는 굵은 라벨과 콜론("**Performance:** Performance improved...")을 쓰지 않습니다. 마침표로 끝나고 새 세부를 더하는 굵은 도입은 괜찮습니다 |
| 17 | 제목은 문장형 대소문자로 씁니다 |
| 18 | 장식용 이모지를 쓰지 않습니다 |
| 19 | 곧은 따옴표를 씁니다 |
| 20 | 챗봇 문구("I hope this helps!", "Let me know if...")를 쓰지 않습니다 |
| 22 | 칭찬이나 동의로 시작하지 않습니다. 바로 답합니다 |
| 23 | 군더더기를 자릅니다. "In order to"는 "to"로 쓰고, "it is important to note that"은 지웁니다 |
| 24 | 헤지는 많아야 하나이고, 그것은 "may"입니다 |
| 25 | 상투적 결론을 쓰지 않습니다. 구체적인 계획이나 사실을 말합니다 |
| 26 | 추상적 은유 명사를 쓰지 않습니다. substrate, wedge, vector, nexus, primitive, harness, surface, scaffolding, paradigm, ratchet, north star, flywheel 대신 구체적인 낱말을 씁니다 |
| 27 | 느낌이 아니라 하는 일을 말합니다. 메커니즘이나 숫자를 댑니다. 다른 프로젝트의 문서에 그대로 나올 수 있는 문장은 자릅니다 |
| 28 | 문장 하나에 생각 하나를 둡니다. 독자가 다시 읽어야 하는 문장은 나눕니다 |
| 29 | 능동태로 씁니다. 행위자를 모르거나 상관없을 때가 아니면 행위자를 밝힙니다 |
| 30 | 부사를 자르거나 더 강한 동사를 씁니다. 숫자를 댑니다 |
| 31 | 평범한 낱말을 씁니다. "utilize"나 "leverage"가 아니라 "use"입니다 |
| 32 | 문자 그대로의 표현이 있는 곳에 은유, 격언, 의인화한 코드, 비유적 동사를 쓰지 않습니다 |
| 33 | 관사와 동사가 있는 완전한 문장으로 씁니다. 화살표와 약어는 풀어 씁니다 |

### 사용 예

```text
/unslop 읽기 문서 변경분 다듬어 줘, 긴 줄표는 쓰지 마
```

스킬은 대상 글을 위 규칙에 맞춰 스캔하고 의미와 톤을 보존하며 다시 씁니다. 같은 내용은 다른 스킬에도 걸립니다. `poteto-mode`의 응답 쓰기 절은 긴 줄표와 연결어로 쓰는 콜론을 금하는데, 규칙 13, 14와 같은 내용입니다. `teach`는 모든 응답을 이 스킬을 거쳐 쓰라고 합니다.

### 함정과 주의점

- 규칙 16의 예외를 기억합니다. 마침표로 끝나고 새 세부를 더하는 굵은 도입은 티가 아닙니다.
- 규칙 번호는 안정 식별자입니다. 삭제된 규칙은 번호가 비므로 번호를 당겨 다시 매기지 않습니다.

### 관련 스킬

[`technical-writing`](#skill-technical-writing)이 이 스킬 위에서 문서 구조와 문장 규율을 더합니다. [`bro`](utility.md#skill-bro)도 응답을 평이하게 되돌리는 스킬입니다.

## technical-writing {#skill-technical-writing}

원문: {{src:skills/technical-writing/SKILL.md}} {{src:docs/guide/09-make-it-yours.md}}

> 층화된 기술 문서 기준. Diátaxis 구조, Google 개발자 스타일 문장, STE 지시 규칙, Global English 구문.

### 언제 쓰는가

원문의 `description`이 든 트리거는 `/technical-writing`, 그리고 문서, RFC, README, PR 설명, 커밋 메시지를 쓰거나 리뷰할 때입니다. 안내서는 이 스킬을 이렇게 소개합니다. 지친 엔지니어가 한 번 읽고 이해하는 글이라는 하나의 목표를 가진 층화된 기준(standard)이고, 문서의 모드(튜토리얼, how-to, 레퍼런스, 설명)를 먼저 고른 뒤 문장별로 작업합니다. 누가 무엇을 하는지, 문장당 한 생각, 두 가지로 읽히는 것은 없게. 방금 자신이나 에이전트가 쓴 것을 리뷰하는 데 쓰거나 문서를 요청할 때 미리 지명합니다.

```text
/technical-writing README 변경분을 리뷰해 줘
```

`poteto-mode`는 문서, PR 설명, 커밋 메시지에서 이 스킬을 요구합니다. PR 설명과 커밋 메시지에는 Diátaxis를 제외한 모든 층이 적용된다고 이 스킬 자신이 적습니다.

### 동작 방식

목표는 지친 엔지니어가 첫 읽기에 이해하는 글입니다. 다섯 규칙이 먼저 옵니다.

- 일하지 않는 낱말은 모두 자릅니다.
- 짧고 일상적인 낱말을 씁니다. "utilize"가 아니라 "use"입니다.
- 규칙이 문장을 더 나쁘게 만들면 문장을 다른 방식으로 고치거나 그대로 둡니다.
- 동의어나 설명이 아니라 실제 심볼, 파일, 플래그, 명령의 이름을 씁니다.
- 전문 용어를 지어내지 않습니다. 개발자가 소리 내어 말할 낱말을 씁니다. 이름 붙은 패턴은 처음 나올 때 뜻을 밝힙니다.

**리듬을 다양하게.**

- 문장 길이를 섞습니다. 생각 둘을 나르는 문장은 나누고, 생각 하나를 나르는 긴 문장은 둡니다.
- 설명 문서에서는 견해를 밝히고, 레퍼런스는 건조하게 둡니다.
- 구체적으로 씁니다. "schema changes can cause issues"가 아니라 "a column rename fails the build"입니다.

**먼저 모드를 고릅니다(Diátaxis).** 문서 하나에 모드 하나입니다. 모드를 섞지 않고, 나누고 링크합니다.

- **튜토리얼(하면서 배우기).** 학습자가 무엇을 만들지 말합니다. 단계마다 눈에 보이는 결과가 나오고, 학습자가 무엇을 보아야 하는지 알려 줍니다. 설명은 한 절과 링크로 줄입니다.
- **how-to(목표를 위한 단계).** 독자의 문제를 풉니다. 유능함을 가정하고 행동만 씁니다. 갈림길은 허용합니다. 안내서 이름은 과업으로 붙입니다.
- **레퍼런스(찾아보는 사실).** 기술만 합니다. 건조하고 완전하고 확실하게 씁니다. 기술하는 대상의 구조를 그대로 따릅니다.
- **설명(이해와 이유).** 경계 있는 주제 하나를 다룹니다. 설계 결정, 역사, 제약, 대안 같은 맥락을 줍니다. 의견은 여기서만 허용됩니다.

**독자를 향해 문장을 씁니다(Google 개발자 스타일).**

- 독자에게 "you"로, 현재 시제로 말합니다.
- 누가 무엇을 하는지 말합니다. 수동은 행위자를 모르거나 중요하지 않을 때만 씁니다.
- 지시는 명령으로 씁니다. 조건은 지시 앞에, 흔한 경우는 먼저 둡니다.
- 유행어, 비유적 표현, "please"를 쓰지 않고, 절차(procedure) 안에서는 "simply", "easy", "quickly"를 절대 쓰지 않습니다.
- 미리 알리지 않고, 연속한 문장을 같은 구문으로 시작하지 않습니다.
- 링크는 링크가 어디로 가는지 말하는 낱말로 겁니다.
- 제목은 요점을 담고 문장형 대소문자로 씁니다. 페이지당 h1은 하나이고 수준을 건너뛰지 않습니다.
- 순서에는 번호 목록, 나머지에는 불릿을 씁니다. 목록은 완전한 문장으로 도입하고 항목은 병렬로 둡니다.
- 코드는 코드 글꼴, UI 요소는 굵게 씁니다. 시리얼 콤마를 쓰고 "etc."는 버립니다.

**진술을 하나씩 싣습니다(STE 규칙).**

- 지시는 문장당 하나, 그 밖의 곳은 문장당 생각 하나입니다.
- 약 20 낱말보다 긴 지시와 약 25 낱말보다 긴 다른 문장은 나눕니다.
- 경고나 조건은 그것이 지키는 단계 앞에 둡니다.
- "the"와 "a"를 남깁니다.
- 낱말마다 뜻 하나를 주고, 행동마다 낱말 하나를 고릅니다.
- 절차는 직접 명령으로 쓰고, 서술이나 수동으로는 쓰지 않습니다.
- 가능하면 "-ing" 낱말을 피합니다.

**어떤 문장도 두 가지로 읽히게 두지 않습니다(Global English).**

- "only", "not" 같은 낱말은 바꾸려는 낱말 옆에 둡니다.
- 긴 명사 열을 나눕니다.
- 모든 "it", "they", "this"가 뻔한 한 대상을 가리키게 합니다. "this"나 "which"로 절 전체를 가리키지 않습니다.
- 동사를 떨어뜨리지 않고, "that"처럼 구조를 보여 주는 작은 낱말도 남깁니다.
- 오독을 막을 때는 나열에서 관사를 반복합니다. "and"나 "or"이 무엇을 잇는지 밝힙니다.
- 세미콜론이나 긴 줄표가 아니라 마침표를 씁니다. 슬래시와 "(s)"를 쓰지 않습니다. 괄호 안의 글은 완전한 문법 단위로 씁니다.
- 각 대상을 어디서나 하나의 이름으로 부릅니다.
- 관용구, 구어체, 라틴어 약어, 은유를 건너뜁니다.

**목소리와 저장소별 규칙.**

- 이 스킬이 건드리는 모든 문서에 **unslop** 스킬을 적용합니다. 그 스킬이 슬롭 패턴 목록(AI 어휘, 군더더기, 헤지, 서식 티)을 소유합니다.
- PR 설명과 커밋 메시지도 글쓰기입니다. Diátaxis를 제외한 모든 층이 적용됩니다. PR 본문은 리뷰어가 1분 안에 읽을 수 있는 브리핑입니다. swarm 로그, SHA 목록, 지표 표를 붙여 넣지 않고 링크합니다.
- 제품 UI 문자열은 문서가 아닙니다. 그런 것에는 제품의 카피 지침(guideline)을 씁니다.
- 코드 조각은 탭으로 들여씁니다. 실제 경로를 씁니다. 개수나 트리에 대한 모든 주장이 그것을 랜딩하는 커밋에서 참이게 하고, 그것을 다시 생성하는 명령을 포함합니다.

### 사용 예

```text
/technical-writing README 변경분을 리뷰해 줘
```

스킬은 문서의 모드를 먼저 고르고, 문장별로 네 층을 적용해 리뷰합니다. 문서를 요청할 때 미리 이 스킬을 지명해도 됩니다.

### 함정과 주의점

- 한 문서에 모드를 섞지 않습니다. 나누고 링크합니다.
- 규칙이 문장을 나쁘게 만들면 문장을 다른 방식으로 고치거나 그대로 둡니다.
- PR 본문에 swarm 로그, SHA 목록, 지표 표를 붙여 넣지 않고 링크합니다.

### 관련 스킬

[`unslop`](#skill-unslop)이 슬롭 패턴 목록을 소유합니다. PR 제목 형식과 본문의 `##` 머리말은 [Opening a PR](playbooks-pr.md#playbook-opening-a-pr) 플레이북이 정합니다.

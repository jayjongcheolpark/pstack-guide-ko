# 작업 플레이북

원문 디렉터리: {{src:skills/poteto-mode/playbooks/investigation.md}}

플레이북(playbook)은 작업 유형별 절차서입니다. `poteto-mode`는 요청을 읽고 이 중 하나를 골라 단계를 할 일 목록에 그대로 복사하고, 단계가 필요로 할 때 다른 스킬을 부릅니다. 이 장은 코드와 조사, 스킬 자체를 다루는 12개 플레이북을 설명합니다. PR을 다루는 플레이북은 [다음 장](playbooks-pr.md), 장시간과 대규모 작업용 플레이북은 [그다음 장](playbooks-long.md)에 있습니다.

플레이북마다 절의 끝에 다섯 가지가 붙어 있습니다. 단계와 분기와 중단 조건을 그린 흐름도, 단계별 산출물, 이 책의 저자가 만든 예시(원본에 없음), 실패와 중단과 모호함의 처리, 호출하는 스킬과 스크립트의 표입니다. 흐름도의 실선은 진행, 점선은 중단이나 되돌아감, 점선 테두리 상자는 중단 조건을 뜻합니다. 표의 산출물은 각 단계의 서술에서 읽어 낸 것이고, 원문이 정하지 않은 것은 정하지 않았다고 적었습니다.

모든 플레이북은 첫 줄에 "당신이 무엇을 책임지는가"를 선언하고, 마지막에 그 플레이북이 요구하는 **응답** 내용을 적습니다. 코드를 바꾸는 플레이북은 대부분 Opening a PR로 끝납니다.

## Investigation {#playbook-investigation}

원문: {{src:skills/poteto-mode/playbooks/investigation.md}}

> 읽기 전용 질문에 출처가 있는 설명이나 권고로 답합니다. 코드는 바꾸지 않습니다.

### 언제 쓰는가

"X는 어떻게 동작하나", "Y는 왜 이렇게 만들었나", "Z가 확실한가", "X와 Y 중 무엇을 할까" 같은 질문입니다.

### 동작 방식

1. `how` 스킬로 라우팅합니다. 동기를 묻는 질문이면 `why` 스킬도 거칩니다.
2. 처리량 점검표는 한 줄로 끝냅니다. `throughput checkpoint: n/a, read-only investigation`.
3. `how` 형식의 출력(Overview / Key Concepts / How It Works / Where Things Live / Gotchas)을 냅니다. 요청이 대안 사이의 결정이라면 트레이드오프 표가 있는 권고를 냅니다.
4. 응답에 `unslop` 스킬을 적용합니다.

PR도, babysit도 없습니다. 조사가 코드 변경보다 앞서는 경우가 아니면 `architect`도 쓰지 않습니다. 코드 변경으로 이어진다면 사용자에게 돌려주고 Bug fix나 Feature로 다시 라우팅합니다.

### 응답

조사 결과 자체입니다. "확실한가?"에는 진짜 판단을 이유와 함께 담고, 전제가 틀렸다면 반박합니다(Autonomy 규칙(Autonomy section)).

### 사용 예

```text
/poteto-mode new task. 로그아웃 뒤에도 캐시 항목이 남는 이유를 알아내 줘. 아직 코드는 바꾸지 마.
```

"코드는 바꾸지 마"가 이 요청을 Investigation에 고정합니다.

### 흐름도

```flow Investigation 플레이북의 흐름
start 읽기 전용 질문
step 1. 질문 라우팅
step 2. 처리량 점검표 한 줄
step 3. 출력 만들기
  alt 코드 변경으로 이어짐 | 사용자에게 돌려주고 Bug fix나 Feature로 다시 라우팅
step 4. unslop 적용
end 응답
```

### 단계별 산출물

이 장의 산출물 표는 각 단계의 서술에서 읽어 낸 것입니다. 원문이 파일 이름이나 형식을 정한 경우에만 그 이름을 씁니다.

| 단계 | 산출물 |
| --- | --- |
| 1 | 라우팅 결정(`how`, 필요하면 `why`). 별도 파일은 없습니다 |
| 2 | 한 줄짜리 처리량 점검표 |
| 3 | `how` 형식의 다섯 절(Overview / Key Concepts / How It Works / Where Things Live / Gotchas), 또는 트레이드오프 표가 있는 권고 |
| 4 | `unslop`을 거친 응답 |

PR, babysit, 코드 변경은 이 플레이북의 산출물이 아닙니다.

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "결제 재시도를 지금의 지수 백오프 대신 작업 큐로 옮기는 편이 나을까? 코드는 바꾸지 마."
>
> - 읽기 전용 질문이고 두 대안 사이의 결정이므로 Investigation입니다. `how`로 재시도가 지금 어디서 일어나는지 읽습니다.
> - 처리량 점검표는 `throughput checkpoint: n/a, read-only investigation` 한 줄입니다.
> - 출력은 `how` 형식이 아니라 권고입니다. 두 대안의 트레이드오프 표와, 표 아래에 근거가 있는 판단 하나를 냅니다. 전제가 틀렸다면(예를 들어 재시도가 이미 큐 위에서 돕니다) 그 점을 먼저 반박합니다.
> - 코드는 바꾸지 않습니다. 사용자가 옮기기로 하면 그때 Feature로 다시 라우팅합니다.

### 실패, 중단, 모호할 때

- **조사가 코드 변경으로 이어질 때.** 이 플레이북 안에서 고치지 않습니다. 사용자에게 돌려주고 Bug fix나 Feature로 다시 라우팅합니다.
- **질문의 전제가 틀렸을 때.** "확실한가?" 같은 질문에는 이유가 있는 진짜 판단을 냅니다. 전제가 틀렸으면 반박합니다(Autonomy의 "No is an acceptable answer").

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| [`how`](how.md#skill-how) | 스킬 | 1, 출력의 형식도 정합니다 |
| [`why`](why.md#skill-why) | 스킬 | 1, 동기를 묻는 질문일 때 |
| [`unslop`](writing.md#skill-unslop) | 스킬 | 4 |

이 플레이북은 스크립트를 부르지 않습니다.

## Bug fix {#playbook-bug-fix}

원문: {{src:skills/poteto-mode/playbooks/bug-fix.md}}

> 보고된 결함을 재현하고, 근본 원인을 찾고, 런타임 증거로 고칩니다.

### 언제 쓰는가

결함이 보고되었을 때입니다. "이 PR에 잔 버그가 있는데 유휴 상태에서도 750ms마다 스크롤이 밀립니다. 먼저 재현하고 고쳐서 검증(verification)해 줘" 같은 요청이 원문 README의 예입니다.

### 동작 방식

부모는 작업을 책임지고 계획, 리뷰, 검증을 맡습니다. 조사와 수정은 서브에이전트에게 위임하고 자신은 리드로 남습니다.

플레이북의 태도는 과학적이어야 한다는 것입니다. 배포되는 모든 줄은 런타임 증거로 추적되어야 합니다. "도움이 될지도 모르는" 이중 안전장치는 수정이 아니라 가설이고 배포하지 않습니다. 증거가 가설을 반박하면 그 가설이 만든 변경을 되돌립니다. 증거가 정당화하는 가장 작은 변경만 배포합니다.

1. **직접 재현합니다.** 맞는 표면에서 control 스킬(cursor-team-kit의 `control-cli`, `control-ui`)로 재현합니다. 디버그나 계측 프로토콜이 사용자에게 재현을 부탁하라고 해도 먼저 직접 합니다. 사용자에게 묻는 것은 control 표면이 목표에 닿지 못하는 구체적 이유를 밝힐 수 있고, 그 표면으로 갈 수 있는 데까지 갔을 때뿐입니다. 재현이 안 되면 트리거를 합성하거나 조건을 좁히거나 계측해서 발생시킵니다.
2. **원인을 이분 탐색합니다.** 후보 가설을 세우고 하나가 살아남을 때까지 배제합니다. 영향받는 서브시스템에 대한 `how`와, 회귀 이력에 대한 `why`로 가설을 채웁니다. 매 라운드 남은 문제 공간을 가장 많이 줄이는 분할을 택하고 런타임 증거를 얻어 배제합니다. 프로그램 상태가 불분명하면 계측이나 로깅을 넣어 실행 중에 읽습니다. 추측하지 않습니다. 길거나 끈질긴 사냥은 Cursor의 `/loop` 명령으로 돌립니다. 3단계의 architect나 interrogate 팬아웃 전에, 살아남은 *메커니즘*을 런타임 증거로 확정합니다.
3. **수정을 계획합니다.** 함수 경계를 넘으면 `architect`를 먼저 씁니다. 구현은 설정된 bug-fix 모델(기본 `grok-4.7-xhigh-fast`)의 서브에이전트에게 구체적 범위로 위임합니다.
4. **같은 표면에서 검증합니다.** 원래 재현이 이제 통과해야 합니다. "결론 없음"이나 잘못된 표면은 통과가 아닙니다. 그렇게 표시합니다. 단위 테스트는 분기 동작을 보여 줄 뿐 버그가 없음을 보여 주지는 않습니다.
5. **커밋을 쌓는 순서를 정합니다.** 실패하는 재현이 수정보다 git 이력에서 먼저 오게 합니다. 버그에 값싼 로컬 테스트 경로가 있으면 실패하는 테스트를 먼저 쓰는 리듬은 `tdd` 스킬을 봅니다. 테스트가 비싸거나 통합에 무겁거나 불분명하면 건너뜁니다. 이것이 `sequence-verifiable-units` 원칙(principle)의 표준 사례입니다. 실패하는 테스트가 먼저이고 수정이 그 위에 옵니다.
6. **Opening a PR**을 실행합니다.

### 응답

무엇이 고장났는지, 근본 원인, 수정, 어떻게 검증했는지. 실패하다가 통과하는 재현 출력을 그대로 붙여 넣습니다.

### 함정과 주의점

- 재현 없이 수정으로 가지 않습니다. 사용자에게 재현을 넘기는 것은 좁은 예외입니다.
- 단위 테스트 통과를 버그가 사라졌다는 증거로 삼지 않습니다.
- 살아남은 메커니즘을 확정하기 전에 설계 팬아웃으로 넘어가지 않습니다.

### 흐름도

```flow Bug fix 플레이북의 흐름
start 결함이 보고됨
step 1. 직접 재현
  alt 재현되지 않음 | 트리거를 합성하거나 조건을 좁히거나 계측해서 발생시킴
  stop 표면이 목표에 닿지 못함 | 그 이유를 밝히고, 갈 수 있는 데까지 간 뒤에만 사용자에게 재현을 부탁함
step 2. 원인 이분 탐색
  alt 증거가 가설을 반박함 | 그 가설이 만든 변경을 되돌림
step 3. 수정 계획과 위임
step 4. 같은 표면에서 검증
  alt 결론 없음 또는 잘못된 표면 | 통과로 세지 않고 그렇게 표시함
step 5. 커밋 순서
step 6. Opening a PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 실제 표면에서 얻은 재현. 재현하는 출력 |
| 2 | 살아남은 가설 하나와 그것을 확정한 런타임 증거(계측이나 로그의 출력). 배제된 가설이 만든 변경은 남지 않습니다 |
| 3 | 범위가 정해진 위임(모델은 bug-fix 역할의 설정값)과 서브에이전트의 diff |
| 4 | 같은 표면에서 이제 통과하는 원래 재현 |
| 5 | 실패하는 재현(가능하면 실패하는 테스트)이 수정보다 앞서는 커밋 이력 |
| 6 | Opening a PR의 산출물 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "장바구니 수량을 2로 바꾸고 새로고침하면 합계가 이전 값으로 돌아갑니다. 재현하고 고쳐서 검증해 줘."
>
> 1. 브라우저용 control 스킬로 같은 조작을 직접 합니다. 합계가 되돌아가는 화면을 잡습니다. 사용자에게 재현을 부탁하지 않습니다.
> 2. 후보 가설은 셋입니다. 저장 요청이 안 나감, 서버가 값을 무시함, 캐시가 옛 값을 돌려줌. 요청과 응답을 로깅하는 계측을 넣어 저장 요청은 나가고 서버도 저장하며, 새로고침 때 오래된 캐시가 반환된다는 증거로 둘을 배제합니다. 캐시 무효화가 빠진 것이 살아남은 메커니즘입니다.
> 3. 수정이 함수 경계를 넘지 않으므로 `architect`는 건너뜁니다. 범위(파일 두 개, 무효화 호출 위치)를 적어 서브에이전트에게 맡깁니다.
> 4. 같은 표면에서 원래 순서를 다시 밟아 합계가 유지되는지 봅니다. 단위 테스트가 초록인 것은 이 검증을 대신하지 않습니다.
> 5. 값싼 로컬 테스트 경로가 있으므로 실패하는 테스트 커밋을 수정 커밋 앞에 둡니다.
> 6. Opening a PR을 실행하고, 응답에 실패했다가 통과하는 재현 출력을 그대로 붙입니다.

### 실패, 중단, 모호할 때

- **재현되지 않을 때.** 트리거를 합성하거나 조건을 좁히거나 계측해서 발생시킵니다. 길거나 끈질긴 사냥은 Cursor의 `/loop` 명령으로 돌립니다.
- **control 표면이 목표에 닿지 못할 때.** 그 구체적 이유를 밝히고, 표면으로 갈 수 있는 데까지 간 뒤에만 사용자에게 재현을 부탁합니다. 디버그 프로토콜이 사용자에게 재현을 부탁하라고 해도 먼저 직접 합니다.
- **증거가 가설을 반박할 때.** 그 가설이 만든 변경을 되돌립니다. 증거가 정당화하는 가장 작은 변경만 배포합니다.
- **검증 결과가 "결론 없음"이거나 표면이 틀렸을 때.** 통과가 아닙니다. 그렇게 표시합니다.
- **버그에 값싼 로컬 테스트 경로가 없을 때.** 테스트가 비싸거나 통합에 무겁거나 불분명하면 실패하는 테스트를 먼저 쓰는 리듬을 건너뜁니다.

| `control-cli`, `control-ui` | cursor-team-kit의 스킬 | 1, 4 |
| [`how`](how.md#skill-how) | 스킬 | 2, 가설 채우기 |
| [`why`](why.md#skill-why) | 스킬 | 2, 회귀 이력 |
| [`architect`](architect.md#skill-architect) | 스킬 | 3, 함수 경계를 넘을 때 |
| [`tdd`](tdd-blast.md#skill-tdd) | 스킬 | 5, 값싼 테스트 경로가 있을 때 |

## Perf issue {#playbook-perf-issue}

원문: {{src:skills/poteto-mode/playbooks/perf-issue.md}}

> 측정된 느림을 추적해 기준선과 비교하며 개선합니다. 모든 수정은 측정과 짝을 이룹니다.

### 언제 쓰는가

"가상화했는데도 큰 목록을 불러오는 데 1~2초가 걸립니다. CPU 트레이스를 돌려서 이유를 알려 줘" 같은 요청입니다. 한 번으로 끝나는 수정입니다. 한 지표를 목표까지 계속 끌어올리는 일은 Hillclimb입니다.

### 동작 방식

부모는 측정 이야기를 책임집니다. 소스를 읽는 것으로 측정을 대신하지 않습니다.

1. 맞는 control 스킬로 기준선 트레이스를 잡습니다. 기준선과 그 뒤의 숫자마다 [`benchmark-checklist`](verification.md#skill-benchmark-checklist)로 걸러 냅니다.
2. `how`로 가설의 근거를 잡습니다. 돌려 보지 않고 성능 한계를 주장하지 않습니다. 성능 만트라를 싼 것부터 이 순서로 시도합니다.

   1. **Don't do it.** 결과를 아무도 쓰지 않는 일은 싸게 만들지 말고 멈춥니다.
   2. **Do it, but don't do it again.** 같은 일을 다시 하지 않습니다.
   3. **Do it less.** 덜 합니다.
   4. **Do it later.** 나중에 합니다.
   5. **Do it when they're not looking.** 보지 않을 때 합니다.
   6. **Do it concurrently.** 동시에 합니다.
   7. **Do it cheaper.** 더 싸게 합니다.

   앞선 만트라가 목표를 충족하면 멈춥니다.

3. 트레이스로 수정을 계획합니다. 함수 경계를 넘으면 `architect`를 먼저 씁니다. 구현은 설정된 perf-issue 모델(기본 `grok-4.7-xhigh-fast`)의 서브에이전트에게 위임하고 diff를 검토한 뒤 수정 후 트레이스를 잡습니다. `sequence-verifiable-units` 원칙에 따라 시도마다 검증한 뒤 다음을 시도합니다.
4. 산출물(artifact)을 파싱해 비교합니다(JSON을 sqlite로, diff). "결론 없음"이나 잘못된 표면은 통과가 아닙니다.
5. PR에 측정값을 인용합니다.
6. Opening a PR을 실행합니다.

### 응답

기준선 수치, 수정 후 수치, 차이, 산출물 경로.

### 함정과 주의점

- 측정 없이 소스를 읽고 병목을 단정하지 않습니다.
- 앞선 만트라가 목표를 충족하면 뒤의 만트라로 넘어가지 않습니다.
- 기준선과 이후의 숫자는 `benchmark-checklist`를 거치기 전에 계획의 근거가 되지 않습니다.

### 흐름도

```flow Perf issue 플레이북의 흐름
start 측정된 느림
step 1. 기준선 트레이스
step 2. 성능 만트라
  alt 앞선 만트라가 목표를 충족 | 멈춤
step 3. 수정과 재측정
step 4. 산출물 비교
  alt 결론 없음 또는 잘못된 표면 | 통과로 세지 않고 표시함
step 5. PR에 측정값 인용
step 6. Opening a PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 기준선 트레이스 파일. `benchmark-checklist`를 거친 숫자 |
| 2 | 싼 순서의 성능 만트라에 매단 가설. 앞선 만트라가 목표를 충족하면 거기서 멈춤 |
| 3 | 서브에이전트의 diff(설정된 perf-issue 역할의 모델), 시도마다의 수정 후 트레이스 |
| 4 | 기준선과 수정 후를 파싱해 비교한 결과 |
| 5 | 측정값을 인용한 PR 본문 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "가상화했는데도 검색 결과 목록이 열릴 때 1.5초 정도 멈춥니다. CPU 트레이스를 돌려서 이유를 알려 주고 고쳐 줘."
>
> 1. 맞는 control 스킬로 목록을 열어 CPU 트레이스를 잡습니다. `benchmark-checklist`로 그 기준선을 걸러 냅니다.
> 2. `how`로 목록 초기화 경로를 읽습니다. 같은 정렬이 행마다 다시 돕니다. 만트라 1(하지 않는다)은 정렬 결과가 화면에 쓰이므로 해당하지 않고, 만트라 2(다시 하지 않는다)가 목표를 충족할 후보입니다. 더 비싼 만트라로는 넘어가지 않습니다.
> 3. 정렬 결과를 한 번 계산해 재사용합니다. 수정 뒤 트레이스를 다시 잡고 그 숫자도 체크리스트로 걸러 냅니다.
> 4. 두 트레이스를 파싱해 같은 함수의 누적 시간을 비교합니다.
> 5. PR에 기준선과 수정 후 수치를 인용합니다. 응답에는 두 수치, 차이, 트레이스 파일 경로를 적습니다.

### 실패, 중단, 모호할 때

- **앞선 만트라가 목표를 충족할 때.** 뒤의 만트라로 넘어가지 않고 멈춥니다.
- **성능 한계를 소스로만 주장하고 싶을 때.** 돌려 보지 않고 성능 한계를 주장하지 않습니다.
- **비교 결과가 "결론 없음"이거나 표면이 틀렸을 때.** 통과가 아닙니다. 표시합니다.
- **한 번의 수정으로 끝나지 않는 일일 때.** 한 지표를 목표까지 끌어올리는 일은 Hillclimb로 넘깁니다. Hillclimb는 이 만트라의 순서만 빌리고, 앞선 만트라에서 멈추는 규칙은 빌리지 않습니다.
- **숫자를 보고하거나 그 숫자로 계획을 세우기 전.** 기준선과 이후의 숫자마다 `benchmark-checklist`를 돌립니다.

## Hillclimb {#playbook-hillclimb}

원문: {{src:skills/poteto-mode/playbooks/hillclimb.md}}

> 지표 하나를 목표까지 가설 검증 루프로 끌어올립니다. 변경 하나, 측정 하나, 유지 또는 되돌림.

### 언제 쓰는가

측정 가능한 한 가지를 목표에 대해 지속적이고 반복적으로 개선할 때입니다. 한 번으로 끝나는 수정은 Bug fix나 Perf issue이고, 이것은 그 루프입니다.

핵심 규율은 "변경 하나, 측정 하나, 유지하거나 되돌림"입니다. 검증하지 않은 변경을 쌓지 않고, 코드를 읽는 것만으로 승리를 주장하지 않습니다(`prove-it-works` 원칙).

### 동작 방식

부모는 지표와 실험의 무결성을 책임지고, 감독하고 리뷰하며 시도는 위임합니다.

1. **작업 부하와 아키텍처를 먼저 파악합니다.** 지표를 고르기 전에 대상에 `how`를 돌리고, 결과를 움직일 수 있는 현실적 작업 부하 차원(데이터 크기, 이력, 상태, 동시성)에 이름을 붙이고, 사용자가 호소한 문제를 재현하는 사례를 고릅니다. 재현하는 사례가 없으면 hillclimb하지 말고 재현부터 고칩니다. 그다음 지표 하나, 무엇이 더 나은 방향인지, 검사 가능한 중단 조건을 정합니다. 중단 조건은 목표와 시도 횟수의 하한을 짝지어서, 운 좋은 초기 승리로 실행이 끝나지 않게 합니다("기준선보다 50% 이상 개선 그리고 10회 이상 반복"이 원문의 예). 사용자가 숫자를 주면 그것을 쓰고, 아니면 합의합니다.
2. **측정 하니스를 만들고 민감도를 증명한 뒤 동결합니다**(`build-the-lever` 원칙). 대조적인 현실적 작업 부하를 돌려 목표 사례가 증상을 재현하고 쉬운 사례는 예상대로 갈리는지 확인합니다. 하니스가 구별하지 못하면 작업 부하나 지표를 고칩니다. 동결하기 전에 [`benchmark-checklist`](verification.md#skill-benchmark-checklist)로 하니스를 걸러 내고, 하니스가 오류 횟수와 실제로 한 일의 횟수를 찍게 만듭니다. 동결한 뒤에는 명령 하나가 반복 가능하게 지표를 내고, 잡음을 넘도록 충분히 표본을 뽑습니다(한 번이 아니라 N번의 중앙값). 변경 전에 기준선 지표와, 회귀 관문(계속 통과해야 하는 테스트)의 초록 실행을 기록합니다.
3. **결정 기록을 엽니다**(`show-me-your-work` 스킬). `decision.tsv`에 시도마다 한 행: id, 가설, 변경, before, after, delta, 테스트, 판정(유지 또는 되돌림), 메모. 시도 전마다 읽습니다. 트리 밖에 둡니다(gitignore).
4. **가설을 1단계의 아키텍처 모델에 붙입니다.** "무언가를 메모이즈해 보자"가 아니라 구체적 메커니즘("X를 부팅 경로에서 미룬다, 첫 페인트를 막기 때문")을 이름으로 댑니다. 성능 지표이면 가설의 순서는 Perf issue 2단계의 성능 만트라를 따릅니다. 순서를 빌릴 뿐이고, 앞선 만트라가 목표를 충족하면 멈추라는 그 단계의 중단 규칙은 빌리지 않습니다.
5. **루프, 반복당 가설 하나.**
   - 설정된 hillclimb 모델(기본 `grok-4.7-xhigh-fast`)의 서브에이전트에게 좁은 범위로 변경을 넘깁니다. 직접 치지 않고 감독하고 diff를 리뷰합니다(`guard-the-context-window` 원칙). 독립적인 가설이 여러 개 살아 있으면 병렬 서브에이전트로 나눠 각자 워크트리를 씁니다(`separate-before-serializing-shared-state` 원칙).
   - 동결한 하니스로 전후를 측정하고 회귀 관문(gate)을 돌립니다.
   - 지표가 잡음을 넘어 움직이고 관문이 초록일 때만 받아들입니다. 아니면 변경을 통째로 되돌립니다. "도움이 될지도 모르는" 손질은 남기지 않습니다.
   - 받아들인 수정마다 커밋 하나. 바꾼 파일만 스테이징합니다(`git add <files>`, `-A`는 쓰지 않음). 유지든 되돌림이든 행을 기록합니다.

   반복은 매번 검사로 끝난 뒤에 다음이 시작됩니다(`sequence-verifiable-units` 원칙(principle)). 무인 실행이면 Autonomous run 플레이북에서 깨우는 장치만 빌리고 중단 규칙(rule)은 빌리지 않습니다.
6. **첫 정체기를 넘어 밀어붙입니다.** 연속으로 여러 번 거부되면 범주를 바꾸거나, 아쉬운 시도를 결합하거나, 소스를 다시 읽거나, 더 급진적인 것을 시도한 뒤에야 언덕을 다 올랐다고 결론냅니다. 정확성과 단순성이 숫자보다 우선합니다. 동작을 깨는 승리는 되돌리고, 숫자를 유지하는 단순화는 남깁니다(`laziness-protocol` 원칙).
7. **중단 조건이 충족되었거나, 남은 아이디어가 사소해 비용만 못할 때 멈춥니다.** 충족하려고 조건을 완화하지 않고, 값싼 미시도 가설이 남았는데 그만두지도 않습니다. 막혔으면 빙빙 돌지 말고 드러냅니다.
8. 받아들인 커밋을 들어온 순서로 쌓아 Opening a PR을 실행합니다.

### 응답

지표와 목표, 기준선에서 최종까지와 퍼센트 차이, 실행한 반복(유지 대 되돌림), 받아들인 수정을 한 줄씩, `decision.tsv` 경로, 더 밀어붙인다면 다음에 시도할 최선의 아이디어.

### 함정과 주의점

- 하니스가 대조 사례를 구별하지 못하는 상태로 시작하지 않습니다.
- 목표만 있고 시도 횟수의 하한이 없는 중단 조건은 운 좋은 초기 승리에 끝납니다.
- 조건을 충족하려고 조건을 낮추지 않습니다.

### 흐름도

```flow Hillclimb 플레이북의 흐름
start 지표 하나를 목표까지
step 1. 작업 부하와 아키텍처
  stop 재현하는 사례가 없음 | hillclimb하지 않고 재현부터 고침
step 2. 하니스 제작과 동결
  alt 하니스가 구별하지 못함 | 작업 부하나 지표를 고침
step 3. 결정 기록 열기
step 4. 가설을 메커니즘에 연결
step 5. 루프
  alt 지표가 잡음 안이거나 관문이 빨강 | 변경을 통째로 되돌림
  back 5 | 다음 가설
step 6. 첫 정체기 넘기기
step 7. 중단 판단
step 8. Opening a PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 지표 하나, 더 나은 방향, 목표와 시도 횟수 하한을 짝지은 중단 조건, 재현 사례 |
| 2 | 동결한 측정 하니스(명령 하나로 지표를 내고, 오류 횟수와 일의 횟수를 찍음). 동결 전에 `benchmark-checklist`. 기준선 지표, 회귀 관문의 초록 실행 |
| 3 | `decision.tsv`(id, 가설, 변경, before, after, delta, 테스트, 판정, 메모). 트리 밖에 둡니다 |
| 4 | 구체적 메커니즘에 이름을 댄 가설 |
| 5 | 받아들인 수정마다 커밋 하나(바꾼 파일만 스테이징), 유지든 되돌림이든 `decision.tsv` 한 행 |
| 6 | 정체를 넘기려는 새 시도들 |
| 7 | 중단 근거 |
| 8 | 커밋이 들어온 순서로 쌓인 PR |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "앱 콜드 스타트를 지금 3.2초에서 절반 밑으로 줄여 줘. 자러 갈 테니 알아서 해 줘."
>
> 1. `how`로 시작 경로를 읽고 "저장소 100개, 이력 1만 건"이라는 사용자 사례를 골라 첫 화면까지의 시간을 지표로 삼습니다. 중단 조건은 "기준선보다 50% 이상 개선 그리고 10회 이상 반복"입니다.
> 2. 명령 하나로 지표를 내는 하니스를 만들고, 작은 저장소 사례와 큰 사례가 다르게 나오는지 확인한 뒤 동결합니다. 중앙값으로 표본을 뽑아 기준선을 기록합니다.
> 3. `decision.tsv`를 열고, 시도마다 "인덱스 로드를 첫 페인트 뒤로 미룬다"처럼 메커니즘이 있는 가설을 하나씩 서브에이전트에게 맡깁니다.
> 4. 어떤 시도는 지표가 잡음 안이라 통째로 되돌리고, 어떤 시도는 받아들여 커밋 하나로 남깁니다. 되돌린 시도도 한 행으로 남깁니다.
> 5. 무인 실행이므로 Autonomous run에서 깨우는 장치만 빌립니다. 중단 규칙은 이 플레이북의 것을 씁니다.

### 실패, 중단, 모호할 때

- **재현하는 사례가 없을 때.** hillclimb하지 않고 재현부터 고칩니다.
- **하니스가 대조 사례를 구별하지 못할 때.** 작업 부하나 지표를 고칩니다.
- **지표가 잡음을 넘지 못하거나 관문이 빨강일 때.** 변경을 통째로 되돌립니다. "도움이 될지도 모르는" 손질은 남기지 않습니다.
- **정체되거나 연속으로 거부될 때.** 범주를 바꾸거나 아쉬운 시도를 결합하거나 소스를 다시 읽거나 더 급진적인 것을 시도합니다. 그 뒤에야 언덕을 다 올랐다고 결론냅니다.
- **동작을 깨는 승리.** 되돌립니다. 숫자를 유지하는 단순화는 남깁니다.
- **중단.** 술어가 충족되었거나, 남은 아이디어가 사소해 비용만 못할 때 멈춥니다. 조건을 완화해서 충족하지 않고, 값싼 미시도 가설이 남았는데 그만두지도 않습니다. 막혔으면 빙빙 돌지 말고 드러냅니다.
- **무인 실행.** Autonomous run 플레이북에서 깨우는 장치만 빌리고 중단 규칙은 빌리지 않습니다.

## Runtime forensics {#playbook-runtime-forensics}

원문: {{src:skills/poteto-mode/playbooks/runtime-forensics.md}}

> 살아 있는 프로세스를 계측해 진단합니다. 산출물은 수정이 아니라 출처가 있는 진단입니다.

### 언제 쓰는가

누수, 유휴 CPU 스핀, 화면 글리치 같은 런타임 증상을 실행 중인 상태에서 진단할 때입니다.

### 동작 방식

부모는 진단을 책임집니다. 소스로 이론을 세우지 않고 살아 있는 프로세스를 계측합니다.

1. 맞는 표면에서 control 스킬로 살아 있는 신호를 잡습니다. 도는 프로세스라면 CPU 프로파일, 누수라면 힙 스냅숏, 시각적 글리치라면 CDP 트레이스. 추측이 아니라 실제 산출물입니다.
2. 산출물을 결정적 증거로 줄입니다. 핫 경로의 함수, 누수된 객체에서 GC 루트까지의 retainer 체인, 입력 없이 발화하는 루프. 큰 산출물은 서브에이전트에서 파싱하고(`guard-the-context-window` 원칙) 줄인 결과만 메인 스레드에 둡니다.
3. 메커니즘을 믿기 전에 증명합니다. 실행 중인 프로세스에 CDP eval로 계측을 주입하거나 라이브 코드를 리로드 없이 핫픽스해서 가설을 값싸게 확인합니다.
4. 결과를 소스로 되짚습니다. 파일, 심볼, 할당하거나 스케줄하는 줄.
5. 처리량 점검표는 한 줄로 끝냅니다. `throughput checkpoint: n/a, read-only forensics`.

### 응답

포착한 신호, 줄인 결과, 메커니즘을 어떻게 증명했는지, 소스 위치, 산출물 경로. 요청이 없으면 수정하지 않습니다. 원인이 밝혀지면 Bug fix나 Perf로 넘깁니다.

### 흐름도

```flow Runtime forensics 플레이북의 흐름
start 런타임 증상
step 1. 살아 있는 신호 포착
step 2. 결정적 증거로 줄임
step 3. 메커니즘 증명
step 4. 소스로 되짚음
step 5. 처리량 점검표 한 줄
end 응답
  alt 원인이 밝혀짐 | Bug fix나 Perf로 넘김
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 실제 산출물(프로파일, 스냅숏, 트레이스) |
| 2 | 줄인 결과. 핫 경로 함수, 누수된 객체에서 GC 루트까지의 retainer 체인, 입력 없이 발화하는 루프 중 해당하는 것 |
| 3 | 계측이나 핫픽스로 확인한 메커니즘 |
| 4 | 파일, 심볼, 할당하거나 스케줄하는 줄 |
| 5 | `throughput checkpoint: n/a, read-only forensics` |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "앱을 켜 두고 아무것도 안 하는데 CPU가 15%로 유지됩니다. 원인만 알려 줘."
>
> 1. control 스킬로 유휴 상태의 실행 중인 프로세스에서 CPU 프로파일을 잡습니다.
> 2. 프로파일이 크므로 서브에이전트에서 파싱하고, 메인 스레드에는 "입력 없이 250ms마다 도는 타이머 콜백이 시간의 대부분을 차지한다"는 줄인 결과만 받습니다.
> 3. 실행 중인 프로세스에 CDP eval로 계측을 넣어 콜백이 실제로 타이머에서 호출된다는 것을 확인합니다.
> 4. 타이머를 등록하는 줄을 파일과 심볼로 짚습니다.
> 5. 처리량 점검표는 `throughput checkpoint: n/a, read-only forensics` 한 줄로 끝내고, 수정하지 않고 진단을 응답합니다. 고치려면 Bug fix로 넘긴다고 덧붙입니다.

### 실패, 중단, 모호할 때

- **요청이 없으면 고치지 않습니다.** 원인이 밝혀지면 Bug fix나 Perf로 넘깁니다.
- **가설을 믿기 전에 증명합니다.** 신호만으로 원인을 단정하지 않고 계측이나 핫픽스로 값싸게 확인합니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| `control-cli`, `control-ui` | cursor-team-kit의 스킬 | 1 |
| [`guard-the-context-window`](principles.md#skill-principle-guard-the-context-window) | 원칙 | 2 |
| [Bug fix](playbooks-work.md#playbook-bug-fix), [Perf issue](playbooks-work.md#playbook-perf-issue) | 플레이북 | 원인이 밝혀진 뒤의 인계 |

## Trace forensics {#playbook-trace-forensics}

원문: {{src:skills/poteto-mode/playbooks/trace-forensics.md}}

> 이미 캡처된 프로파일링 산출물을 읽어 진단합니다. 산출물은 고정된 데이터셋입니다.

### 언제 쓰는가

cpuprofile, 트레이스, spindump, 힙 스냅숏을 나중에 넘겨받았을 때입니다. 실행 중인 프로세스를 계측하는 Runtime forensics와 달리 캡처가 이미 있습니다. 다시 돌리지 않고 읽습니다. 플레이북을 이식 가능하게 두려고 도구는 일반적으로 씁니다. cpuprofile과 `.json.gz`는 DevTools나 트레이스 파서, spindump는 텍스트 편집기, heapsnapshot은 자신의 힙 도구입니다.

### 동작 방식

1. 형식을 식별하고 맞는 도구로 로드합니다. 큰 산출물은 서브에이전트에서 파싱하고(`principle-guard-the-context-window`) 줄인 결과만 메인 스레드에 둡니다.
2. 원시 산출물을 질의할 수 있는 형태로 바꿉니다. 트레이스나 힙 스냅숏을 sqlite에 덤프해 샘플, 프레임, 노드마다 한 행을 둡니다. 읽기 전에 질의 가능한 모양에 도달합니다.
3. 원인으로 좁힙니다. 시간을 가장 많이 가진 프레임을 질의하고 호출 트리를 따라 핫 경로로 갑니다. 누수라면 누수된 객체에서 GC 루트까지 retainer 체인을 따릅니다. spindump라면 CPU에서 멈춘 스레드나 블록된 스레드와 그 대기 이유를 찾습니다.
4. 소스로 귀속합니다. 핫 프레임을 산출물 자체의 심볼로 파일, 심볼, 줄에 대응시킵니다. 소스 매핑이 없는 프레임은 아직 진단이 아닙니다. 심볼을 풀거나 산출물에 심볼이 없다고 분명히 말합니다.
5. 짝이 되는 캡처가 있으면 대조합니다. 전후 산출물을 비교합니다. 없으면 발견을 확정된 원인이 아니라 산출물이 뒷받침하는 가장 강한 가설로 표시합니다.
6. 출처가 있는 진단을 넘깁니다. 요청이 없으면 수정하지 않습니다. 원인이 밝혀지면 Bug fix나 Perf issue로 라우팅합니다. 처리량 점검표는 한 줄, `throughput checkpoint: n/a, read-only forensics`.

### 응답

산출물과 형식, 줄인 결과, 소스 위치, 산출물 경로, 짝이 되는 캡처가 확인해 주었는지.

### 함정과 주의점

소스 매핑이 없는 프레임을 진단으로 내지 않습니다. 짝이 되는 캡처 없이는 확정이 아니라 "가장 강한 가설"이라고 표시합니다.

### 흐름도

```flow Trace forensics 플레이북의 흐름
start 캡처된 산출물을 넘겨받음
step 1. 형식 식별과 로드
step 2. 질의 가능한 형태로
step 3. 원인으로 좁힘
step 4. 소스로 귀속
  alt 소스 매핑이 없는 프레임 | 아직 진단이 아님, 심볼을 풀거나 없다고 분명히 말함
step 5. 짝이 되는 캡처와 대조
  alt 짝이 없음 | 확정된 원인이 아니라 가장 강한 가설로 표시
step 6. 진단을 넘김
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 로드된 산출물 |
| 2 | 질의할 수 있는 sqlite 표 |
| 3 | 좁혀진 원인 후보(핫 경로, retainer 체인, 대기하는 스레드와 이유) |
| 4 | 파일, 심볼, 줄에 대응된 프레임 |
| 5 | 전후 대조 결과, 또는 "가장 강한 가설"이라는 표시 |
| 6 | 처리량 점검표 한 줄(`n/a, read-only forensics`)과 출처가 있는 진단 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "동료가 보낸 힙 스냅숏이야. 메모리가 왜 늘었는지 봐 줘. 고치지는 말고."
>
> 1. 형식이 heapsnapshot임을 확인하고, 크기가 크므로 서브에이전트에서 로드합니다.
> 2. 노드를 sqlite에 한 행씩 덤프해 질의할 수 있게 만든 뒤에 읽기 시작합니다.
> 3. 크기가 가장 큰 객체 그룹에서 retainer 체인을 따라 GC 루트까지 갑니다.
> 4. 체인 끝의 노드를 산출물의 심볼로 파일과 줄에 대응시킵니다. 소스 매핑이 없으면 그렇게 말합니다.
> 5. 짝이 되는 이전 스냅숏이 없으므로 결론을 "가장 강한 가설"로 표시합니다.

### 실패, 중단, 모호할 때

- **소스 매핑이 없는 프레임.** 진단으로 내지 않습니다. 심볼을 풀거나 산출물에 심볼이 없다고 분명히 말합니다.
- **짝이 되는 캡처가 없을 때.** 확정된 원인이 아니라 산출물이 뒷받침하는 가장 강한 가설로 표시합니다.
- **캡처를 다시 돌리고 싶을 때.** 이 플레이북에서 산출물은 고정된 데이터셋입니다. 다시 돌리지 않고 읽습니다. 살아 있는 프로세스를 계측해야 하면 Runtime forensics입니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |

| [Runtime forensics](playbooks-work.md#playbook-runtime-forensics), [Bug fix](playbooks-work.md#playbook-bug-fix), [Perf issue](playbooks-work.md#playbook-perf-issue) | 플레이북 | 인계 |

## Feature {#playbook-feature}

원문: {{src:skills/poteto-mode/playbooks/feature.md}}

> 이름 붙인 데이터 모양에서 출발해 새 동작이나 바뀐 동작을 만듭니다.

### 언제 쓰는가

새 동작이나 바뀐 동작입니다. 예: "기능 플래그 뒤에 작은 기능을 만들어 줘. 정말 동작하는지 검증해 줘."

### 동작 방식

부모는 설계를 책임지고 계획, 리뷰, 검증을 맡습니다. 구현은 위임하고 리드로 남습니다.

1. 영향받는 서브시스템에 `how`.
2. 병렬 설계 탐색을 위해 `architect`.
3. **처리량 점검표**를 네 개의 할 일 항목으로 씁니다. 정말 해당하지 않는 차원(단일 파일, 팬아웃 없음)은 지우지 않고 `n/a: <이유>`로 남깁니다.
   - **Blocking first steps.** 팬아웃 전에 돌릴 관문.
   - **Independent workstreams.** 서로 겹치지 않는 파일, 서비스, 계층은 병렬화하고 공유 쓰기는 직렬화합니다.
   - **Shared mutable state.** 기본은 대상을 쪼개는 것입니다(`separate-before-serializing-shared-state` 원칙). 진짜 불변식이 있을 때만 직렬화합니다.
   - **Smallest safe decomposition.** 작업자 한 명이 최선이라면 왜 그런지 밝힙니다.
4. 코드 작성을 설정된 feature 모델(기본 `grok-4.7-xhigh-fast`)의 서브에이전트에게 구체적 범위로 위임합니다. 범위에는 파일 경로, 이름 붙인 데이터 모양과 그 조직 구조(`principle-model-the-domain`: 흩어진 불리언 대신 상태 기계, 분기 대신 테이블과 레지스트리, 반복되는 모양 가정 대신 타입 모델), 그것이 로직 작성 전에 선택되어야 한다는 점, 성공 기준(criteria)이 들어갑니다. 구현이 여러 유효한 모양(오류 처리, 추상화 계층, 테스트 구조)을 허용하면 대신 `arena` 스킬로 위임해, 러너들이 대안을 드러내고 교차 심사자가 선택을 지키게 합니다. 이것은 필수입니다. 이유를 대고 건너뛸 수 없고 Laziness Protocol도 이를 덮지 않습니다(이득은 줄 수를 아끼는 것이 아니라 리뷰의 분리입니다). 서브에이전트를 띄울 수 없는 경우에는 같은 리뷰 분리를 지키며 diff를 직접 소유하는 것으로 충족합니다. 중첩된 에이전트를 기다리며 "대기 중"이라고 답하지 않습니다. 주석은 Comments 규칙을 따릅니다. 수술적으로 고치고, upstream에서 온 파일은 원본에 다시 맞춥니다. 공유 프리미티브의 개선은 모든 소비자에 이식하고 각각 검증합니다. 자주 커밋합니다.
5. 맞는 표면에서 검증합니다. "결론 없음"이나 잘못된 표면은 통과가 아닙니다.
6. 작고 순서 있는 커밋으로 리베이스합니다. 후속은 스택으로 쌓습니다. `sequence-verifiable-units` 원칙에 따라 작은 단위 하나를 만들고 검증하고 커밋한 뒤 다음으로 갑니다.
7. 설계가 논쟁적이면 배포 전에 `interrogate`.
8. Opening a PR을 실행합니다.

코드가 서로 결합된 작업(기능 하나, 마이그레이션 하나)은 처리량 점검표를 안에 담은 단일 소유자에게 갑니다. 그 소유자가 블로킹 단계 뒤에 안에서 팬아웃합니다. 부모 수준의 팬아웃은 독립된 산출물(감사, 서브시스템을 가로지르는 조사, 경쟁 실험)을 내는 조각에 씁니다. 처리량 점검표는 단계 경계마다 다시 씁니다. 인터럽트로 잇지 말고 새 소유자를 띄웁니다.

### 응답

무엇을 만들었는지, 무엇을 왜 골랐는지, 처리량 점검표, 열린 결정. 설계 대안은 표로 씁니다.

### 함정과 주의점

- 구현이 여러 유효한 모양을 허용하는데 `arena` 위임을 이유를 대고 건너뛰면 규칙(mandatory) 위반입니다. 서브에이전트를 띄울 수 없을 때만 같은 리뷰 분리를 지키며 diff를 직접 소유하는 것으로 갈음합니다.
- 코드가 결합된 작업에 부모 수준 팬아웃을 걸지 않습니다.

### 흐름도

```flow Feature 플레이북의 흐름
start 새 동작이나 바뀐 동작
step 1. how로 서브시스템 읽기
step 2. architect로 설계 탐색
step 3. 처리량 점검표
step 4. 구현 위임
  alt 유효한 모양이 여럿 | arena로 위임 (필수)
  alt 서브에이전트를 띄울 수 없음 | 같은 리뷰 분리로 diff를 직접 소유
step 5. 맞는 표면에서 검증
  alt 결론 없음 또는 잘못된 표면 | 통과로 세지 않고 표시함
step 6. 작고 순서 있는 커밋
step 7. interrogate (설계가 논쟁적일 때)
step 8. Opening a PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 서브시스템에 대한 `how` 출력 |
| 2 | `architect`의 스케치와 근거 |
| 3 | 네 항목(Blocking first steps / Independent workstreams / Shared mutable state / Smallest safe decomposition)의 처리량 점검표 |
| 4 | 파일 경로, 이름 붙인 데이터 모양과 그 조직 구조, 성공 기준이 들어간 위임과 서브에이전트의 diff. `arena` 경로면 러너들의 대안과 교차 심사자의 선택 |
| 5 | 맞는 표면에서 통과한 검증 |
| 6 | 작은 단위마다 만들고 검증하고 커밋한 이력 |
| 7 | `interrogate`의 검토 결과 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "설정 화면에 '알림 일시 중지' 기능을 추가해 줘. 기능 플래그 뒤에 두고 실제로 동작하는지 검증해 줘."
>
> 1. `how`로 알림이 지금 어디서 결정되는지 읽고, `architect`로 상태 모양의 후보를 비교합니다.
> 2. 처리량 점검표를 네 항목으로 씁니다. 파일이 셋뿐이고 서로 겹치므로 Independent workstreams는 `n/a: 세 파일이 결합됨`, Smallest safe decomposition은 "작업자 한 명"과 그 이유입니다.
> 3. 데이터 모양은 `paused: boolean`과 `resumeAt: Date`를 따로 두지 않고 `active | pausedUntil(time)`의 상태로 정해서 위임합니다(`model-the-domain`).
> 4. 오류 처리 방식이 두 가지로 갈려 유효한 모양이 여럿이므로 구현은 `arena`로 위임합니다.
> 5. 앱을 실제로 띄워 일시 중지를 누르고 알림이 오지 않는지 봅니다.
> 6. 단위마다 커밋하고 Opening a PR로 끝냅니다.

### 실패, 중단, 모호할 때

- **구현이 여러 유효한 모양을 허용할 때.** `arena`로 위임하는 것은 필수입니다. 이유를 대고 건너뛸 수 없고 Laziness Protocol도 이를 덮지 않습니다.
- **서브에이전트를 띄울 수 없을 때.** 같은 리뷰 분리를 지키며 diff를 직접 소유하는 것으로 충족합니다. 중첩된 에이전트를 기다리며 "대기 중"이라고 답하지 않습니다.
- **처리량 점검표의 차원이 해당하지 않을 때.** 항목을 지우지 않고 `n/a: <이유>`로 남깁니다.
- **단계 경계를 넘을 때.** 점검표를 다시 씁니다. 인터럽트로 잇지 말고 새 소유자를 띄웁니다.
- **검증 결과가 "결론 없음"이거나 표면이 틀렸을 때.** 통과가 아닙니다. 표시합니다.
- **설계가 논쟁적일 때.** 배포 전에 `interrogate`를 돌립니다.

## Refactoring {#playbook-refactoring}

원문: {{src:skills/poteto-mode/playbooks/refactoring.md}}

> 구조는 바꾸고 동작은 바꾸지 않습니다.

### 언제 쓰는가

이름 바꾸기, 추출, 인라인, 중복 제거, 이동처럼 동작을 보존하는 구조 변경입니다. 동작을 더하는 Feature, 동작을 바로잡는 Bug fix와 다릅니다. 정리하다가 빠진 기능이나 진짜 버그가 드러나면 분리하고, 고정한 계약에 대해 구조 변경을 먼저 배포합니다. 재설계는 허용되지만 이름을 붙이고 Feature로 라우팅합니다. 크거나 여러 곳에 걸친 구조 작업은 `figure-it-out` 스킬의 몫이고, 이 플레이북은 집중적인 것에서 중간 크기까지의 변경입니다.

### 동작 방식

1. **동작 계약을 먼저 고정합니다.** 영향받는 서브시스템에 `how`를 돌려 계약을 파악하고, 구조를 옮기기 전에 현재 동작을 담는 특성화 테스트, 스냅숏, 동등성 하니스를 씁니다. 커버리지가 없는 영역이면 구조를 건드리기 전에 고정을 씁니다. 타입 검사와 린트는 고정이 아닙니다.
2. **코드에 빠진 구조에 이름을 붙입니다**(`principle-model-the-domain`). 모양이 이미 분명하고 지역적이면 지루한 코드는 그대로 둡니다. 재구성은 분기나 불가능한 상태를 지워야 하고 간접 계층을 더해서는 안 됩니다.
3. **목표 모양에 이름을 붙입니다.** 오늘 새로 만든다면 모듈 배치, 타입, 호출 그래프가 어떠해야 하는지 씁니다(`principle-foundational-thinking`, `principle-redesign-from-first-principles`). 목표가 함수 경계를 넘으면 옮기기 전에 `architect` 스킬로 모양을 병렬 탐색합니다.
4. **더하기 전에 뺍니다.** 죽은 코드를 지우고, 호출자가 하나인 래퍼를 접고, 중복 검증기(validator)를 없애고, 고아 참조를 제거한 뒤 새 모양을 넣습니다(`principle-subtract-before-you-add`). 목표 모양에 이르는 가장 작은 변경만 배포합니다(`principle-laziness-protocol`). "도움이 될지도 모르는" 추측성 정리는 되돌립니다.
5. **동작을 보존하는 작은 단계로 움직이고, 매 단계 고정이 초록이어야 합니다.** API 재구성은 모든 호출자를 옮기고 옛 API를 같은 웨이브에서 지웁니다(`principle-migrate-callers-then-delete-legacy-apis`). 호환 shim도, 옛 경로와 새 경로의 병행도 없습니다. 이름 바꾸기는 실제 파일과 대조합니다. 이름 변경은 문자열, 산문, 역참조의 사용처를 조용히 놓칩니다. 기계적 수정은 설정된 refactoring 모델(기본 `grok-4.7-xhigh-fast`)의 서브에이전트에게 구체적 범위(파일 경로, 옮길 이름, 유지할 동작)로 위임합니다.
6. **동작이 바뀌지 않았음을 실제 산출물로 증명합니다.** "컴파일된다"가 아닙니다(`principle-prove-it-works`). 큰 재구성은 동등성 검사를 돌립니다. 옛것과 새것의 출력을 diff하는 스크립트, 기록된 기준선을 새 코드에 재생, 맞는 표면에서의 스모크 실행.
7. **유지할 가치가 있는지 확인합니다.** 성공의 척도는 독자 부담의 감소입니다(`principle-minimize-reader-load`). diff가 어디에서도 독자 부담을 낮추지 않으면 되돌립니다.
8. 작고 순서 있는 커밋으로 리베이스합니다. 삭제 커밋, 재구성, 후속 정리의 순서입니다. `sequence-verifiable-units` 원칙으로 짜서 각 동작 보존 조각이 다음 전에 초록을 유지하게 합니다. Opening a PR을 실행합니다.

### 응답

바뀐 구조, 고정한 계약, 동등성 증명, 독자 부담의 변화, 배포한 것과 되돌린 것. 새 동작은 없습니다.

### 함정과 주의점

- 타입 검사와 린트를 동작 고정으로 세지 않습니다.
- 이름 바꾸기는 문자열과 산문 속 사용처를 놓치므로 실제 파일로 대조합니다.
- 호환 shim을 남기지 않습니다.

### 흐름도

```flow Refactoring 플레이북의 흐름
start 동작은 그대로, 구조만 변경
step 1. 동작 계약 고정
  alt 커버리지가 없음 | 구조를 건드리기 전에 고정부터 씀
step 2. 빠진 구조에 이름 붙이기
step 3. 목표 모양에 이름 붙이기
step 4. 더하기 전에 빼기
step 5. 작은 단계로 이동
step 6. 실제 산출물로 동등성 증명
step 7. 유지할 가치 확인
  alt 어디서도 줄지 않음 | 되돌림
step 8. 작고 순서 있는 커밋
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 현재 동작을 담는 특성화 테스트, 스냅숏, 또는 동등성 하니스 |
| 2 | 코드에 빠진 구조의 이름 |
| 3 | 목표 모양(모듈 배치, 타입, 호출 그래프) |
| 4 | 죽은 코드, 한 호출자 래퍼, 중복 검증기, 고아 참조의 삭제(8단계에서 삭제 커밋으로 정리) |
| 5 | 고정이 초록인 작은 이동들, 옛 API 삭제, 이름 바꾸기의 실제 파일 대조 |
| 6 | 동등성 증명(출력 diff 스크립트, 기록된 기준선의 재생, 스모크 실행 중 하나) |
| 7 | 독자 부담이 줄었다는 판단, 아니면 되돌림 |
| 8 | 삭제 커밋, 재구성, 후속 정리의 순서로 쌓인 커밋 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "`UserService`에서 `UserStore`로 넘기기만 하는 래퍼가 여러 겹이라 읽기 힘듭니다. 동작은 바꾸지 말고 정리해 줘."
>
> 1. 현재 응답 모양을 기록하는 특성화 테스트를 먼저 씁니다. 타입 검사와 린트는 고정으로 세지 않습니다.
> 2. 호출자가 하나뿐인 래퍼 둘을 인라인하는 삭제 커밋을 먼저 만듭니다.
> 3. 남은 이름 바꾸기는 문자열과 문서 속 사용처까지 실제 파일에서 대조합니다.
> 4. 옛 인터페이스를 쓰는 호출자를 모두 옮기고 같은 웨이브에서 옛 인터페이스를 지웁니다. 호환 shim은 남기지 않습니다.
> 5. 기록해 둔 기준선을 새 코드에 재생해 출력이 같음을 확인합니다.
> 6. "X는 어디서 오나?"를 따라가는 계층이 줄었는지 봅니다. 줄지 않은 변경은 되돌립니다.

### 실패, 중단, 모호할 때

- **정리 중 진짜 버그나 빠진 기능이 드러날 때.** 분리하고, 고정한 계약에 대해 구조 변경을 먼저 배포합니다.
- **재설계가 필요해질 때.** 허용되지만 이름을 붙이고 Feature로 라우팅합니다.
- **범위가 크거나 여러 곳에 걸칠 때.** 이 플레이북은 집중적인 것에서 중간 크기까지입니다. 큰 구조 작업은 `figure-it-out`입니다.
- **커버리지가 없을 때.** 구조를 건드리기 전에 고정부터 씁니다.
- **추측성 정리.** "도움이 될지도 모르는" 정리는 되돌립니다. 독자 부담을 낮추지 못한 diff도 되돌립니다.

## Prototype {#playbook-prototype}

원문: {{src:skills/poteto-mode/playbooks/prototype.md}}

> 설계나 동작에 관한 결정을 값싸게 내리려고 만드는 일회용 스케치입니다.

### 언제 쓰는가

"prototype", "mock it up", "try this layout", "sketch it to decide" 같은 요청, 또는 사람에게 묻는 대신 관찰로 경험적 갈림길을 풀고 싶을 때입니다. 예: "마크다운 렌더러 프로토타입을 두 개 만들어서 비교하자. 각각 에이전트를 띄워 줘."

### 동작 방식

부모는 설계 결정을 책임지고 코드는 책임지지 않습니다. 프로토타입은 일회용 도구이고 실제 구현은 Feature가 따릅니다. Laziness Protocol의 "가장 작은 변경"과 검증 기준(bar)이 뒤집히는 유일한 플레이북입니다. 폴리시보다 속도이고, 코드 품질은 중요하지 않으며, 계획도 없습니다. 엄밀함은 올바른 설계를 싸게 고르는 데 있습니다. 사용자가 묻지 않은 변형을 제안하고, 접근 하나를 버리고 다른 것을 시도합니다.

1. 프로토타입이 내릴 결정의 범위를 정합니다. 어느 레이아웃, 어느 상호작용, 어느 밀도인지, 경험적 갈림길이면 어느 동작, 타이밍, 접근인지. 결정이 없으면 프로토타입도 없습니다. Feature로 갑니다.
2. 설계 공간이 열려 있으면 참고 자료를 모읍니다. 선행 사례를 찾고 테마, 팔레트, 레이아웃의 무드보드를 요약하고, 만들기 전에 사용자가 방향을 고르게 합니다. 방향이 정해졌으면 건너뜁니다.
3. 프로덕션 소스와 분리된 격리 스크래치 디렉터리에 일회용으로 만듭니다. 시각적 결정은 아이디어를 그려 내는 가장 가벼운 스택(바닐라 HTML/CSS/JS, CDN 의존성, 핫 리로드가 있는 개발 서버)으로, 동작이나 타이밍 결정은 질문을 실행하는 가장 작은 스크립트로 만듭니다. 프로덕션 프레임워크도, 테스트도, 추상화도 없습니다.
4. 대안을 비교할 때는 하나의 전환기(버튼이나 키 입력) 뒤에 각 변형에 라벨을 붙여 만듭니다. `exhaust-the-design-space` 원칙을 값싸게 만든 것입니다.
5. 맞는 표면에서 검증합니다. 시각적 결정은 control 스킬로 변형마다 스크린숏을 찍고 상호작용을 구동합니다. 동작이나 타이밍 결정은 타이밍을 로깅하고, 출력을 찍고, 렌더를 지켜보며 결정하려는 대상을 관찰합니다. 여기서는 관찰이 테스트이지 단언이 아닙니다.
6. 대안, 트레이드오프, 추천을 제시합니다. 산출물은 결정과 일회용 산출물이고 배포할 코드가 아닙니다. 선택한 방향을 실제 구현을 위해 Feature(모양이면 `architect`)로 넘깁니다.

### 응답

탐색한 변형, 증거(시각적 결정은 스크린숏, 동작 결정은 관찰한 출력이나 타이밍), 트레이드오프, 추천, 스크래치 경로. 프로토타입이 일회용이라고 분명히 밝힙니다.

### 함정과 주의점

결정이 없으면 프로토타입을 만들지 않습니다. 프로토타입 코드를 프로덕션으로 승격하지 않고 Feature로 다시 짓습니다.

### 흐름도

```flow Prototype 플레이북의 흐름
start 결정을 싸게 내려야 함
step 1. 내릴 결정의 범위 정하기
  alt 결정이 없음 | 프로토타입도 없음, Feature로
step 2. 참고 자료 모으기
step 3. 일회용으로 만들기
step 4. 대안은 전환기 뒤에
step 5. 맞는 표면에서 관찰
step 6. 대안, 트레이드오프, 추천 제시
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 프로토타입이 내릴 결정 한 문장 |
| 2 | 선행 사례와 무드보드 요약, 사용자가 고른 방향 |
| 3 | 프로덕션 소스와 분리된 스크래치 디렉터리의 일회용 코드 |
| 4 | 하나의 전환기 뒤에 라벨이 붙은 변형들 |
| 5 | 시각적 결정이면 변형마다 스크린숏, 동작이나 타이밍 결정이면 관찰한 출력이나 타이밍 |
| 6 | 대안, 트레이드오프, 추천. 결정과 일회용 산출물이 산출물이고 배포할 코드는 아닙니다 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "대시보드 카드를 촘촘하게 할지 넉넉하게 할지 정하고 싶어. 두 안을 만들어 보여 줘."
>
> 1. 결정을 "카드 밀도 두 가지 중 무엇인가"로 좁힙니다. 결정이 분명하므로 진행합니다.
> 2. 방향이 이미 정해져 있으므로 참고 자료 모으기는 건너뜁니다.
> 3. 스크래치 디렉터리에 바닐라 HTML/CSS로 페이지 하나를 만들고, 키 입력 하나로 두 밀도를 전환하게 합니다. 테스트도 추상화도 없습니다.
> 4. control 스킬로 변형마다 스크린숏을 찍고 스크롤 상호작용을 구동합니다.
> 5. 트레이드오프(한 화면에 보이는 카드 수 대 눈의 피로)와 추천을 적고, 프로토타입은 일회용이며 실제 구현은 Feature로 넘긴다고 밝힙니다.

### 실패, 중단, 모호할 때

- **내릴 결정이 없을 때.** 프로토타입을 만들지 않고 Feature로 갑니다.
- **설계 공간이 열려 있을 때.** 만들기 전에 참고 자료를 모으고 사용자가 방향을 고르게 합니다.
- **묻고 싶은 갈림길이 관찰로 풀릴 때.** 사용자에게 묻지 않고 이 플레이북으로 관찰해서 결정합니다(poteto-mode의 Non-negotiables). 제품이나 취향의 결정이면 사람에게 남깁니다.
- **프로토타입 코드를 쓰고 싶을 때.** 프로덕션으로 승격하지 않습니다. 선택한 방향은 Feature(모양이면 `architect`)로 다시 짓습니다.

## Visual parity {#playbook-visual-parity}

원문: {{src:skills/poteto-mode/playbooks/visual-parity.md}}

> 두 구현이나 스타일 시스템 마이그레이션 사이의 픽셀 단위 동등성을 이미지 diff로 검증합니다.

### 언제 쓰는가

예: "이 플래그가 켜져 있을 때 행 간격이 너무 큽니다. 두 번째 이미지가 맞는 것입니다. 재현하고 일치할 때까지 고쳐 줘."

### 동작 방식

부모는 픽셀 단위 동등성을 책임지고, 기준선이 명세이며 그것을 건드리지 않습니다. 동등성은 눈이 아니라 이미지 diff로 검증합니다.

1. 마이그레이션 전에 기준선을 먼저 세웁니다. 현재 컴포넌트를 상태별로 스크린숏 찍는 시각 회귀 하니스, 그리고 두 구현을 맞추는 경우 대상도 찍습니다. 기준선이 없으면 동등성 주장도 없습니다. 후속이 아니라 진행을 막는 선행 조건입니다.
2. 반(反)편법 조항을 밝히고 지킵니다. 하니스 수정 금지, 기준선 조작 금지, diff를 통과시키려고 컴포넌트를 재구성하는 일 금지. 기준선이 틀려 보이면 멈추고 묻습니다. 고치지 않습니다.
3. 컴포넌트 하나씩 마이그레이션합니다. 워크트리를 나눠 병렬화하고 컴포넌트당 소유자 하나(`separate-before-serializing-shared-state` 원칙). 공유 프리미티브는 진행을 막는 단계로 먼저 마이그레이션합니다.
4. control 스킬로 맞는 표면에서 컴포넌트마다 기준선과 이미지 diff로 검증합니다. 0이 아닌 diff는 실패입니다. 픽셀 차이를 조사합니다. 컴포넌트별로 diff가 0이 될 때까지 `/loop`을 돕니다.
5. 컴포넌트별로, 또는 안전한 묶음별로 Opening a PR을 실행합니다.

### 응답

마이그레이션한 컴포넌트, 각각의 diff 결과, 기준선 하니스의 위치, 남은 것.

### 함정과 주의점

기준선을 수정하거나, 하니스를 고치거나, diff를 통과시키려고 컴포넌트를 재구성하는 것은 금지된 편법입니다.

### 흐름도

```flow Visual parity 플레이북의 흐름
start 두 구현이나 스타일 시스템이 픽셀까지 같아야 함
step 1. 기준선 먼저
  stop 기준선이 없음 | 동등성 주장도 없음, 진행을 막는 선행 조건
step 2. 반편법 조항
  stop 기준선이 틀려 보임 | 멈추고 묻는다, 고치지 않는다
step 3. 컴포넌트 하나씩
step 4. 이미지 diff로 검증
  back 4 | 0이 될 때까지 loop
step 5. 컴포넌트별 또는 안전한 묶음별 PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 상태별 스크린숏을 찍는 시각 회귀 하니스와 기준선 |
| 2 | 밝히고 지키는 반편법 조항 |
| 3 | 컴포넌트마다 마이그레이션한 결과(소유자 하나, 워크트리 하나) |
| 4 | 컴포넌트별 이미지 diff 결과 |
| 5 | 컴포넌트별 또는 안전한 묶음별 PR |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "버튼과 입력창을 새 스타일 시스템으로 옮겨 줘. 화면은 픽셀 하나도 달라지면 안 돼."
>
> 1. 옮기기 전에 두 컴포넌트를 상태(기본, 호버, 비활성)별로 스크린숏 찍는 하니스를 만들고 기준선을 저장합니다.
> 2. 반편법 조항을 응답에 적어 둡니다. 하니스도 기준선도 컴포넌트 구조도 diff를 맞추려고 건드리지 않습니다.
> 3. 두 컴포넌트가 공유하는 색 토큰을 먼저, 진행을 막는 단계로 옮깁니다. 이어서 컴포넌트마다 워크트리와 소유자를 나눠 병렬로 옮깁니다.
> 4. 컴포넌트마다 기준선과 이미지 diff를 내고, 0이 아니면 픽셀 차이를 조사해 0이 될 때까지 `/loop`을 돕니다.
> 5. 안전한 묶음별로 PR을 엽니다.

### 실패, 중단, 모호할 때

- **기준선이 없을 때.** 동등성 주장도 없습니다. 후속 작업이 아니라 진행을 막는 선행 조건입니다.
- **기준선이 틀려 보일 때.** 멈추고 묻습니다. 고치지 않습니다.
- **diff가 0이 아닐 때.** 실패입니다. 픽셀 차이를 조사하고 컴포넌트별로 0이 될 때까지 `/loop`을 돕니다.
- **금지된 지름길.** 하니스 수정, 기준선 조작, diff를 통과시키려는 컴포넌트 재구성은 하지 않습니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| `control-cli`, `control-ui` | cursor-team-kit의 스킬 | 4 |
| [`separate-before-serializing-shared-state`](principles.md#skill-principle-separate-before-serializing-shared-state) | 원칙 | 3 |
| Cursor의 `/loop` 명령 | 내장 명령 | 4 |
| [Opening a PR](playbooks-pr.md#playbook-opening-a-pr) | 플레이북 | 5 |

## Authoring or modifying a skill {#playbook-authoring-a-skill}

원문: {{src:skills/poteto-mode/playbooks/authoring-a-skill.md}}

> `SKILL.md`를 쓰거나 고칠 때의 절차입니다. 스킬의 목소리를 책임집니다.

### 언제 쓰는가

스킬을 새로 쓰거나 고칠 때입니다. 예: "이 저장소의 데이터베이스 마이그레이션을 검증하는 스킬을 써 줘". 안내서는 `SKILL.md`를 손으로 그냥 쓰지 말고 이 플레이북으로 보내라고 권합니다. 에이전트용 글은 사람용 글보다 기준이 높습니다. 도움이 안 되는 문장 하나가 미래의 에이전트가 따르는 지시가 되기 때문입니다.

### 동작 방식

1. **create-skill** 스킬(Cursor의 `SKILL.md` 작성용 내장 스킬)을 씁니다.
2. 스킬을 검증(validation)합니다. 프런트매터에 `name`과 `description`이 있고, 참조한 파일이 존재하고, 스킬 간 링크가 풀립니다.
3. 구조적이면 테스트 케이스를 만듭니다. 주관적이면 건너뜁니다.
4. Opening a PR을 실행합니다.

문체 지침은 이렇습니다. 의심스러우면 지웁니다. 결정을 바꾸는 글만 남깁니다. 이유는 빼고 하라고만 말합니다. 규칙(rule)이 이유 없이는 헷갈릴 때만 설명합니다. 톤을 범위에 맞춥니다. 구조적 출처(타입, README, 설정)를 가리키며 `encode-lessons-in-structure` 원칙(principle)을 따릅니다. 다른 스킬에는 경로로 위임하고 다시 쓰지 않습니다. 계속 부딪히는데 정리되지 않은 워크플로가 있으면 새 스킬을 제안합니다.

### 응답

스킬의 요약, 핵심 설계 결정, 검증 메모.

### 함정과 주의점

작업 중 스킬이 오작동한다고 그 자리에서 스킬을 고치지 않습니다. 별도 PR로 고치고 작업은 계속 진행합니다. 기능 작업에 뒤섞여 나간 스킬 수정은 리뷰에서 보이지 않고 평가할 수도 없습니다.

### 흐름도

```flow Authoring or modifying a skill 플레이북의 흐름
start SKILL.md를 쓰거나 고침
step 1. create-skill 스킬 사용
step 2. 스킬 검증
step 3. 테스트 케이스
step 4. Opening a PR
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 쓰거나 고친 `SKILL.md` |
| 2 | 검증 결과(프런트매터의 `name`과 `description`, 참조된 파일의 존재, 스킬 사이 링크가 풀리는지) |
| 3 | 구조적이면 테스트 케이스 |
| 4 | PR |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "릴리스 노트를 정리하는 반복 작업을 스킬로 만들어 줘."
>
> 1. Cursor의 `create-skill`로 초안을 만들고, 이유를 길게 풀어 쓰지 않고 결정을 바꾸는 문장만 남깁니다. 다른 스킬이 하는 일은 다시 쓰지 않고 경로로 가리킵니다.
> 2. 프런트매터에 `name`과 `description`이 있는지, 참조한 파일이 있는지, 다른 스킬로 가는 링크가 풀리는지 검증합니다.
> 3. 출력이 구조적(정해진 섹션)이라 테스트 케이스를 하나 씁니다. 검증할 구조가 없고 주관적이라면 건너뜁니다.
> 4. Opening a PR로 끝내고, 응답에 요약, 설계 결정, 검증 메모를 적습니다.

### 실패, 중단, 모호할 때

- **애매하면 지웁니다.** 결정을 바꾸는 문장만 남깁니다.
- **주관적일 때.** 테스트 케이스를 건너뜁니다. 구조적일 때만 씁니다.
- **반복되지만 스킬로 잡히지 않은 워크플로를 만났을 때.** 새 스킬을 제안합니다.
- **정해진 구조가 이미 있을 때.** 구조적 출처(타입, README, 설정)를 가리킵니다(`encode-lessons-in-structure`).

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| `create-skill` | Cursor의 내장 스킬 | 1 |
| [`encode-lessons-in-structure`](principles.md#skill-principle-encode-lessons-in-structure) | 원칙 | 본문의 작성 지침 |
| [Opening a PR](playbooks-pr.md#playbook-opening-a-pr) | 플레이북 | 4 |

## Eval {#playbook-eval}

원문: {{src:skills/poteto-mode/playbooks/eval.md}}

> 스킬, 구조, 프롬프트 변경이 에이전트 행동에 미치는 영향을 승격하기 전에 눈가림으로 시험합니다.

### 언제 쓰는가

스킬 수정은 앞으로의 모든 세션에 영향을 주므로 실험처럼 시험해야 합니다. 예: "이 스킬 변경에 eval 플레이북을 돌려 줘. 두 변형에 같은 작업, 후보는 눈가림 유지."

### 동작 방식

부모는 실험 설계를 책임지고 계획, 눈가림, 실행, 종합을 맡습니다. 이 플레이북은 관찰자 효과 하나를 겨냥해 만들었습니다. 평가받는다는 것을 아는 에이전트는 다르게 행동합니다.

**눈가림의 필수 규칙(non-negotiable)**

- 후보가 보는 디렉터리, 파일, 프롬프트 어디에도 `eval`, `test`, `judge`, `experiment`, `rubric`, `score`, `compare`, `benchmark`, `candidate`, `arena`를 쓰지 않습니다.
- 후보 프롬프트는 자연스러운 사용자 요청처럼 보여야 합니다. 메타가 아니라 목표를 말합니다.
- 연쇄를 유도하는 단서를 주지 않습니다. 후보에게 어떤 스킬, 원칙, 파일을 적용했는지 나열하라고 하지 않습니다. 설계 노트를 일반적으로 묻고, 연쇄를 따랐는지는 자기 보고가 아니라 코드 모양으로 채점합니다.
- 디렉터리와 슬러그 이름을 정화합니다. 사용자가 고를 법한 프로젝트다운 이름을 씁니다.
- 다른 후보가 있다고 후보에게 알리지 않습니다.
- 심사자는 심사 중임을 알아도 되지만 출력을 정화된 라벨로만 보고 모델 이름은 절대 보지 못합니다.
- 두 변형을 비교할 때는 한 심사자가 두 집합을 한 번에, 한 척도로, 각 집합이 어디서 왔는지 모르는 채 채점합니다.

**단계**

1. **틀 짓기.** 시험하는 변형이 무엇이고 무엇이 성공인지 씁니다. 심사자만을 위한 루브릭, 곧 구체적 기준(criteria) 3~6개를 쓰고 후보에게는 감춥니다.
2. **정화된 환경을 준비합니다.** 후보마다 변형이 놓인 작업 디렉터리를 둡니다. 자연스러운 작업이 가졌을 맥락(프로젝트 뼈대(skeleton), 후보가 자연스럽게 읽을 스킬)을 심어 둡니다.
3. **자연스러운 프롬프트 하나를 씁니다.** 사용자가 칠 법한 그대로, 측정 대상이 새지 않게 합니다.
4. **후보 N개를 병렬로 띄웁니다.** `arena` 스킬의 Phase B에 따라 서로 다른 모델로, 각자 정화된 디렉터리에서, 같은 프롬프트로.
5. **눈가림된 심사자 하나를 띄웁니다.** `arena` 스킬의 Phase C에 따라 다른 모델 계열로. 심사자는 정화된 라벨의 출력과 루브릭을 보고 모델 이름은 보지 않습니다.
6. **자기 보고가 아니라 대화 기록으로 연쇄를 검증(verification)합니다.** 활성 워크스페이스의 `agent-transcripts/` 디렉터리(시스템 프롬프트가 경로를 알려 줌) 아래의 후보별 로컬 대화 기록을 읽습니다. `~/.cursor/projects/*/`를 글롭하지 않습니다. 워크스페이스 경계를 넘어 무관한 프로젝트의 비공개 채팅을 읽게 됩니다. 각 후보가 실제로 연 파일을 봅니다. 연쇄를 따랐는지는 실제로 읽은 파일과 코드의 모양으로 채점하고, 후보의 주장으로는 채점하지 않습니다.
7. **모든 후보 출력을 직접 처음부터 끝까지 읽습니다.** 심사자의 판정과 비교합니다. 불일치는 모델이 편향되었거나 루브릭이 모호하다는 뜻입니다. 종합합니다.

### 응답

시험한 변형, 루브릭, 후보별 메모, 심사자의 판정, 종합, 변형을 승격할지에 대한 추천.

### 함정과 주의점

- 눈가림 금지어를 후보가 보는 어디에도 남기지 않습니다.
- 후보의 자기 보고로 연쇄 준수를 채점하지 않습니다.
- 심사자와 의견이 다르면 판단보다 먼저 루브릭을 의심하라고 안내서는 권합니다.
- `~/.cursor/projects/*/`를 글롭하지 않습니다.

### 관련 스킬

`arena`([설계하기](arena-swarm.md#skill-arena))의 Phase B와 C를 그대로 씁니다.

### 흐름도

```flow Eval 플레이북의 흐름
start 변형이 에이전트 행동에 주는 영향을 시험
step 1. 틀 잡기
step 2. 소독한 환경
step 3. 자연스러운 프롬프트 하나
step 4. 후보 N개를 병렬로
step 5. 눈가림 심사자 하나
step 6. 대본에서 사슬 확인
step 7. 모든 출력을 직접 읽고 종합
  alt 심사자와 의견이 갈림 | 모델의 편향이거나 루브릭이 모호함
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 시험할 변형, 성공으로 칠 행동, 심사자에게만 보이는 루브릭(3~6개 기준) |
| 2 | 후보마다 변형이 놓인 소독된 작업 디렉터리 |
| 3 | 자연스러운 사용자 요청 같은 프롬프트 하나 |
| 4 | 후보 N개의 출력 |
| 5 | 소독된 라벨로만 본 심사자의 판정 |
| 6 | 후보가 실제로 연 파일에 근거한 사슬 채점 |
| 7 | 직접 읽은 뒤의 종합 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "새로 쓴 리뷰 스킬 문구가 실제로 에이전트의 리뷰를 바꾸는지 시험해 줘."
>
> 1. 성공을 "PR 설명의 검증 섹션에 실행한 명령이 적힌다"로 정하고, 이 기준 세 개를 루브릭으로 씁니다. 후보에게는 보이지 않습니다.
> 2. 모델마다 프로젝트처럼 보이는 이름의 디렉터리를 둘씩 만들고, 하나에는 옛 문구를, 하나에는 새 문구를 둡니다. 디렉터리와 파일에 `eval`, `judge` 같은 단어를 쓰지 않습니다.
> 3. 프롬프트는 "이 브랜치의 PR 설명을 써 줘"처럼 사용자가 실제로 칠 만한 말 한 줄입니다.
> 4. 서로 다른 모델 셋이 각자 자기 디렉터리 둘에서 같은 프롬프트로 돕니다. 어떤 스킬을 적용했는지 자기 보고를 요구하지 않습니다.
> 5. 다른 모델 계열의 심사자가 소독된 라벨만 보고 두 묶음을 한 번에 같은 척도로 채점합니다. 대본에서 각 후보가 실제로 연 파일을 따로 확인합니다.
> 6. 모든 출력을 직접 읽고 심사자와 비교해 종합하고 승격 여부를 권고합니다.

### 실패, 중단, 모호할 때

- **눈가림이 깨질 수 있는 표현.** `eval`, `test`, `judge`, `experiment`, `rubric`, `score`, `compare`, `benchmark`, `candidate`, `arena`는 후보가 보는 디렉터리, 파일, 프롬프트에 쓰지 않습니다. 후보에게 다른 후보가 있다고 말하지 않습니다.
- **후보의 자기 보고.** 적용한 스킬이나 파일을 나열하라고 묻지 않습니다. 사슬을 따랐는지는 실제로 연 파일과 코드 모양으로 채점합니다.
- **대본 읽기.** 활성 작업공간의 `agent-transcripts/` 아래에서만 읽습니다. `~/.cursor/projects/*/` 전체를 글롭하지 않습니다. 작업공간 경계를 넘어 관계없는 프로젝트의 비공개 채팅을 읽게 되기 때문입니다.
- **심사자와 내가 갈릴 때.** 모델이 편향되었거나 루브릭이 모호하다는 뜻입니다. 종합에서 다룹니다.
- **두 변형을 비교할 때.** 심사자 한 명이 두 묶음을 한 번에 같은 척도로, 어느 묶음인지 모르는 채 채점합니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| [`arena`](arena-swarm.md#skill-arena) | 스킬 | 4(Phase B), 5(Phase C) |
| 활성 작업공간의 `agent-transcripts/` | 데이터 | 6 |

# architect: 코드 전에 모양을 정한다

![세 로봇이 각자의 탁자에서 경쟁하는 다리 모형을 그리고 심사 로봇이 회의적으로 살피는 일러스트](images/design.jpg)

## architect {#skill-architect}

원문: {{src:skills/architect/SKILL.md}} {{src:skills/architect/references/runner-prompt.md}} {{src:skills/architect/references/rationale-template.md}} {{src:skills/architect/references/design-red-flags.md}} {{src:docs/guide/04-design.md}}

> 타입, 시그니처, 모듈 구조를 코드 전에 스케치하고, 구현이 채워지는 동안에도 루프 안에 머뭅니다.

### 언제 쓰는가

원문의 `description`이 든 트리거는 `/architect`, "architect this", "design this", 그리고 코드로 곧장 뛰어들면 잘못된 모양이 굳을 사소하지 않은 작업입니다. `disable-model-invocation: true`라서 사용자가 부르거나 `poteto-mode` 같은 워크플로가 부릅니다. `poteto-mode`는 코드가 함수 경계를 넘으면 구현 전에 이 스킬을 부르고, Feature와 Refactoring 플레이북이 이 스킬을 씁니다. 안내서는 이 정도 설계 작업이 모든 변경에 필요한 것은 아니라고 말합니다. 대부분의 변경은 필요 없고, 함수 경계를 넘거나 소유권을 옮기는 변경에는 `/architect`가 맞습니다. 이때 `/arena`가 함께 옵니다.

핵심 태도는 구현 전에 설계하는 것입니다. 본문을 `not implemented`로 두고 의사코드로 적은 타입, 함수 시그니처, 클래스 모양, 모듈 경계를 스케치하고, 여러 모델의 관점을 종합한 다음 선택한 스케치에 맞춰 코드를 채웁니다. 구현이 스케치가 틀렸음을 보이면 버리고 다시 설계합니다.

### 동작 방식

시작할 때 단계마다 항목이 하나씩인 할 일 목록을 엽니다. 단계는 Ground, Sketch, Agree, Implement, Scrap 다섯 개입니다.

**A단계. 문제를 그라운딩합니다.** 새 코드가 건드리는 모든 시스템의 진짜 멘탈 모델을 세웁니다. 관련 서브시스템마다 `how` 스킬을 돌립니다. 파일 이름을 대는 것은 그라운딩이 아닙니다. `how`가 요구하는 추적된 모델을 만듭니다. 설계가 소유권이나 계층을 다시 정의한다면 기존 모양에 `why` 스킬도 돌려 그 근거가 추측이 아니라 제약이 되게 합니다. 주변 시스템과 통합할 것이 없는 진짜 그린필드일 때만 A단계를 건너뜁니다.

**B단계. 스케치합니다.** 설계 스케치 작업과 A단계의 그라운딩 산출물(artifact)로 `arena` 스킬을 돌립니다. 각 러너의 프롬프트로 `references/runner-prompt.md`를 넘깁니다. 각 후보는 `references/rationale-template.md`의 모양을 갖춘 설계 패키지를 만듭니다. 러너는 `pstack-models.mdc` 규칙(rule)의 `architect runners` 줄에서 가져오고, `arena runners` 줄 대신 씁니다. 규칙이나 그 줄이 없으면 `claude-opus-5-5-max`, `gpt-5.6-sol-max`, `grok-4.7-xhigh-fast`를 씁니다. 별칭이나 거부된 항목은 `arena` 스킬 A단계의 러너 규칙을 따릅니다.

- **두 번 설계합니다.** 첫 후보가 충분해 보여도 종합 전에 구조가 뚜렷이 다른 후보를 적어도 둘 요구합니다. `exhaust-the-design-space` 원칙(principle)을 구체화한 것입니다. 한 모양 안의 점 수정이 아니라 모양 전체의 대안입니다.
- 종합 전에 모든 후보를 `references/design-red-flags.md`(아래 "설계 적신호" 참조)에 견줘 거릅니다. 다음 기여자는 연 파일만 보고, 가장 가까운 예를 베끼며, 컴파일되는 가장 짧은 길을 택하는 에이전트라고 가정합니다. 한 파일에서 맞아 보이는 변경이 저장소 전체에도 맞는 설계를 선호합니다.
- 살아남은 후보는 인터페이스 깊이로 비교합니다. 더 작고 단순한 공개 표면 뒤에 더 많은 복잡도를 숨기는 설계를 선호합니다. 풍부한 인터페이스는 능력을 여러 계층에 흩뿌리지 않고 집중시켜 호출 사슬을 짧게 유지할 수 있습니다.
- `arena`가 종합된 설계 패키지 하나를 돌려줍니다. 종합 결정이 근거서의 "Synthesis decision" 절을 채웁니다.

**C단계. 합의(선택 사항).** 기본은 종합된 설계로 곧장 구현에 들어가는 것이고 사람의 체크포인트가 없습니다. 호출한 사람이 명시적으로 요청할 때만 체크포인트를 둡니다. "/architect with checkpoint", "stop and show me before implementing" 같은 요청입니다. 그러면 종합된 설계를 보여 주고 승인을 위해 멈춥니다.

어느 쪽이든 종합본은 `foundational-thinking` 원칙의 "scaffold first" 모드로 별도 커밋이 될 수 있습니다. 채워 넣는 동안의 계획되고 범위가 정해진 깨짐은 `outcome-oriented-execution` 원칙에 따라 괜찮습니다. 구현 전에 설계에 대한 적대적 압력이 필요하면 종합된 스케치에 `interrogate` 스킬을 돌립니다. 사람이 (체크포인트에서든 나중에든) 모양에 반대하면 그것을 A단계의 증거로 취급합니다. 코드를 더 쓰기 전에 다시 그라운딩하고 B단계를 다시 돌립니다.

**D단계. 스케치에 맞춰 구현합니다.** `not implemented` 본문을 코드로, 의사코드를 로직으로 바꿉니다. 종합된 스케치가 계약입니다. 스케치에서의 이탈은 조용히 흡수할 마찰이 아니라 드러낼 가치가 있는 신호입니다. 함수가 스케치가 예상하지 못한 매개변수를 필요로 하면 스케치가 틀렸는지, 요구를 놓쳤는지, 구현이 지나친지를 묻습니다.

**E단계. 아키텍처가 틀렸으면 버립니다.** 구현이 스케치가 흡수할 수 없는 마찰을 계속 만들면 스케치를 버립니다. 틀린 설계에 수정을 덧대지 않습니다(`redesign-from-first-principles`, `fix-root-causes` 원칙). 신호는 개별 사례가 아니라 *패턴*입니다. 징후는 다음과 같습니다.

- 같은 모양의 우회책이 무관한 코드에서 반복해 나타난다.
- 서로 무관한 여러 엣지 케이스가 모두 특수 분기를 필요로 한다.
- 컴파일하려면 타입에 탈출구(`any`, 캐스트, 실제로는 항상 채워지는 선택 필드)가 필요하다.
- 스케치는 상태가 공유되지 않는다고 했는데 "락이 필요하다"는 반사가 나온다.
- 호출자가 추상화를 쓰려면 그 내부 규칙을 알아야 한다.
- 구현 전체에서 같은 모양의 독립적인 D단계 이탈이 둘 이상 있다.

판단력을 씁니다. 엣지 케이스 몇 개가 아키텍처를 단죄하지는 않고, 어떤 문제는 정말로 복잡합니다. 데이터의 복잡도는 설계의 복잡도가 아닙니다. 버릴 때는 이렇게 합니다. (1) 지금까지 만든 것에 `how`를 다시 돌립니다. (2) 새 제약이 첫날부터의 가정이었던 것처럼 다시 설계합니다(redesign-from-first-principles). (3) 더하기 전에 뺍니다(`subtract-before-you-add` 원칙). 새 스케치는 자라기 전에 옛것보다 작아야 합니다. (4) B단계로 돌아가 `arena`를 다시 돌립니다.

#### 산출물

호출자의 사용법을 먼저 쓰고 타입 스케치는 거기서 도출합니다. 작은 변경은 새 타입과 시그니처가 든 파일 하나, 큰 작업은 모듈 지도와 타입 정의입니다. 근거서가 사용 스케치와 종합 결정을 포함해 `references/rationale-template.md`의 모양으로 함께 갑니다.

#### 러너 프롬프트

오케스트레이터는 B단계에서 모든 병렬 후보 러너에게 `references/runner-prompt.md`를 그대로 넘기고 과제, A단계 그라운딩 산출물, 격리된 작업 디렉터리, 출력 경로 같은 변수 입력을 주변에 채웁니다. 작업 디렉터리는 가능하면 git 워크트리이고 아니면 스케치 디렉터리 아래 러너별 하위 디렉터리입니다. 중요한 것은 후보 사이의 독립성입니다. 러너는 먼저 `architect` 스킬 전체를 읽습니다. 그 스킬이 러너가 들어와 있는 워크플로이기 때문입니다. 그다음 후보 설계 패키지 하나(타입 스케치, 함수 시그니처, 모듈 지도, 근거서)를 만들며 다음 규율을 적용합니다. 오케스트레이터는 이 축들로 후보를 비교해 기준안을 고릅니다.

- 호출자의 사용법이 먼저입니다. 타입 전에 README 식 사용법과 실제 호출 지점 두세 개를 쓰고 거기서 타입 스케치를 도출합니다. 사용법이 명세이고 둘은 일치해야 하며, 어긋나면 스케치를 사용법에 맞춥니다.
- 데이터 구조가 먼저입니다. 핵심 타입을 맞추면 코드가 뻔해집니다. 지배적인 접근 패턴마다 제안한 구조를 통과시켜 봅니다. 답이 "나중에 맵, 인덱스, 캐시를 추가하면 된다"면 구조가 틀린 것입니다.
- 인터페이스 깊이. 공개 표면의 크기 대비 그 뒤에 숨은 능력을 비교합니다. 구현이 덜 단순해지더라도 복잡도를 피호출자로 끌어들이는 단순한 인터페이스를 선호합니다. 전송 타입이나 wire 타입을 공개 API에 두지 않고, 인터페이스 뒤에서 도메인 타입으로 파싱합니다.
- 공유 상태. 두 행위자가 모두 쓸 수 있으면 "어떻게 되나?"를 묻습니다. 답이 "아무 일 없다"가 아니면 기본은 행위자별 상태에 읽기 경계에서의 병합입니다(`separate-before-serializing-shared-state` 원칙).
- 경계를 보이게 만듭니다. 본문은 `not implemented` 오류, 까다로운 로직은 `// TODO` 의사코드, 의도와 불변식을 말하는 문서 주석. 독자가 타입과 시그니처만 읽고 입력에서 출력까지 데이터를 따라갈 수 있어야 합니다.
- 불변식을 타입에 인코딩합니다. 오용하기 어려운 타입 > 런타임 검사 > 산문 주석(`encode-lessons-in-structure` 원칙).
- 경계에서 검증(validation)하고 안쪽에서는 타입을 믿습니다(`boundary-discipline` 원칙). 비즈니스 로직은 순수 함수로, 셸은 얇게.
- 불변식마다 단일 진실 원천. 동기화하지 말고 도출합니다.
- 해당하면 멱등한 상태 전이(`make-operations-idempotent` 원칙). 연산이 두 번 돌거나 중간에 죽으면 어떻게 되는지 묻습니다.
- 짧은 호출 사슬. 흐름을 따라가는 데 파일이 셋을 넘으면 계층을 평평하게 합니다(`laziness-protocol`, `minimize-reader-load` 원칙).

러너는 여러 러너 중 하나이고 각자 다른 모델에서 돕니다. 자기 모델이 낼 수 있는 최선의 설계를 만들고 다른 러너에 대비해 헤지하지 않습니다. 후보 사이의 차이가 기준안을 고르고 이식하는 데 쓰는 신호이고, 안전해 보이는 중간으로 수렴하면 탐색이 무의미해집니다.

#### 근거서 템플릿

타입 스케치와 함께 가는 한 쪽짜리 산문입니다. 제목은 문장형 대소문자, 상투 문구 없음입니다. 절은 다음과 같습니다.

| 절 | 내용 |
| --- | --- |
| Problem | 한 문단. 무엇을 하려는지, 기존 시스템이나 제약의 무엇이 모양을 자명하지 않게 만드는지. A단계가 드러낸 제약(연동해야 할 기존 타입, 깨뜨릴 수 없는 호출자, 경계를 넘은 불변식)을 여기에 적습니다 |
| Usage (caller's view) | 타입 스케치보다 먼저 씁니다. 소비자가 읽는 README나 퀵스타트와 그들의 코드의 현실적인 호출 지점 두세 개. 무엇을 임포트하고 무엇을 호출하고 무엇이 돌아오는지. 스케치는 이것에서 도출되며 둘이 어긋나면 스케치를 사용법에 맞춥니다 |
| Shape | 권장 아키텍처. 데이터 구조가 먼저이고 그다음 시그니처를 따라 데이터가 어떻게 흐르는지. 하중을 받는 결정에 이름을 붙이고, 타입에 인코딩된 불변식, 검증이 있는 곳, 시스템이 일부러 하지 않는 것을 밝힙니다. 인터페이스 깊이를 명시적으로 판단합니다 |
| Synthesis decision | arena가 채웁니다. 어느 후보가 기준안이 되었고 이유, 다른 후보들에서 무엇을 가져왔고 무엇이 왜 기각되었는지 |
| Tradeoffs accepted | 선택한 모양이 하는 트레이드오프마다 불릿 하나. "Y를 얻는 대가로 X를 감수한다" 형식 |
| Alternatives considered | 필수입니다. 구체적 대안 모양을 하나 이상, 왜 졌는지 한 줄. 구현의 단순함만이 아니라 인터페이스 깊이로 판단합니다. 같은 모양의 변종을 나열하지 않습니다. 실제 경쟁안이 있었다면 둘이나 셋을 적고, 제약이 답을 강제했다면 하나면 되며 그때는 "이것이 유일하게 가능한 모양이었다. 왜냐하면..."으로 씁니다. 이 절은 다른 러너의 후보가 아니라 선택한 모양이 검토하고 기각한 설계 대안을 다룹니다 |
| Open questions and risks | 스케치 중 눈에 띈 것으로 사람이 판단해야 할 것과 구현 시작 전에 알릴 위험. 주장이 아니라 질문으로 적습니다 |
| Next implementation step | 스케치에 맞춰 처음 만들 것. 한 문장 |

#### 설계 적신호 {#ref-design-red-flags}

`references/design-red-flags.md`는 종합 전에 모든 후보를 거르는 기준입니다. 적신호는 모양을 고치거나 기각할 이유입니다.

| 적신호 | 뜻과 징후 |
| --- | --- |
| Shallow module(얕은 모듈) | 큰 인터페이스를 노출하면서 숨기는 복잡도는 적은 모듈. 깊이는 공개 표면의 크기 대비 그 뒤에 숨은 능력과 정책으로 판단합니다. 깊은 모듈을 깊은 호출 사슬과 혼동하지 않습니다. 깊은 호출 사슬은 이해를 계층에 흩뿌리고 깊은 모듈은 능력을 인터페이스 하나 뒤에 집중시킵니다. 징후는 호출자가 연산 하나를 마치려고 메서드 여러 개를 조율하고, 공개 옵션이 내부 단계나 구현 선택을 노출하고, 인터페이스를 배워도 구현을 배우는 수고가 줄지 않는 것 |
| Information leakage(정보 누수) | 여러 모듈이 같은 내부 결정에 의존합니다. 표현, 정책, 프로토콜 세부가 두 곳 이상에 나타나 바꾸려면 함께 고쳐야 합니다. 전송 타입이나 wire 타입의 공개 재수출은 누수입니다. 외부 데이터는 인터페이스 뒤에서 도메인 타입으로 파싱하고, 저장 스키마, 프레임워크 객체, 프로토콜 세부는 비공개로 둡니다 |
| Temporal decomposition(시간적 분해) | 모듈을 소유한 지식이 아니라 실행 순서로 나눕니다. load, validate, transform, save를 따로 두면 표현 하나와 그 불변식이 여러 경계에 반복됩니다. 도메인 지식과 소유권을 중심으로 묶습니다. 다른 시점에 도는 메서드도 같은 결정을 지키면 한 모듈에 속할 수 있습니다 |
| Pass-through method(통과 메서드) | 같은 모양의 인자를 다른 메서드로 그대로 넘깁니다. 복잡도를 숨기지 않고 계층만 더합니다. 없애거나 연산을 마칠 수 있는 모듈로 책임을 옮깁니다. 정책, 적응, 뚜렷한 추상화를 더할 때만 전달 경계를 둡니다 |
| Split ownership(쪼개진 소유권) | 모듈 둘 이상이 같은 상태에 쓰거나 각자 사본을 둡니다. 한쪽 작성자만 고치는 에이전트는 나머지를 보지 못해 규칙이 갈립니다. 상태 조각마다 소유자 하나를 두고, 다른 모듈은 읽거나 소유자에게 바꾸라고 요청합니다 |
| Two ways to do one task(한 일의 두 길) | 같은 일을 하는 길이 둘 이상입니다. 에이전트는 먼저 찾은 길을 베끼므로 모든 길에 호출자가 늘어납니다. 길을 하나로 두고, 나머지 호출자를 옮긴 뒤 같은 변경에서 지웁니다 |
| Importable internals(임포트 가능한 내부) | 호출자가 모듈의 내부를 임포트할 수 있습니다. 에이전트는 컴파일되는 가장 짧은 길을 택해 내부를 직접 가져와 그것이 인터페이스가 됩니다. 모듈 밖에서 내부를 닿을 수 없게 해서, 바깥에서 임포트하면 빌드가 실패하게 합니다 |
| Hand-synced list(손으로 맞춘 목록) | 같은 항목을 둘 이상의 곳이 나열하고, 항목을 더하려면 목록마다 고쳐야 합니다. 목록 하나만 본 에이전트는 그 하나만 고칩니다. 목록을 하나로 두고 나머지는 도출합니다. 도출할 수 없으면 목록이 어긋날 때 빌드가 실패하게 합니다 |

### 사용 예

```text
/architect 코드를 쓰기 전에 임포트 파이프라인을 설계해 줘. 호출하는 쪽이 어떻게 쓰는지가 가장 중요해.
```

`/architect`가 먼저 그라운딩합니다. 설계가 건드리는 코드에 `/how`를 돌리고, 소유권이나 계층을 옮긴다면 `/why`도 돌립니다. 그다음 `/arena`로 경쟁하는 설계 스케치를 만드는데, 각 스케치는 호출자의 사용법이 먼저이고 타입, 시그니처, 모듈 지도가 뒤따릅니다. 기본은 종합된 설계에서 곧장 구현으로 들어갑니다. 설계를 먼저 보고 싶다면 그렇게 말합니다.

```text
/architect with checkpoint. 구현하기 전에 멈추고 보여 줘.
```

### 함정과 주의점

- 첫 후보가 충분해 보여도 구조가 다른 후보를 둘 이상 요구합니다.
- 스케치에서의 이탈은 조용히 흡수하지 않고 드러냅니다.
- 같은 모양의 우회책이 반복되면(패턴) 스케치를 버립니다. 개별 엣지 케이스 몇 개는 아키텍처의 유죄 증거가 아닙니다.
- 사용법과 타입이 어긋나면 사용법이 이깁니다. 호출자의 경험이 명세입니다.
- 사람이 모양에 반대하면 코드를 더 쓰기 전에 다시 그라운딩하고 B단계를 다시 돌립니다.

### 관련 스킬

그라운딩에 [`how`](how.md#skill-how)와 [`why`](why.md#skill-why), 후보 생성에 [`arena`](arena-swarm.md#skill-arena), 스케치에 대한 적대적 압력에 [`interrogate`](interrogate.md#skill-interrogate)를 씁니다. 판단의 근거는 [원칙 장](principles.md)의 `exhaust-the-design-space`, `foundational-thinking`, `boundary-discipline`, `separate-before-serializing-shared-state` 등입니다.

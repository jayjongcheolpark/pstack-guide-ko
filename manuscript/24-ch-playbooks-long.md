# 장시간, 대규모 플레이북

원문 디렉터리: {{src:skills/poteto-mode/playbooks/autonomous-run.md}}

이 장은 한 번의 대화를 넘는 작업을 위한 플레이북 8개를 다룹니다. 하나의 작업을 끝까지 몰고 가는 Autonomous run, 이전 작업을 이어받고 안전하게 멈추는 Session pickup과 Pause safely, 디스크를 정리하는 Worktree and simulator cleanup, 계획서를 쓰는 Multi-phase or multi-PR plan, 그리고 여러 PR과 에이전트 무리를 다루는 Orchestrate, Autopilot-full, Autopilot-stack입니다. 밤새 맡기는 사용법은 [실전 부의 밤새 돌리기](overnight.md)에서 예와 함께 다룹니다.

## Autonomous run {#playbook-autonomous-run}

원문: {{src:skills/poteto-mode/playbooks/autonomous-run.md}} {{src:docs/guide/07-overnight.md}}

> 끝나는 조건을 먼저 정하고, 멈추지 않고 그 조건까지 몰고 갑니다.

### 언제 쓰는가

멈추지 않고 끝까지 가야 하는 긴 작업입니다("run until done", "/loop until X"). 며칠에 걸친 상시 프로젝트는 Orchestrate이고, 이것은 하나의 작업을 하나의 조건까지 몰고 가는 플레이북입니다.

### 동작 방식

부모는 종료 조건을 책임집니다.

1. 첫 반복 전에 종료 조건을 검사 가능한 술어로 밝힙니다(테스트 초록, 재현 수정됨, PR N개 모두 병합됨, 픽셀 diff 0).
2. Cursor의 `/loop` 명령(내장 기능이며 pstack 스킬이 아님)으로 깨우는 방식을 고릅니다. 지켜볼 이벤트(CI, 병합, 참조가 앞으로 감)가 있으면 이벤트에 깨우는 감시자 서브에이전트를 두고 긴 시간 기반 하트비트를 대비책으로 둡니다. 이벤트가 없으면 결과를 다시 확인할 가치가 생기는 때에 맞춘 고정 간격 하트비트를 씁니다.
3. 반복마다 증거가 정당화하는 가장 작은 변경을 하고, 술어에 대해 검증(verification)하고, 진전이 있으면 커밋하고, 도움이 되지 않은 변경은 버립니다. "도움이 될지도 모르는" 이중 안전장치는 되돌리고 그대로 두지 않습니다. `sequence-verifiable-units` 원칙(principle)에 따라 검사를 끝에 몰아서 하지 않고 단위마다 검증한 뒤 다음으로 갑니다.
4. 실행 중 발견은 자기 몫입니다. 고장난 스킬, 관련 버그, 불안정한 검증기(verifier), 리뷰 잡음, 도구 실패, 고아가 된 후속 작업, 고칠 수 있는 표류를 poteto-mode로 직접 처리합니다. 범위 밖 수정은 별도 PR로 냅니다. 되돌릴 수 있는 일을 사람에게 떠넘기거나 `AskQuestion`을 쓰지 않습니다. 올리는 것은 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 진짜 제품이나 취향 판단, 진짜 막다른 길뿐입니다. 술어를 주된 동력으로 삼고 곁가지 수정마다 술어로 돌아옵니다.
5. 반복마다 `show-me-your-work` 스킬로 체크포인트를 남깁니다. 무엇이 바뀌었고 술어가 움직였는지 한 행씩입니다.
6. 술어가 충족되면 멈춥니다. 정체는 멈춤이 아닙니다. 계속하면서 접근을 바꿔 뚫습니다. 진짜 막다른 길은 빙빙 돌지 말고 드러내고, 승리를 선언하려고 술어를 완화하지 않습니다.

### 응답

종료 조건, 실행한 반복, 랜딩된 것, 버린 것, 술어의 최종 상태.

### 함정과 주의점

기간은 종료 조건이 아닙니다. 안내서는 "4시간 동안 작업해"라고 하면 에이전트가 확인할 것이 없고 결과 대신 네 시간의 움직임을 얻는다고 경고합니다. `/loop`에 통과나 실패가 있는 술어를 줍니다.

### 흐름도

```flow Autonomous run 플레이북의 흐름
start 오래 걸리는 일을 멈추지 않고 끝까지
step 1. 종료 조건을 검사 가능한 술어로
step 2. 깨우는 장치 고르기
step 3. 반복
  alt 나아졌음 | 커밋
  alt 도움이 되지 않음 | 변경을 버림
step 4. 중간 발견은 스스로 처리
step 5. 반복마다 체크포인트
  back 4 | 술어가 충족될 때까지
step 6. 술어가 충족되면 멈춤
  stop 진짜 막다른 길 | 빙빙 돌지 않고 드러냄
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 검사 가능한 종료 술어 |
| 2 | 선택한 깨우는 장치(감시 서브에이전트와 긴 하트비트, 또는 고정 간격 하트비트) |
| 3 | 반복마다 커밋(나아졌을 때) 또는 폐기 |
| 4 | 별도 PR로 나간 범위 밖 수정 |
| 5 | 반복마다 결정 기록 한 행(무엇이 바뀌었고 술어가 움직였는지) |
| 6 | 술어 충족 확인 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "이 브랜치의 테스트가 전부 초록이 될 때까지 알아서 돌려 줘. 나는 자러 갈게."
>
> 1. 종료 조건을 "`bun test`가 실패 0으로 끝난다"로 적습니다.
> 2. 기다릴 이벤트는 CI이므로, 이벤트에서 깨우는 감시 서브에이전트와 긴 시간 기반 하트비트를 함께 씁니다.
> 3. 매 반복에서 실패 하나를 골라 그 증거가 정당화하는 가장 작은 변경을 하고 테스트를 돌립니다. 실패 수가 줄면 커밋하고, 그렇지 않으면 변경을 버립니다.
> 4. 반복 도중 깨진 린트 설정을 발견하면 그 수정은 별도 PR로 내보내고 술어로 돌아옵니다. 사용자에게 묻지 않습니다.
> 5. 매 반복 뒤 결정 기록에 한 행을 남깁니다.
> 6. 실패 0이 되면 멈춥니다. 중간에 정체하면 접근을 바꿔 밀고, 진짜 막다른 길이면 드러냅니다.

### 실패, 중단, 모호할 때

- **정체기.** 멈춤 조건이 아닙니다. 접근을 바꿔 밀고 나갑니다.
- **막다른 길.** 빙빙 돌지 않고 드러냅니다. 술어를 완화해 승리를 선언하지 않습니다.
- **도움이 되지 않은 변경.** 되돌립니다. "도움이 될지도 모르는" 변경을 남겨 두지 않습니다.
- **중간에 발견한 문제.** 깨진 스킬, 관련 버그, 불안정한 검증기, 리뷰 잡음, 도구 실패, 남은 후속, 고칠 수 있는 표류는 스스로 처리하고, 범위 밖 수정은 별도 PR로 냅니다. 되돌릴 수 있는 일을 사람에게 미루거나 `AskQuestion`을 쓰지 않습니다.
- **사람에게 올리는 것.** 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 제품이나 취향의 결정, 진짜 막다른 길뿐입니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |

## Session pickup {#playbook-session-pickup}

원문: {{src:skills/poteto-mode/playbooks/session-pickup.md}} {{src:docs/guide/03-understand.md}}

> 이전 에이전트가 남긴 진행 중 작업을 이어받습니다. 이전 기록을 읽고, 다시 하지 않습니다.

### 언제 쓰는가

다른 에이전트(혹은 지난주의 자신)가 브랜치를 중간에 남겨 두었을 때입니다. 대화 기록, 클라우드 에이전트 URL, 푸시된 브랜치에서 이어받습니다.

```text
/poteto-mode 이 브랜치를 이어받아 줘. 결정 기록을 읽고, 무엇이 끝났는지 파악하고, 거기서부터 계속해 줘. 끝난 일은 다시 하지 마.
```

### 동작 방식

부모는 재개 지점을 책임집니다.

1. **이전 기록을 찾습니다.** 활성 워크스페이스의 `agent-transcripts/` 디렉터리 아래의 로컬 대화 기록(시스템 프롬프트가 경로를 알려 줌), 클라우드 에이전트 URL, 푸시된 브랜치입니다. `~/.cursor/projects/*/`를 글롭하지 않습니다. 워크스페이스 경계를 넘어 무관한 프로젝트의 비공개 채팅을 읽게 됩니다. 메타데이터 개요와 마지막 메시지를 먼저 읽고 결정 지점을 찾아 거슬러 올라갑니다. 긴 대화 기록은 서브에이전트에서 파싱하고 줄인 타임라인만 메인 스레드에 둡니다(`principle-guard-the-context-window`).
2. **운영 상태를 재구성합니다.** 브랜치와 워크트리, 이미 랜딩된 것(`git log`, 베이스 대비 `git diff`), 열린 할 일, 내려진 결정. 이전 기록은 권위 있는 입력입니다. 다시 도출하려는 편향에 저항합니다.
3. **끝난 것과 남은 것을 비교합니다.** 배포된 것과 계획된 것을 비교하고, 재개 지점에 이름을 붙이고, 이전 재현을 다시 돌리거나 완료된 작업을 다시 하지 않습니다. "처음부터 검증해 볼게요" 패스는 권위 있는 기록을 못 믿을 것으로 취급하고 있다는 뜻입니다.
4. **남은 작업을 맞는 플레이북으로 라우팅하고 판정을 고릅니다.** 실행 계속, 끝난 권고 배포, 이전 결론의 승인 또는 번복, 실패한 실행의 포스트모템. 이 플레이북은 여기서 끝나고 라우팅된 플레이북이 나머지를 맡습니다.
5. **물려받은 주장을 원래 목표에 대해 실제 산출물(artifact)로 검증합니다**(`principle-prove-it-works`). 통과한 이전 자기 보고는 증명이 아닙니다.

### 응답

이전 에이전트가 어디서 멈췄는지, 물려받은 것과 다시 한 것(이상적으로는 다시 한 것이 없음), 재개 지점, 결과.

### 함정과 주의점

- 재개할 특정 채팅 하나는 이 플레이북이고, 최근 채팅 여러 개에서 맥락을 모으는 것은 [`recall`](teach-recall.md#skill-recall)입니다.
- 이전 기록을 못 믿어서 처음부터 다시 도출하지 않습니다. 단, 물려받은 주장은 실제 산출물로 검증합니다.

### 흐름도

```flow Session pickup 플레이북의 흐름
start 이전 에이전트의 작업을 이어받음
step 1. 이전 흔적 찾기
  alt 대본이 김 | 서브에이전트에서 파싱, 줄인 타임라인만 메인에
step 2. 운영 상태 재구성
step 3. 끝난 것과 남은 것을 대조
  alt 처음부터 다시 검증하고 싶어짐 | 흔적을 신뢰하지 않는 신호, 다시 하지 않음
step 4. 남은 일을 맞는 플레이북으로
step 5. 물려받은 주장을 실제 산출물로 검증
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 줄인 타임라인(메타데이터 개요, 마지막 메시지, 결정 지점) |
| 2 | 브랜치와 워크트리, 착륙한 것(`git log`, 기준(base)에 대한 `git diff`), 열린 할 일, 내린 결정 |
| 3 | 완료 대 미완료의 대조와 재개 지점 |
| 4 | 판정 하나(실행 이어가기, 끝난 권고를 배포, 이전 결론을 비준하거나 뒤집기, 실패한 실행의 사후 분석)와 라우팅 |
| 5 | 원래 목표에 대해 실제 산출물로 확인한 결과 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "어제 다른 에이전트가 하던 마이그레이션이야. 푸시된 브랜치가 있어. 이어서 끝내 줘."
>
> 1. 브랜치의 로그와 관련 대본이 있으면 메타데이터 개요와 마지막 메시지부터 읽고, 결정 지점만 거슬러 올라가 줄인 타임라인을 만듭니다. 대본이 길면 서브에이전트에서 파싱합니다.
> 2. 이미 착륙한 커밋과 열린 할 일을 정리합니다. 이전 흔적은 권위 있는 입력입니다.
> 3. 계획의 8개 단위 중 5개가 끝났다는 것을 확인하고 6번을 재개 지점으로 정합니다. 앞의 재현을 다시 돌리지 않습니다.
> 4. 남은 일은 Feature의 플레이북으로 라우팅하고 판정은 "실행 이어가기"입니다. 그 뒤는 라우팅한 플레이북이 맡습니다.
> 5. 마지막에 이전 에이전트가 낸 "통과" 보고를 믿지 않고 원래 목표에 대해 실제 산출물로 확인합니다.

### 실패, 중단, 모호할 때

- **처음부터 다시 검증하고 싶을 때.** 흔적을 신뢰할 수 없는 것으로 다루는 신호입니다. 이전 흔적은 권위 있는 입력이므로 다시 도출하려는 편향에 저항합니다.
- **이전 에이전트의 자기 보고가 통과일 때.** 증거가 아닙니다. 실제 산출물로 확인합니다.
- **대본을 어디서 찾을지.** 활성 작업공간의 `agent-transcripts/` 아래를 읽습니다. `~/.cursor/projects/*/` 전체를 글롭하지 않습니다. 작업공간 경계를 넘어 관계없는 프로젝트의 비공개 채팅을 읽게 되기 때문입니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| [`guard-the-context-window`](principles.md#skill-principle-guard-the-context-window), [`prove-it-works`](principles.md#skill-principle-prove-it-works) | 원칙 | 본문의 각 단계 |
| `git log`, `git diff` | 명령 | 2 |
| 상황에 맞는 플레이북 | 플레이북 | 4 |

## Pause safely {#playbook-pause-safely}

원문: {{src:skills/poteto-mode/playbooks/pause-safely.md}}

> 진행 중인 작업을 나중에 이어 갈 수 있게 깨끗하게 멈춥니다. 콜드 스타트 에이전트가 재개할 수 있는 체크포인트를 남깁니다.

### 언제 쓰는가

명시적으로 일시 정지를 요청하거나, 오프라인이 되거나, Cursor를 재시작하거나, 컨텍스트 압축이 임박했을 때입니다. Session pickup의 짝입니다. 명시적일 때만 씁니다. "keep going", "going to bed, keep going", "don't stop"이면 멈추지 않습니다.

### 동작 방식

1. 안전한 경계에서 멈춥니다. 현재의 원자적 단계를 끝내거나 물립니다. 새로운 것을 시작하지 않고 중첩된 서브에이전트를 취소합니다.
2. 멈추려고 되돌릴 수 없는 행동을 하지 않습니다. 이미 내보낸 것이 없으면 PR도 푸시도 하지 않습니다.
3. 작업을 영속적으로 만듭니다. 커밋되지 않은 편집을 현재 브랜치에 명확한 `wip:` 커밋 하나로 커밋해 아무것도 잃지 않게 합니다. 트리가 깨져 있으면 커밋 본문에 한 줄로 밝힙니다.
4. 컨텍스트 밖에 재개 메모를 씁니다. 의도, 하던 일, 진행과 검증된 것, 현재 상태, 다음 단계, 핵심 파일, 함정을 담습니다. 압축 트리거이면 `/tmp/<slug>-resume.md` 같은 파일에 씁니다. show-me-your-work 기록이 있으면 복제하지 말고 그것을 가리킵니다.

### 응답

루프의 어디에 있는지, 디스크에 있는 것과 머릿속에만 있는 것(경로만, diff 덤프 없이), 만든 커밋과 트리가 깨끗한지, 재개할 때의 첫 행동. 최종 보고가 아니라 일시 정지입니다.

### 흐름도

```flow Pause safely 플레이북의 흐름
start 명시적으로 일시 중지를 요청받음
  stop 계속 진행하라는 말 | 멈추지 않음 (keep going, don't stop)
step 1. 안전한 경계에서 멈춤
step 2. 되돌릴 수 없는 행동을 하지 않음
step 3. 작업을 영속화
step 4. 재개 노트를 컨텍스트 밖에 작성
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 안전한 경계에서 멈춘 상태 |
| 2 | 없음(새 PR, 새 푸시 없음) |
| 3 | 현재 브랜치의 `wip:` 커밋 하나. 트리가 깨졌으면 커밋 본문 한 줄에 밝힙니다 |
| 4 | 재개 노트. 컴팩션 트리거라면 `/tmp/<slug>-resume.md` 같은 파일. `show-me-your-work` 기록이 있으면 복제하지 않고 가리킵니다 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>

>
> 1. 진행 중이던 테스트 실행을 마치고, 새 작업은 시작하지 않으며 돌던 서브에이전트를 취소합니다.
> 2. 이미 열린 PR이 없으므로 PR을 새로 열지 않고 푸시도 하지 않습니다.
> 3. 커밋되지 않은 편집을 `wip:` 커밋 하나로 남기고, 테스트 하나가 아직 실패하므로 커밋 본문에 한 줄로 적습니다.

### 실패, 중단, 모호할 때

- **명시적으로 요청할 때만 씁니다.** "계속해", "자러 갈 건데 계속해", "멈추지 마" 같은 말에는 멈추지 않습니다.
- **트리가 깨져 있을 때.** 그렇게 커밋 본문에 한 줄로 밝힙니다.
- **일시 중지의 계기.** 명시적 일시 중지, 오프라인 전환, Cursor 재시작, 임박한 컨텍스트 컴팩션이 있습니다. 컴팩션이면 재개 노트를 파일로 씁니다.
- **PR과 푸시.** 이미 낸 것이 없으면 새로 PR을 열거나 푸시하지 않습니다. 일시 중지는 되돌릴 수 없는 행동으로 이루어지지 않습니다.

## Worktree and simulator cleanup {#playbook-worktree-cleanup}

원문: {{src:skills/poteto-mode/playbooks/worktree-cleanup.md}} {{src:skills/poteto-mode/scripts/worktree-audit.sh}}

> 병합되었거나 버려진 git 워크트리와 오래된 iOS 시뮬레이터를 정리해 디스크를 되찾습니다.

### 언제 쓰는가

"what's using my disk", "clean up worktrees", "prune safe-to-prune worktrees", "free up space", "delete old simulators" 같은 요청입니다. 안내서의 예입니다.

```text
/poteto-mode 디스크를 뭐가 먹고 있어? 지워도 안전한 워크트리는 정리해 줘.
```

이 플레이북은 코드 리뷰가 실수를 잡아 주지 않는 채로 사용자 상태를 지우는 유일한 플레이북이라서, 아래의 관문(gate)이 곧 리뷰입니다.

### 동작 방식

부모는 디스크와 안전 관문을 책임집니다. 삭제는 되돌릴 수 없으므로 모든 단계가 사용 중이거나 커밋되지 않은 작업이 있는 것을 지우지 않도록 지킵니다.

1. **스냅숏과 감사.** `df -h /`를 기록한 뒤 `scripts/worktree-audit.sh`를 돌립니다(`principle-build-the-lever`). 경로는 손으로 입력하지 않고 `git worktree list`에서 읽습니다. 손으로 쓴 `myrepo-worktrees/x`는 `.cursor/worktrees/myrepo/x`에 있는 것을 놓치기 때문입니다(`principle-encode-lessons-in-structure`). 이 스크립트는 워크트리마다 크기, 나이, 병합 상태, 커밋되지 않은 작업, PR 상태, 그것을 건드린 가장 최근 채팅을 분류하고 버킷을 제안합니다. 대화 기록 스캔은 느리므로 백그라운드로 돌립니다.
2. **버킷은 조언이지 허가가 아닙니다.** 고정된 채팅과 활성 채팅이 진짜 산출물입니다(`principle-prove-it-works`). 그 집합을 사용자나 사이드바에서 받아 모든 후보와 교차 확인합니다. 지렛대(스크립트)가 사용자가 고정해 둔 워크트리를 `safe`로 표시한 적이 있으므로, 고정 집합이 이깁니다.
3. **삭제 전에 사용 여부를 검증합니다.** 모든 `verify-recent-chat` 행이나 의심스러운 것은 서브에이전트를 팬아웃해 대화 기록을 읽고 그 채팅이 고정되었거나 진행 중인지, 어느 워크트리를 건드리는지 보고하게 합니다(`principle-guard-the-context-window`, 대화 기록은 대용량입니다). 고정된 채팅은 백그라운드 서브에이전트로 arena와 재현 트리를 형제 워크트리에 만들고, 그 이름이 사이드바에 나타나지 않아도 사용 중입니다.
4. **되돌릴 수 없는 손실 앞에서 멈춥니다.** `wip:N`은 추적되는 커밋되지 않은 편집 N개입니다. 깨끗한 워크트리는 브랜치에서 복구할 수 있지만 커밋되지 않은 작업은 사라지므로 diff를 보여 주고 결정을 먼저 받습니다. `scratch:N`은 추적되지 않는 일회용이라 버려도 안전하지만 파일 이름을 밝힙니다. Autonomy에 따라 깨끗하고 병합되었고 사용 중이 아니면 진행하고, `wip`와 사용 중이면 멈춥니다.
5. **확정된 집합을 정리합니다.** 경로마다 `git worktree remove --force <path>`. 무시된 빌드 산출물 때문에 디렉터리가 남으면 `rm -rf`한 뒤 `git worktree prune`. 브랜치 참조는 남으므로 커밋은 잃지 않습니다. `df -h /`로 확인하고 다시 나열합니다.
6. **시뮬레이터와 그 밖의 회수 대상.** 시뮬레이터가 보통 그다음으로 큰 이득입니다. `xcrun simctl --set testing delete all`(XCTestDevices 복제본), `xcrun simctl delete unavailable`, `xcrun simctl runtime list` 뒤에 `runtime delete <id>`로 오래된 런타임. 더 필요하면 Xcode `DerivedData`와 `iOS DeviceSupport`, `~/Library/Application Support/Cursor`(`state.vscdb.backup`, 그리고 작업 공간으로 연 폴더 이름이 붙은 `<root>`가 부풀어 오르는 `snapshots/roots/<root>`), 패키지 캐시(pnpm, uv, brew, yarn). 사용자가 남기라고 하지 않은 캐시만 지웁니다.

### 응답

`df -h /`의 전과 후와 되찾은 공간, 정리한 워크트리, 보류한 것마다 한 줄 이유(어느 채팅이 쓰는 중인지, 혹은 커밋되지 않은 작업).

### 보조 자료: worktree-audit.sh

이 스크립트는 모든 git 워크트리를 감사하고 제안 버킷이 붙은 표를 출력합니다. 헤더 주석은 "아무것도 지우지 않는다"고 말합니다. 사용법은 `worktree-audit.sh [repo-path]`이고 기본은 `git rev-parse --show-toplevel`입니다. git 저장소가 아니면 종료 코드 1로 "not in a git repo; pass a repo path"를 냅니다. 메인 워크트리(`git worktree list --porcelain`의 첫 항목)는 건너뜁니다. 실행할 때 `git fetch origin main --quiet`로 병합 열이 오래되지 않게 하고(실패하면 경고), `gh pr list --author "@me" --state all --limit 1000`을 한 번 돌립니다. 내 PR만 보입니다.

출력은 탭으로 구분되고 헤더는 `SIZE AGE MERGED DIRTY REMOTE PR LAST_CHAT BUCKET WORKTREE`이며 크기순(큰 것이 위)으로 정렬됩니다.

| 열 | 뜻 |
| --- | --- |
| `SIZE` | `du -sh` |
| `AGE` | HEAD 커밋 이후 일수(`12d` 형식), 모르면 `?` |
| `MERGED` | HEAD가 `origin/main`의 조상이면 `YES`, 아니면 `no`. 스쿼시 병합은 놓치므로 PR 상태가 더 강한 신호입니다 |
| `DIRTY` | `clean`, `wip:N`(추적되는 변경 N개), `scratch:N`(추적되지 않는 항목만 N개) |
| `REMOTE` | `detached`, `pushed`, `ahead<N>`, `no-remote` |
| `PR` | `#<number>/<STATE>` 또는 `-` |
| `LAST_CHAT` | 워크트리 경로를 언급하는 대화 기록 파일 중 가장 최근에 수정된 것의 날짜, 없으면 `-`. `~/.cursor/projects/<repo-path-slug>/agent-transcripts` 아래를 `rg`로 검색하며, 경로 뒤에 `/`나 `"`가 와야 일치하므로 `glint-482`는 `glint-482-r37`과 일치하지 않습니다 |

버킷 규칙(bucket)은 순서대로 적용됩니다. (1) DIRTY가 `wip:`로 시작하면 `hold-wip`. (2) PR에 `OPEN`이 들어 있으면 `hold-open-pr`. (3) 최근 4일 안에 채팅이 있으면 `verify-recent-chat`. (4) `MERGED=YES`이거나 PR이 하나라도 있으면(CLOSED 포함) `safe`. (5) 그 밖은 `review`. `git`, `gh`, `jq`, `rg`, `awk`, `sed`, `du`, `xargs`, `sort`, `mktemp`이 필요하고 BSD/macOS 형태의 `stat -f`와 `date -r`을 쓰므로 macOS 지향입니다. 부수 효과는 `origin/main` 원격 참조 갱신과 임시 파일뿐이고 아무것도 지우지 않습니다.

### 함정과 주의점

- 버킷 `safe`를 삭제 허가로 읽지 않습니다. 고정된 채팅의 집합이 우선합니다.
- `wip:N`은 diff를 보여 주고 결정을 받은 뒤에만 지웁니다.
- 경로를 손으로 입력하지 않고 `git worktree list`에서 읽습니다.

### 흐름도

```flow Worktree and simulator cleanup 플레이북의 흐름
start 디스크를 되찾고 싶음
step 1. 스냅숏과 감사
step 2. 버킷은 조언일 뿐
step 3. 삭제 전에 사용 여부 검증
step 4. 되돌릴 수 없는 손실 앞에서 멈춤
  stop wip:N (추적되는 미커밋 편집) | diff를 보이고 결정을 받음
  alt scratch:N (추적되지 않는 임시) | 파일 이름을 밝히고 버려도 됨
step 5. 확정된 집합을 정리
step 6. 시뮬레이터와 기타 회수 대상
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | `df -h /` 기록, 감사 표(크기, 나이, 병합 상태, 미커밋 작업, PR 상태, 마지막으로 닿은 채팅, 제안된 버킷) |
| 2 | 고정된 채팅과 활성 채팅의 집합, 후보별 교차 대조 |
| 3 | `verify-recent-chat` 행마다 채팅이 고정 또는 진행 중인지, 어떤 워크트리를 건드리는지에 대한 보고 |
| 4 | `wip`이면 보여 준 diff와 받은 결정, `scratch`이면 이름을 밝힌 파일 목록 |
| 5 | 정리된 워크트리. 브랜치 참조는 남습니다 |
| 6 | 정리된 시뮬레이터 등 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "디스크가 꽉 찼어. 안 쓰는 워크트리 정리해 줘."
>
> 1. `df -h /`를 기록하고 감사 스크립트를 돌립니다. 대본 스캔이 느리므로 백그라운드로 돌립니다.
> 2. 스크립트가 `safe`로 표시한 워크트리 중에 사용자가 고정해 둔 채팅이 쓰는 것이 있어 고정된 쪽이 이깁니다. 사용자에게서 고정 채팅 목록을 받아 후보를 하나씩 대조합니다.
> 3. `verify-recent-chat` 행은 서브에이전트에게 대본을 읽혀 채팅이 진행 중인지 확인합니다.
> 4. `wip:2`인 워크트리는 diff를 보여 주고 결정을 받을 때까지 손대지 않습니다. 깨끗하고 병합되었고 쓰이지 않는 것만 진행합니다.
> 5. 확정된 경로마다 `git worktree remove --force`를 실행하고 `git worktree prune`을 돌린 뒤 `df -h /`로 회수량을 확인합니다.

### 실패, 중단, 모호할 때

- **미커밋 작업.** `wip:N`은 추적되는 미커밋 편집 N개입니다. 깨끗한 워크트리는 브랜치에서 복구할 수 있지만 미커밋 작업은 사라지므로 diff를 보이고 결정을 먼저 받습니다. `scratch:N`은 추적되지 않는 임시라 버려도 안전하지만 파일 이름을 밝힙니다.
- **버킷과 사용자의 고정 목록이 어긋날 때.** 고정된 집합이 이깁니다. 버킷은 조언이고 허가가 아닙니다.
- **이름이 사이드바에 없어도 쓰이는 워크트리.** 고정된 채팅이 배경 서브에이전트로 arena와 재현 트리를 형제 워크트리에 만들기 때문에, 그것들은 사용 중입니다.
- **디렉터리가 남을 때.** 무시된 빌드 산출물 때문에 디렉터리가 살아남으면 `rm -rf`한 뒤 `git worktree prune`을 합니다.
- **자율 규칙(Autonomy section).** 깨끗하고 병합되고 쓰이지 않는 것은 진행합니다. `wip`와 사용 중은 멈춥니다.
- **다른 회수 대상.** 사용자가 보관하라고 하지 않은 캐시만 비웁니다.
- **경고.** 코드 리뷰가 실수를 잡아 주지 않는 상태에서 사용자 상태를 지우는 유일한 플레이북이므로, 위의 관문들이 곧 리뷰입니다.

## Multi-phase or multi-PR plan {#playbook-multi-phase-plan}

원문: {{src:skills/poteto-mode/playbooks/multi-phase-plan.md}} {{src:skills/poteto-mode/scripts/check-plan.mjs}}

> 여러 단계나 스택된 PR에 걸친 작업의 계획서를 씁니다. 계획서가 산출물이고 구현은 하지 않습니다.

### 언제 쓰는가

단계나 스택된 PR에 걸친 작업입니다. 원문 README의 예는 "이 스킬들을 플러그인으로 오픈소스화해 줘. 내부 정보가 새면 안 되고, 임시 디렉터리에서 작업하고, 의존성 그래프를 먼저 보여 줘"입니다.

### 동작 방식

부모는 계획을 책임지고 코드는 책임지지 않습니다. 계획서는 소유자가 상자 하나씩 실행하고 운영자가 증거로 감사하는 체크리스트입니다.

1. 변경이 파일 한두 개에 접근이 뻔하면 계획을 건너뜁니다. 그렇다고 말하고 멈춥니다.
2. 글을 쓰기 전에 열린 질문을 프로토타입으로 정리합니다. 질문마다 `playbooks/prototype.md`를 돌립니다. 브랜치, SHA, 스크린숏을 부록 A용으로 보관합니다. 어떤 실행으로도 풀 수 없는 제품이나 취향 판단에 한해서만 운영자에게 묻고 선택지를 줍니다(`never-block-on-the-human` 원칙).
3. `subagent_type: "poteto-agent"`와 명시된 모델로 서브에이전트에서 탐색합니다(`guard-the-context-window` 원칙). 각자 파일 포인터, 관례, 테스트 명령, 진입점을 돌려줍니다. 덤프를 붙여 넣지 않습니다.
4. 아래 뼈대(skeleton)를 계획서 파일에 복사하고 모든 자리표시자를 채웁니다. 운영자가 경로를 지정하지 않으면 에이전트 저장소의 `docs/` 아래에 씁니다. 모든 제목과 하위 블록을 보인 순서대로 유지합니다. PR마다 절 하나, PR 하나는 자기 증거가 있는 변경 하나입니다(`sequence-verifiable-units` 원칙(principle)). **How to read this**에 실행 플레이북을 명시합니다. `playbooks/autopilot-full.md`와 `playbooks/autopilot-stack.md` 중에서는 `playbooks/autopilot-stack.md` 끝의 규칙(rule)에 따라 고르고, 상시 프로그램이면 `playbooks/orchestrate.md`를 씁니다.
5. `/technical-writing` 전체로 쓴 뒤 `/unslop`을 적용합니다. 본문은 Diátaxis 모드 하나, how-to입니다. 부록에 설명과 참조를 둡니다. 각 제목은 과업이나 발견을 말합니다. 긴 줄표도, 문장 중간 콜론도 쓰지 않습니다.
6. `node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`를 돌리고 출력되는 모든 줄을 고칩니다(`encode-lessons-in-structure` 원칙).
7. 넘깁니다. 계획서 경로와 스크립트 출력을 게시하고 멈춥니다. 실행은 운영자의 명시적 승인에서 시작하며, 계획서가 지정한 실행 플레이북 아래에서 합니다.

**검증 규칙.** 테스트만으로는 충분한 검증이 아닙니다. PR은 단위, 라이브, 성능 상자가 모두 체크되어야만 검증된 것입니다(`prove-it-works` 원칙(principle)). 이 문장이 검증 규칙(rule)이고 모든 검증 블록이 이것으로 시작합니다. 라이브 블록은 필수입니다. PR 헤드에서 열 개의 레인이 control 스킬로 실제 표면을 구동하며, `swarm` 스킬에 따라 `swarm workers` 모델(기본 `grok-4.7-xhigh-fast`)로 돌립니다. 레인마다 상자 하나이고 구체적 시나리오, 저장하는 스크린숏, 통과 술어가 있습니다. 레인 하나는 **Regression lane against trunk**입니다. 같은 핵심 시나리오를 트렁크와 헤드에서 돌립니다. 트렁크에 기능이 없으면 그 사실을 기록하고, 트렁크 결과를 지어내지 않고 diff가 더한 동작과 사용자가 기다리는 최종 상태를 관문으로 삼습니다. 성능 관문은 양쪽입니다. 트렁크와 헤드가 모두 지정된 지표를 내야 합니다. 트렁크에 기능이 없으면 diff가 더한 작업을 분리해서 그 작업과 사용자가 기다리는 종단 상태에 절대 예산을 정합니다. 서로 다른 시나리오 사이의 비율은 주장하지 않습니다. 성능 블록은 지표, 교차 실행하는 프로브, 먼저 측정한 트렁크 기준선, 실패하는 수치가 있는 규칙을 밝힙니다. 상호작용을 바꾸는 PR은 리뷰 관문이 걸립니다. 운영자가 병합 전에 채팅에서 스크린숏과 영상으로 검토합니다. 상호작용을 바꾸지 않는 PR은 `**Review gate.** None. <PR id> is not review-gated.`를 쓰고 그 아래에 상자를 두지 않습니다.

**Control 스킬.** 표면에 따라 고릅니다. 브라우저, Electron, 웹 UI는 cursor-team-kit의 `control-ui`, CLI와 TUI는 cursor-team-kit의 `control-cli`, 네이티브 모바일은 저장소가 가진 시뮬레이터 구동 스킬을 씁니다. 두 표면을 건드리는 PR은 양쪽에 레인을 둡니다. control 스킬이 없는 표면은 부록 C의 위험이고, 그 라이브 블록도 각 레인이 어떻게 구동하는지 이름을 밝힙니다.

#### 계획서 뼈대

계획서는 다음 구조를 따릅니다. 원문이 코드 블록으로 제공하는 뼈대의 골격입니다.

| 부분 | 내용 |
| --- | --- |
| `# <Program> plan` | 열 줄 미만. 무엇이 바뀌고 누구를 위한 것이며 프로그램이 강제하는 규칙과 순서 있는 PR id |
| `## How to read this` | 상자 하나는 작업 단위 하나이고 모든 상자는 자기를 확인하는 증거를 이름 붙입니다. 중첩된 상자는 위 상자의 하위 단계. 증거(파일, 로그 줄, 스크린숏, 테스트 실행, SHA)가 있을 때만 상자를 체크합니다. 본문은 how-to이고 부록은 설명하고 기록합니다. 실행 플레이북, 누가 병합하는지, 검증 규칙 문장 |
| `## Program checklist` | `### Arm the program`(운영자의 승인에 `/loop 1h`로 감사 tick을 무장, 트렁크에서 플레이북과 스킬을 읽기, tick 프롬프트, 정지 명령), `### Spawn owners`(PR마다 소유자 하나, 의존성 그래프, 파일 경계, 리뷰 관문), `### PR mechanics, for every PR`(포지 정하기, Opening a PR에 따라 준비 상태로 열기, 린트와 타입 검사, `/deslop`과 `/no-comments`, Bugbot 분류, 리베이스 규칙), `### Verdict and merge, for every PR`(코드 준비 헤드에서 swarm: 관문 레인 하나, 라이브 레인 열 개, 성능 레인, 감사 레인 둘 이상), `### Boot recipe, for every live lane` |
| PR 절 | PR마다 `**Depends on.**`, `**Files.**`, `**Build.**`, `**You see.**`, `**Verify, unit.**`, `**Verify, live.**`(레인 1에서 10), `**Verify, perf.**`(Metric, Probe, Baseline, Rule), `**Review gate.**`, `**Merge.**` 순서 |
| `## Close the program` | 모든 상자가 증거와 함께 체크됨, 운영자에게 실행 플레이북이 이름 붙인 보고서 |
| 부록 | A. Prototype evidence, B. Alternatives rejected, C. Risks, D. Links and reading list |

깨끗한 판정은 모든 레인이 `PASS`일 때만이고, 레인이 메모로 남긴 결함도 발견으로 소유자에게 돌려보냅니다. PR 절의 `**Merge.**` 상자는 루트의 정확한 헤드 SHA에 대한 깨끗한 판정, Bugbot 분류 완료, 판정 뒤 현재 트렁크로의 리베이스(patch-id 불변), 소유자의 스쿼시 병합 또는 루트의 스택 덧붙임입니다.

원문의 시간당 감사 tick 프롬프트는 이렇게 요약됩니다. 트렁크의 실행 플레이북을 다시 읽고, 그것에 대해 운영을 감사해 표류를 그 tick에서 고치고, 모든 활성 레인을 부수 효과로만 진행을 판단해 조사하고, 막힌 레인은 내려놓고 대체를 즉시 배치하고, 그다음 이전 상태 메시지가 보고하지 않은 추적된 변경이 있을 때만 운영자에게 채팅으로 짧은 상태를 게시하며, 어느 쪽이든 그 tick의 행을 결정 기록에 남깁니다.

### 응답

계획서 경로, 의존성과 리뷰 관문 집합이 있는 PR id들, 프로토타입이 증명한 것과 증명되지 않은 것, 검사 스크립트의 출력.

### 보조 자료: check-plan.mjs

`node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`는 이 계획서 형식을 검사합니다. 종료 코드는 인자가 없으면 2(stderr에 사용법), 문제가 있으면 1, 깨끗하면 0입니다. 출력은 stdout에 PR 절마다 요약 한 줄과 `<n> PR sections, <m> problems`, stderr에 문제마다 `file:line: message` 한 줄입니다. 검사 내용은 다음과 같습니다.

- **문체(코드가 아닌 줄).** 긴 줄표(en dash, em dash), 곡선 따옴표, 문장 중간 콜론(`: ` 뒤에 공백이 아닌 글자)을 보고합니다. 인라인 코드, 이미지, 링크 대상은 먼저 벗깁니다.
- **최상위 구조.** H1 제목이 있어야 하고, H1과 첫 `## How to read this` 사이에 비어 있지 않은 줄 10개 미만, `## How to read this`(필수 문구 포함: "One box is one unit of work", "names the evidence", "Check a box only when its evidence exists", `playbooks/`, 그리고 검증 규칙 문장), `## Program checklist`, PR 절 하나 이상, `## Close the program`.
- **Program checklist.** `###` 제목이 `Arm the program`, `Spawn owners`, `PR mechanics`, `Verdict and merge`, `Boot recipe`로 이 순서로 시작해야 하고, `git show origin/main:`, `/loop 1h`, `status message`를 포함해야 합니다.
- **PR 절.** 위의 아홉 개 굵은 하위 블록이 정확히 이 순서로 있어야 합니다. `Depends on.`은 무언가를 밝혀야 하고, `Files.`, `Build.`, `You see.`, `Verify, unit.`, `Merge.`에는 체크박스가 하나 이상 있어야 합니다. 세 `Verify` 블록은 검증 규칙 문장으로 시작해야 합니다. `Verify, live.`는 "Ten lanes on `<model>` at the PR head"와 채워진 모델, 1에서 10까지 번호가 붙은 레인(`Lane N. `)이 필요하고 레인마다 ``Save `<file>` ``과 `Pass when`이 있어야 합니다. `Verify, perf.`의 상자는 정확히 `Metric.`, `Probe.`, `Baseline.`, `Rule.` 순서입니다. `Review gate.`는 `None.`으로 시작하고 상자가 없거나, 아니면 상자가 하나 이상 있고 `screenshot`, `video`, `operator`를 담아야 합니다.
- **Close 뒤.** `## Appendix...` 절만 허용되고 그중 하나에 "Prototype evidence"가 있어야 합니다.

### 함정과 주의점

- 계획서만 쓰고 구현하지 않습니다. 실행은 운영자의 명시적 승인 뒤입니다.
- 테스트만으로 검증되었다고 하지 않습니다. 단위, 라이브, 성능 상자가 모두 필요합니다.
- 서로 다른 시나리오 사이의 성능 비율을 주장하지 않습니다.
- `check-plan.mjs`가 출력하는 모든 줄을 고칩니다.

### 흐름도

```flow Multi-phase or multi-PR plan 플레이북의 흐름
start 단계나 PR 여럿에 걸친 일
step 1. 계획이 필요한가
  stop 뻔한 변경 | 그렇게 말하고 멈춤
step 2. 열린 질문은 프로토타입으로
  alt 제품이나 취향의 결정 | 옵션과 함께 운영자에게 물음
step 3. 서브에이전트로 탐색
step 4. 골격을 계획 파일에 채움
step 5. technical-writing 후 unslop
step 6. check-plan.mjs 실행
step 7. 계획 경로와 스크립트 출력을 넘기고 멈춤
end 운영자의 명시적인 go 이후에 실행이 시작됨
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 건너뛴다는 말 하나, 또는 계획 작성 시작 |
| 2 | 부록 A용 브랜치, SHA, 스크린숏 |
| 3 | 서브에이전트마다 파일 포인터, 관례, 테스트 명령, 진입점 |
| 4 | 계획 파일. 프로그램 체크리스트와 PR마다 하나의 절, 닫는 절, 부록 A~D(프로토타입 증거, 기각한 대안, 위험, 링크와 읽을거리) |
| 5 | `/technical-writing`과 `/unslop`을 거친 본문 |
| 6 | `check-plan.mjs`의 출력(PR 절마다 상자 수 요약과 문제 개수) |
| 7 | 계획 경로와 스크립트 출력 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "인증을 세션 쿠키에서 토큰으로 옮기는 일을 PR 다섯 개로 쪼개서 계획서로 만들어 줘. 구현은 하지 마."
>
> 1. 한두 파일짜리가 아니므로 계획을 씁니다.
> 2. "토큰 갱신을 클라이언트에서 할 것인가"는 관찰로 풀리는 질문이므로 Prototype 플레이북으로 확인하고, 그 브랜치와 SHA를 부록 A에 남깁니다.
> 3. 서브에이전트를 시켜 인증 관련 파일 포인터, 테스트 명령, 진입점을 모읍니다.
> 4. 골격을 채워 PR마다 절 하나(의존, 파일, 빌드, 관찰 결과, 단위/라이브/성능 검증, 리뷰 관문, 병합)를 씁니다. 상호작용을 바꾸는 PR은 리뷰 관문이 걸립니다. 실행 플레이북은 순서가 있는 작업이므로 `autopilot-stack`을 지목합니다.
> 5. `/technical-writing`, `/unslop`을 적용합니다.
> 6. `check-plan.mjs`가 출력한 줄을 모두 고칩니다.
> 7. 계획 경로와 출력을 넘기고 멈춥니다. 실행은 사용자의 명시적인 go 뒤에 시작됩니다.

### 실패, 중단, 모호할 때

- **계획이 필요 없을 때.** 파일 한두 개에 접근이 뻔하면 계획을 건너뛰고 그렇게 말한 뒤 멈춥니다.
- **열린 질문이 있을 때.** 프로토타입으로 풀 수 있는 것은 먼저 프로토타입으로 풉니다. 어떤 실행으로도 풀 수 없는 제품이나 취향의 결정에만 운영자에게 묻고, 옵션을 함께 줍니다(`never-block-on-the-human`).
- **검사 스크립트가 문제를 출력할 때.** 출력된 모든 줄을 고칩니다. 종료 코드가 0이 아니면 문제가 남은 것입니다.
- **검증 규칙.** 테스트만으로는 검증이 아닙니다. PR은 단위, 라이브, 성능 상자가 모두 체크되어야 검증된 것입니다. 라이브 상자는 필수입니다. 트렁크에 기능이 없으면 그 사실을 기록하고, 차이가 더하는 동작과 사용자가 기다리는 최종 상태를 게이트합니다.
- **표면에 control 스킬이 없을 때.** 부록 C의 위험으로 올리되, 라이브 상자는 각 레인이 어떻게 구동하는지를 여전히 적습니다.
- **실행.** 운영자의 명시적인 go가 있어야 시작합니다. 이 플레이북은 구현하지 않습니다.

## Orchestrate {#playbook-orchestrate}

원문: {{src:skills/poteto-mode/playbooks/orchestrate.md}} {{src:skills/poteto-mode/scripts/orch/orch.ts}} {{src:skills/poteto-mode/scripts/orch/store.ts}} {{src:docs/guide/07-overnight.md}}

> 프로그램 전체를 조정자 채팅 하나에 맡깁니다. 브리프를 쓰고, 대기열을 비우고, 프런티어를 초록으로 유지하고, 결정합니다. 코드는 절대 쓰지 않습니다.

### 언제 쓰는가

며칠에 걸친 프로젝트, 많은 스택 PR, 수십에서 수백의 서브에이전트, 사람은 5분마다가 아니라 하루에 두 번 확인하는 상시 조정자 채팅입니다("run this whole project", "own this migration until it lands"). 하나의 작업을 술어까지 몰고 가는 것은 Autonomous run이고, 맞춤 워크플로가 필요한 야심찬 한 번의 실행은 `figure-it-out`입니다. 작업이 어떤 단일 에이전트의 수명보다 길 때 여기로 갑니다. 세션 예산 안에서 에이전트 하나가 끝낼 수 있는 일은 프로그램이 아닙니다.

의식은 프로그램의 규모에 비례해야 합니다. 값싸고 거의 같은 단위들에서는 각 절의 지시대로 의식을 접습니다. 나머지를 떠받치는 규칙이 셋 있습니다. 완료는 인터럽트가 아니라 대기열 이벤트다. 모든 생성과 재개는 상시 지시를 글자 그대로 싣는다. 브리프가 산출물이다(모호한 브리프는 조용히 실패한다. 작업자가 질문할 수 없기 때문).

### 동작 방식

#### 역할과 배치

- **조정자(이 채팅).** 로컬입니다. 틀을 짓고, 브리프를 쓰고, 인박스를 비우고, 사람에게 보고하고, 판단을 내립니다. 코드를 쓰거나 고치지 않습니다. 충돌이 있는 병합, 리스택, 코드 변경은 항상 작업입니다. 로컬 git이 싼 저장소에서 검증된 단위를 기계적으로 랜딩하는 것(작업자 커밋의 fast-forward나 깨끗한 cherry-pick 뒤 푸시)은 조정자가 직접 해도 되는 장부 작업입니다. 루프는 처음부터 끝까지 에이전트적입니다. 에이전트는 Task 도구로만 띄우고 재개하고 비웁니다. 상태 읽기와 쓰기는 비우는 지점에서 `scripts/orch/orch.ts`를 거칩니다(명령 하나 들어가고 한 줄 나옴). CLI는 아무것도 띄우거나 기다리거나 깨우지 않습니다.
- **하위 조정자.** 항상 로컬이고 내구성이 있으며 트랙당 하나이고, 프로그램이 조정자 하나의 비우기로 관리할 수 있는 범위를 넘을 때만 둡니다. 조정자가 직접 비울 수 있는 트랙에는 중간 계층이 필요 없습니다. 중첩된 계층마다 오리엔테이션 서문을 다시 치르고, 막는 하위 조정자는 자식을 숨긴 채 부모가 논다. 자기 트랙의 단위와 보드를 소유하고, 작업자의 브리프를 쓰고, 자기 작업자와 검증자를 띄웁니다(깊이 3까지 중첩 가능). 웨이브 경계에서 집계를 올립니다. 자식의 원시 보고를 그대로 전달하지 않습니다. 진행 중인 자식은 한 번의 비우기가 처리할 수 있는 정도(약 열 개)로 제한하고, 롤링 윈도로 운영합니다. 가장 느린 자식이 배치마다 비용을 치르는 막는 배치는 쓰지 않습니다.
- **작업자와 검증자.** 작업이 이 머신을 필요로 하지 않는 한 항상 `environment: "cloud"`입니다. 이 머신이 필요한 경우는 `control-ui`나 `control-cli` 런타임 검증(cursor-team-kit), `agent-transcripts/` 아래 로컬 대화 기록 읽기, 시뮬레이터와 로컬 IDE 상태, 여기에만 있는 인증입니다. 클라우드 에이전트는 로컬 저장소를 읽을 수 없으므로 브리프에 필요한 것을 인라인으로 넣거나 저장소 경로를 가리킵니다. 작업자를 적고 넓게 씁니다. 워크트리나 브랜치당 작성자는 하나(`principle-separate-before-serializing-shared-state`). 단위의 검증자는 작업자와 다른 모델 계열에서 돌립니다.

깊이는 조정자, 트랙, 작업자에서 멈춥니다. 트랙 분해는 프로젝트마다 작성합니다(빌드, 랜딩, 검증은 흔한 구분이지 필수 모양이 아님). 하드코딩된 swarm 트리는 시도했다가 너무 경직되어 보류되었습니다.

#### 저장소 배치

현재 에이전트 저장소(경로는 시스템 프롬프트에 있음)에 `orchestrate/<project-slug>/`를 만듭니다. 모든 파일은 작성자가 정확히 하나입니다. 소유자는 사실을 게시하고 독자가 읽을 때 집계합니다. 장부 작업에는 `bun scripts/orch/orch.ts`(플레이북에서는 `orch`)를 쓰되, 정식 형식인 평범한 TSV와 JSON은 CLI 없이도 읽을 수 있습니다.

| 파일 | 내용 |
| --- | --- |
| `preferences.md` | 상시 지시 목록. 번호가 붙은 줄이고 한 줄에 제약 하나(모델 정책, 스택 모양과 개수, 검증 기준(bar), 금지 경로, 에스컬레이션 정책). 모든 생성과 재개에 글자 그대로 붙여 넣습니다. 재개를 거치면 지시가 희미해지고 잃어버린 지시마다 사람의 한 턴이 듭니다. 지시를 되풀이하고 있는 자신을 발견하면 행동 전에 그 줄을 추가합니다(`principle-encode-lessons-in-structure`) |
| `overview.md` | 영속적인 PR과 이슈 DB. 덧붙이기만 하고 이벤트마다 통째로 다시 쓰지 않습니다 |
| `units.tsv` | 단위당 한 행: id, 트랙, 상태, 브랜치, PR, 헤드 SHA, 브리프 경로. 행은 제자리에서 갱신 |
| `frontier.json` | 계산된 병합 프런티어 |
| `ledger.tsv` | 검증 장부 |
| `inbox/` | 완료 포인터. `gates.md`는 사람의 관문을 보관(질문, 선택지, 답이 없을 때의 기본값) |
| `decisions.tsv` | `show-me-your-work` 스킬의 기록 |
| `status.md` | 비울 때마다 `units.tsv`와 `ledger.tsv`에서 도출하며 손으로 유지하지 않습니다 |

#### 브리프

에이전트에게 주는 프롬프트가 조정자의 유일한 산출물이고, 엉성한 브리프는 트리 전체에서 슬롭으로 복리가 붙습니다. 모든 생성이 아래를 전부 싣습니다. 채울 수 없는 필드는 아직 범위를 정하지 못한 단위입니다.

| 필드 | 내용 |
| --- | --- |
| GOAL | 결과 한 문장. 채팅에 접근할 수 없는 낯선 사람이 실행할 수 있어야 함 |
| SCOPE | 이 단위가 쓸 수 있는 경로, 쓸 수 없는 경로, 전용 워크트리나 브랜치 |
| CONTEXT | 파일과 PR의 포인터. 이 단위가 의존하는 상위 보고서는 전문을 붙여 넣음(작업자는 형제를 볼 수 없으므로) |
| ACCEPTANCE | 검사 가능한 기준(criteria), 한 줄에 하나 |
| VERIFY | 정확한 명령이나 control 스킬 경로와 알려진 함정 |
| TIMEBOX | 실행 시간의 대략적 상한. 만료되면 계속 돌지 말고 부분 결과를 돌려주고 멈춤 |
| FORBIDDEN | `gt` 금지, 리베이스 금지, 강제 푸시 금지, 범위 밖 수정 금지, 단위별 금지 |
| REPORT | 상태, 브랜치, 헤드 SHA, PR, 판정, 실제로 돌린 것, 이탈, 제안하는 후속 |
| STANDING | `preferences.md`를 글자 그대로 붙여 넣음 |

브리프의 크기는 단위에 맞춥니다. 명령 하나짜리 단위는 목표, 범위, 검증 명령, 보고 형식을 이름 붙이는 한 문단으로 접습니다. 두 줄짜리 수정 주위의 4KB 뼈대(scaffold)는 수정보다 쓰고 따르는 비용이 큽니다. 로컬 생성은 상시 지시 파일을 저장소 경로로 참조해도 되고, 글자 그대로 붙여 넣는 것은 클라우드 생성과 모든 재개에 씁니다. 하위 조정자의 브리프는 트랙 경계와 단위 목록, 생성 예산(클라우드가 기본이고 로컬 예외 목록), 비우기 프로토콜, 집계 형식(자식마다 이름, 상태, PR, 헤드 SHA, 판정, 한 줄, 그리고 트랙 상태와 프런티어 변화)을 더합니다.

의존성은 순서만이 아니라 맥락 릴레이입니다. 선언되지 않은 상위 맥락은 작업자가 추측하게 만듭니다. 빠진 필드는 생성을 거부하는 조건입니다. 웨이브마다 하위 조정자당 표본 작업자 브리프 하나를 감사하되, 표본으로 삼은 웨이브와 동시에 진행하고 그 앞의 관문으로 삼지 않습니다. 실패한 브리프는 그 트랙을 멈추고 작업자뿐 아니라 하위 조정자의 지시를 고칩니다. 브리프 품질은 실행 후반에 떨어지기 때문입니다. 브리프를 재개로 이어 붙이지 않습니다. 통합한 범위로 새로 생성합니다.

#### 단계

1. **틀 짓기.** 완료 조건을 셀 수 있는 것으로 밝힙니다("126개 단위가 모두 병합되고 각각 장부에서 `unit-test-verified` 이상"). 범위를 수치로 씁니다. 단위 수, 대략의 노력, 예상 스택, 벽시계 예산입니다. 에이전트 하나가 그 예산 안에 끝낼 수 있으면 여기서 멈추고 Autonomous run을 돌립니다. 접는다는 것은 다른 문서의 존재에 의존하지 않습니다. 이 세션에서 직접 작업하고, 도움이 되는 곳에 일반 작업자를 쓰고, 검증은 인라인으로, 진행하며 랜딩하고, 아래의 저장소, 등록부, 파일럿 장치는 쓰지 않는다는 뜻입니다. 랜딩을 예산에 대해 계획합니다. 대략 70% 시점에는 생성을 멈추고 검증된 것을 랜딩합니다. 트랙에 프로젝트별로 이름을 붙입니다. 논쟁적인 분해나 되돌릴 수 없는 문은 파일럿 전에 `arena` 스킬을 거칩니다. 틀을 한 번 제시합니다. 되돌릴 수 있는 준비는 기다리지 않고 진행합니다.
2. **런타임 설치.** `orch init`을 돌립니다. `show-me-your-work` 스킬로 기록을 열고, 생성 전에 상시 지시를 쓰고, `orch frontier set --repo <repo-dir>`로 기존 PR에서 `frontier.json`을 시드합니다.
3. **파일럿.** 단위 하나를 전체 경로(브리프, 작업자, 검증, 스택 진입, 장부 행, 병합)로 밀어 넣습니다. 파일럿은 브리프 템플릿, 검증 레시피, 단위 크기를 에이전트 쉰 개가 아니라 하나로 반증하는 비용으로 시험하려고 있습니다. 어떤 팬아웃보다 먼저 파일럿 증거로 계약을 고칩니다. 파일럿의 규모는 단위에 맞춥니다. 값싸고 거의 같은 단위로 이루어진 프로그램에서는 첫 단위가 파일럿이며, 검증 명령을 인라인으로 두고 정상 단위로 돌리고, 그것이 랜딩되는 순간 팬아웃이 시작됩니다. 전용 파일럿 파이프라인(별도 검증자 에이전트, 감사 관문)은 비싸거나 새로운 단위 모양에 쓰고 복제 단위에는 쓰지 않습니다.
4. **확장.** 진행 중 상한까지 작업자의 롤링 윈도를 띄우고 자식이 끝날 때마다 채웁니다. 막는 배치는 배치마다 가장 느린 자식의 비용을 냅니다. 역할 절의 한 번의 비우기 문턱을 넘을 때만 트랙 하위 조정자를 띄웁니다. 비울 때마다 준비된 작업을 다시 계산합니다. 상위 보고서를 하위 브리프에 릴레이합니다. 형제 사이의 소통은 위로만 합니다. 표본 브리프 감사는 표본으로 삼은 웨이브와 나란히 돌고, 실패하면 현재가 아니라 다음 채우기를 멈춥니다.
5. **비우기.** 아래의 대기열 규율을 모든 비우기 지점에서 따릅니다.
6. **랜딩.** 랜딩은 마지막 단계가 아니라 지속적입니다. 통합은 첫 검증된 단위와 함께 시작하고 나머지 웨이브와 나란히 돕니다. 무거운 저장소에서는 stacker가 첫 웨이브부터 상주 역할로 단위가 검증되는 대로 통합합니다. 로컬 git이 싼 저장소에서는 조정자가 역할 절에 따라 직접 검증된 단위를 랜딩합니다. 상위 스택 작업 전에 프런티어를 초록으로 유지합니다. 스택 안전 규칙(Stack safety)이 지배합니다. `frontier.json`은 병합이나 보고된 새 헤드 SHA에서만 앞으로 갑니다.
7. **마무리.** 마지막 인박스를 비우고, 띄운 모든 에이전트를 종결 행(done, abandoned, zombie-reconciled)으로 정리하고, 실제 산출물에서 술어를 확인하고, 랜딩된 모든 PR에 현재 헤드 SHA의 판정이 있는지 확인하고, 교차 모델 리뷰를 포함해 `show-me-your-work`에 따라 기록을 감사하고, 반복된 교정을 `preferences.md`나 브리프 템플릿에 인코딩합니다. 저장소는 그대로 둡니다. 그것이 포스트모템입니다.

#### 대기열과 비우기

- 완료 알림이 오면 `orch inbox push <agent> <unit> <status> [--report PATH]`를 실행하고 하던 일로 돌아갑니다. 인라인으로 깊이 리뷰하지 않습니다. 리뷰가 필요한 완료는 검증자 단위가 됩니다. 비우기 안에서 diff를 리뷰하지 않습니다.
- 네 지점에서 배치로 비웁니다. 임계 구역의 끝, 트랙 집계, 프런티어 감시자의 깨움(루프 스킬로 무장하고 긴 하트비트를 대비책으로), 사람에게 보고하기 전입니다. 각 배치는 `orch inbox drain`으로 시작합니다. 비우는 동안 도착한 것은 다음 비우기를 기다립니다.
- 먼저 끝내는 임계 구역은 브리프 작성, 스택 조작, 충돌 결정, 관문 쓰기, 장부나 프런티어 갱신입니다.
- 비울 때마다 모든 포인터를 분류하고(landed, needs-verify, failed, zombie, noise), 결과 행을 `orch unit add`, `orch unit set`, `orch ledger record`로 쓰고, `orch status`를 돌리고, 다음 웨이브를 한 메시지로 띄웁니다.
- 띄운 자식은 각 트랙의 집계에서 모두 정산합니다. 도착했거나, 다시 띄웠거나, 범위가 명시적으로 흡수되었거나 셋 중 하나입니다. 사라진 자식의 일을 조용히 다시 하면 낭비된 지출과 그 결과가 메우려던 커버리지 빈틈이 함께 숨습니다.
- 비우는 턴은 `orch status`의 세 줄로 끝납니다. 상태별 개수, 변경, 열린 관문입니다. 세부는 `status.md`에 있습니다. 전체 응답 계약은 체크포인트와 마무리에서 적용됩니다.

#### 스택 안전

- 프런티어는 서사가 아니라 계산된 객체입니다. 병합과 스택 변경 뒤마다 `gt`에서 `frontier.json`을 다시 계산합니다. GitHub 베이스 참조는 리스택 도중 표류하지만 gt 추적은 권위가 있기 때문입니다. 순서 있는 PR 목록, 브랜치 이름, 헤드 SHA, 세대 번호, 가장 낮은 미병합 PR을 담습니다. gt가 스택을 아는 곳(보통 stacker의 클론)에서 해결합니다. gt 메타데이터가 제출을 본 적 없는 체크아웃은 PR이 없다고 보고하고, 명령이 추측하지 않고 오류를 냅니다.
- 스택당 정확히 하나의 stacker만 `gt`를 돌리고 스택 안에서 직렬화됩니다. 소유자를 상시 지시에 기록합니다. 리스택은 클라우드에서 돕니다. 이 규모의 로컬 리스택은 노트북을 죽입니다.
- 작업자는 리베이스하지 않고 `gt`도 돌리지 않습니다. babysitter는 `playbooks/babysit.md`를 따르고, 스택당 하나이며, 불변의 프런티어 세대 하나로 범위가 정해집니다. 충돌은 리스택하지 않고 stacker에게 보고합니다.
- PR 닫기와 재지정은 stacker를 통해서만 합니다. 베이스 PR을 닫으면 그 위의 모든 사슬이 고아가 됩니다. 병합과 스택 수술은 다른 단위와 같이 브리프가 있는 단위입니다.
- 회고 감시자 하나가 병합된 PR의 되돌림, 병합 후 CI 깨짐, 고아 후속을 따릅니다.

#### 검증

검증은 단위에 맞춰 규모를 정합니다. VERIFY가 값싼 명령 하나이면 작업자가 돌려 출력을 보고하고 조정자가 영수증을 표본 점검합니다. 전용 검증자 에이전트(작업자와 다른 모델 계열)는 검증이 비싸거나 판단이 필요하거나 파급이 큰 단위에 씁니다. 명령 하나를 다시 돌리는 것이 산출물 전부인 검증자 에이전트는 검증이 아니라 의식입니다.

`orch ledger record`로 장부 행을 씁니다. 현재 PR과 헤드 SHA는 `orch ledger check`로 확인합니다. `ledger.tsv`는 판정마다 한 행이고 PR 번호와 헤드 SHA를 키로 합니다. 판정은 `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, `verifier-failed` 중 하나입니다. CI 초록은 판정의 입력이지 판정이 아닙니다. 행동 작업에는 `type-check-only`보다 나은 것이 필요합니다. `verifier-blocked`는 통과가 아닙니다. 환경이 복구되면 다시 띄웁니다. `verifier-failed`에는 재검증이 아니라 수정 단위가 갑니다. 작업자가 자기 보고를 해도 되지만 검증자가 같은 키에서 이를 덮어씁니다. 새 헤드 SHA는 행을 무효로 하므로 리스택 뒤에 다시 검증합니다. 장부가 "검증되었는가"에 답합니다. 기억도 대화 기록도 아닙니다.

단위는 산출물이 랜딩되는 순간 외부화되어야 끝난 것이고 실행 끝에 몰아서 하지 않습니다. 작업자는 브랜치를 푸시하고, 검증자는 장부 행을 쓰고, 영수증은 저장소에 놓입니다. VM 하나에만 있는 작업은 그 VM이 죽을 때 한 번도 끝난 적이 없는 것입니다.

#### 생존 확인과 실패

- 에이전트를 확인하려고 재개하지 않습니다. 재개는 놀고 있는 에이전트를 다시 시작합니다. 읽기 전용으로 조사합니다. 장부, `units.tsv`, `gh`, 푸시된 브랜치, Cursor 대시보드의 클라우드 에이전트 상태. 대화 기록의 mtime은 생존 신호가 아닙니다.
- 조용한 죽음은 인박스에 합성 포스트모템 행(단위, 실패 모드, 마지막 증거, 선택지)을 얻습니다. 증거가 도착하는 대로 재계획합니다. 완전한 정지를 기다리지 않습니다.
- 모드별 재시도. 상한 도달이나 oom은 더 작은 범위로 재생성, 네트워크 끊김은 그대로 재시도, 도구 오류는 다른 모델로 재시도, 알 수 없음은 한 번 재시도. 재시도 두 번 뒤에는 단위를 포기하고 그 둘레로 재계획합니다.
- 몇 시간 늦게 돌아온 좀비는 무엇이든 받아들이기 전에 현재 프런티어와 장부에 대해 정산합니다. 고유한 발견은 새 단위로 건지고, 맹목적으로 병합하지 않습니다.
- 계속 생성하면 트리 전체에서 쓰레기가 나올 때(나쁜 상위 출력, 깨진 수용 기준, 죽은 인프라) 상시 지시의 맨 위에 정지 줄을 쓰고, 진행 중 작업이 끝나게 두고, 원인을 고친 뒤 지웁니다.
- 자신의 인프라 재시도도 자식의 것과 같게 제한합니다. 도구 중단이 몇 번 연속되면 재시도를 멈추고, 영속 상태(무엇이 끝났고 어디에 있고 재개할 정확한 명령)에 종결 인계를 쓰고 실행을 끝냅니다.
- Cursor를 재시작한 뒤에는 로컬 에이전트는 죽었지만 클라우드 작업은 아닙니다. 상시 지시와 `units.tsv`를 다시 읽고, 프런티어를 다시 계산하고, 에이전트 id가 아니라 PR과 브랜치로 클라우드 작업에 다시 붙고, 저장된 브리프와 현재 상태로 트랙마다 하위 조정자 하나를 다시 띄우고, 비우고, 재개합니다. 죽은 세션의 저장소 락은 다음 쓰기에서 스스로 풀립니다. `orch`는 보유 pid가 사라진 락을 대체합니다.

#### 에스컬레이션

사람에게 가는 것은 항목별이 아니라 상태 페이지로 묶어서, 되돌릴 수 없는 행동(공유 브랜치 강제 푸시, 배포, 삭제, 남의 PR 닫기), 어떤 실험으로도 풀 수 없는 진짜 제품이나 취향 판단, 관찰된 현실과 모순되는 상시 지시, 재계획을 견딘 프로그램 수준의 막다른 길입니다. 물어보기 전에 각각을 `gates.md` 항목으로 보관하고 그 둘레로 작업을 돌립니다. 사람에게 가지 않는 것은 프런티어 재촉, 리스택 절차, 재시도, CI flake 분류, 리뷰 스레드 분류, 서식 수정, 브리프가 이미 금지한 범위(거부하고 계속), "계속 할까요"입니다. 애매하면 행동하고 기록합니다. 실행 중 발견은 프런티어를 막는 것만 고칩니다. 나머지는 모두 후속으로 보관합니다. 이 팬아웃에서는 작은 범위 누수가 아무도 요청하지 않은 PR로 곱해집니다.

### 응답

체크포인트와 마무리에서 술어와 `units.tsv`, `ledger.tsv`의 그에 대한 수, 트랙과 각각 랜딩한 것, 프런티어(PR 목록과 SHA), 판정 요약, 포기한 것과 이유, 사람을 기다리는 관문(유일한 질문), 저장소 경로와 기록 경로. 서사가 아니라 표의 숫자로. PR 링크를 포함합니다.

### 보조 자료: orch CLI

`orch`는 이 플레이북을 위한 평범한 파일 장부 CLI입니다(`bun scripts/orch/orch.ts`). 아무것도 띄우거나 깨우지 않습니다. 저장소 디렉터리는 `--store <dir>` 또는 환경변수 `ORCH_STORE`로 정하고, `--json`은 완전한 행을 JSON으로 내며, `--force`는 기존 저장소 락을 빼앗습니다.

| 명령 | 하는 일 |
| --- | --- |
| `init` | 저장소를 만듭니다. 멱등 |
| `unit add <id> --track <track> [--brief <path>]`, `unit set <id> --state <state> [--branch] [--pr] [--sha]`, `unit get`, `unit list`, `unit counts` | `units.tsv`(헤더 `id, track, state, branch, pr, sha, brief`). `unit add`는 상태를 `pending`으로 시작하고 중복 id는 오류. 상태는 검증되지 않는 자유 텍스트이고 플레이북의 이름은 관례일 뿐입니다 |
| `ledger record <pr> <sha> <verdict> --evidence <path> [--verifier <name>]`, `ledger check <pr> <sha>`, `ledger summary` | `ledger.tsv`(키는 PR과 SHA, 다시 기록하면 행을 교체). 유효한 판정은 `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, `verifier-failed`. `ledger check`는 일치하는 행이 없으면 `NOT-VERIFIED`를 출력하고 종료 코드 2 |
| `inbox push <agent> <unit> <status> [--report <path>]`, `inbox drain [--peek]`, `inbox count` | `inbox/`에 포인터마다 파일 하나. `drain`은 이름 순으로 읽고 디렉터리를 비웁니다 |
| `gate park <id> --question --options --default`, `gate list`, `gate resolve <id> --answer` | `gates.md` |
| `frontier set [--repo <dir> | ORCH_REPO] [--prs <n,...>]`, `frontier show` | `frontier.json`. `gt`(Graphite)를 호출해 스택 순서와 각 브랜치의 PR을 알아냅니다. `--prs`는 예상 PR 순서를 고정하고 맞지 않으면 쓰기 전에 중단합니다. 쓸 때마다 세대가 1 늘고 `lowestUnmerged`는 첫 `OPEN` PR입니다 |
| `status` | `status.md`를 다시 그립니다. Units, Verification ledger, Frontier, Gates 표. 세 줄(`counts:`, `changed:`, `gates open:`)을 출력 |
| `standing show`, `standing add <line>` | `preferences.md`(번호가 1부터 연속이어야 하고 아니면 읽기 실패) |

쓰기 명령은 `.orch.lock`(PID를 담은 락 파일)을 잡습니다. 보유 PID가 죽었으면 조용히 대체하고(`replacing stale store lock`), 살아 있으면 `store lock held by pid N`으로 실패하며, `--force`면 빼앗습니다. 모든 파일 쓰기는 임시 파일에 쓴 뒤 rename하고, TSV 셀의 탭과 줄바꿈은 공백으로 바꾸며 `=`, `+`, `-`, `@`로 시작하는 셀은 `'`를 앞에 붙여 스프레드시트 수식 주입을 막습니다. `unit list`, `gate list`, `standing show`의 목록 출력은 4행으로 제한되고 이어서 `... N more; use --json`이 붙습니다(`inbox drain`은 제한 없이 전부 출력). 종료 코드는 0(성공), 1(모든 오류), 2(없음: 알 수 없는 단위나 관문, 또는 일치하는 행이 없는 `ledger check`)입니다. `overview.md`와 `decisions.tsv`는 플레이북이 나열하지만 `orch`가 만들거나 관리하지 않습니다.

### 함정과 주의점

- 에이전트 하나가 예산 안에 끝낼 수 있는 일은 프로그램이 아닙니다. Autonomous run으로 갑니다.
- 조정자는 코드를 쓰지 않습니다. 충돌 병합, 리스택, 코드 변경은 작업으로 맡깁니다.
- 브리프를 재개로 이어 붙이지 않습니다. 통합한 범위로 새로 생성합니다.
- 에이전트가 살아 있는지 확인하려고 재개하지 않습니다.
- 프런티어를 막는 것만 고칩니다. 범위 누수는 아무도 요청하지 않은 PR로 곱해집니다.
- 안내서의 표현으로, 이것은 의도적으로 무거운 장치입니다. 한 에이전트가 세션 안에서 끝낼 수 있는 일이면 플레이북 자체가 밤새 맡기는 계약으로 돌려보냅니다.

```flow Orchestrate 플레이북의 흐름
start 여러 날, 많은 PR, 서브에이전트 수십에서 수백 개
step 1. 틀 잡기
  stop 한 에이전트가 예산 안에 끝낼 수 있음 | Autonomous run으로
step 2. 런타임 설치
step 3. 파일럿
step 4. 확장
step 5. 드레인
step 6. 착륙
  back 6 | 다음 웨이브
step 7. 닫기
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 세어지는 완료 술어, 단위 수와 예산, 트랙 이름 |
| 2 | `orchestrate/<project-slug>/` 저장소(`orch init`이 `units.tsv`, `ledger.tsv`, `inbox/`, `gates.md`, `preferences.md`, `frontier.json`을 만듭니다), 열어 둔 결정 기록(`decisions.tsv`). `overview.md`는 덧붙여 가고 `status.md`는 `orch status`가 도출합니다 |
| 3 | 파일럿이 확정한 브리프 템플릿, 검증 레시피, 단위 크기 |
| 4 | 브리프를 갖춘 워커와 검증자 |
| 5 | 분류된 포인터(landed, needs-verify, failed, zombie, noise)와 `orch` 명령이 쓴 행, `orch status`의 세 줄 |
| 6 | 병합된 단위와 갱신된 `frontier.json`, 검증 장부의 행(PR 번호와 head SHA 키) |
| 7 | 종료 행으로 정산된 모든 에이전트, 유지된 저장소(사후 분석용) |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "조직 전체의 API 호출 120곳을 새 클라이언트로 옮기는 프로젝트를 맡아. 내가 하루 두 번 확인할게."
>
> 1. 완료 술어는 "120개 단위가 병합되고 각각 `unit-test-verified` 이상으로 장부에 기록"입니다. 한 에이전트가 예산 안에 끝낼 수 없으니 이 플레이북이 맞습니다.
> 2. `orch init`, 상시 지시(모델 정책, 스택 모양, 금지 경로)를 쓰고 기록을 엽니다.
> 3. 단위 하나를 브리프부터 병합까지 끝까지 통과시켜 브리프 템플릿과 검증 명령이 맞는지 봅니다. 비슷하고 값싼 단위이므로 첫 단위가 파일럿을 겸합니다.
> 4. 진행 창으로 워커를 띄우고 끝나는 대로 채웁니다. 완료 알림이 오면 `orch inbox push`만 하고 하던 일로 돌아갑니다.
> 5. 드레인 지점마다 `orch inbox drain`으로 포인터를 분류하고 행을 갱신한 뒤 다음 웨이브를 한 메시지로 띄웁니다.
> 6. 검증된 단위는 프런티어를 초록으로 유지하며 착륙시킵니다.
> 7. 술어를 실제 산출물로 확인하고 모든 에이전트를 종료 행으로 정산합니다.

### 실패, 중단, 모호할 때

- **에이전트가 조용히 죽을 때.** 받은 편지함에 합성 사후 분석 행(단위, 실패 모드, 마지막 증거, 옵션)을 씁니다. 완전한 정지 상태를 기다리지 않고 증거가 들어오는 대로 다시 계획합니다.
- **재시도.** 상한 초과나 메모리 부족이면 더 작은 범위로 다시 띄웁니다. 네트워크 끊김은 그대로, 도구 오류는 다른 모델로, 알 수 없으면 한 번 재시도합니다. 두 번 재시도해도 안 되면 단위를 버리고 그 주변으로 다시 계획합니다.
- **몇 시간 늦게 돌아온 좀비.** 무엇이든 받아들이기 전에 현재 프런티어와 장부에 대해 조정합니다. 고유한 발견은 새 단위로 건집니다. 맹목적으로 병합하지 않습니다.
- **트리 전체에 쓰레기가 나올 때.** 상시 지시 맨 위에 중지 줄을 쓰고, 진행 중인 일이 끝나게 둔 뒤, 원인을 고치고 줄을 지웁니다.
- **도구가 연달아 중단될 때.** 몇 번 뒤에는 재시도를 멈추고, 끝난 일, 있는 곳, 재개할 정확한 명령을 담은 종료 인수인계를 영속 상태에 쓰고 실행을 끝냅니다.
- **Cursor 재시작 뒤.** 로컬 에이전트는 죽고 클라우드 작업은 살아 있습니다. 상시 지시와 `units.tsv`를 다시 읽고, 프런티어를 다시 계산하고, 에이전트 ID가 아니라 PR과 브랜치로 클라우드 작업에 다시 붙고, 트랙마다 저장된 브리프로 하위 조정자를 다시 띄웁니다.
- **에이전트가 살아 있는지.** 확인하려고 재개하지 않습니다(재개하면 쉬던 에이전트가 다시 시작됩니다). 장부, `units.tsv`, `gh`, 푸시된 브랜치, 대시보드에서 읽기 전용으로 살핍니다. 대본 mtime은 생존 신호가 아닙니다.
- **사람에게 올리는 것.** 되돌릴 수 없는 행동, 실험으로 풀 수 없는 제품이나 취향의 결정, 관측된 현실과 어긋나는 상시 지시, 재계획을 견딘 프로그램 수준의 막다른 길입니다. `gates.md`에 먼저 적고 그 주위로 작업을 돌립니다. 프런티어 밀기, 재스택 절차, 재시도, CI 플레이크, 리뷰 스레드 분류, 서식 수정, "계속해도 되나요"는 올리지 않습니다.
- **브리프에 빈 필드가 있을 때.** 띄우지 않습니다. 필드를 채울 수 없으면 단위의 범위를 아직 정하지 못한 것입니다.

## Autopilot-full {#playbook-autopilot-full}

원문: {{src:skills/poteto-mode/playbooks/autopilot-full.md}} {{src:docs/guide/07-overnight.md}}

> PR마다 소유자 하나가 빌드에서 병합까지 몰고 가고, 루트의 깨끗한 swarm 판정 없이는 아무것도 병합되지 않습니다. 루트는 판정을 소유하고 PR은 소유하지 않습니다.

### 언제 쓰는가

"autopilot this queue", "full autopilot", PR마다 소유자 하나의 프로그램입니다. Orchestrate는 조정자가 검증된 작업을 직접 랜딩하고 작업자는 절대 병합하지 않는 상시 프로그램이고, 여기서는 각 PR의 소유자가 병합까지 전체 수명 주기를 몰고 가며 루트는 검증과 카운터사인과 감사만 합니다. 안내서의 예입니다.

```text
/poteto-mode 이 대기열에 full autopilot 해 줘. 각 항목은 독립적이야. 아침까지 전부 병합해 줘.
```

### 동작 방식

1. **운영자의 항목을 표시하고 "먼저 말하고 기다린다"를 지킵니다.** 운영자가 이름 붙인 항목은 운영자에게 남습니다. 운영자가 검토하고 클릭하며 어떤 소유자도 병합하지 않습니다. 운영자가 프로토콜이나 계획을 진술하라고 하면 진술을 전달하고 멈춥니다. 실행은 운영자의 명시적 승인에서만 시작합니다.
2. **PR마다 전체 수명 주기와 이른 기록을 가진 소유자 하나를 띄웁니다.** 프로그램 전체에서 포지를 한 번 정합니다(`gh` 기본, Origin이 있으면 `origin pr ...`, `gt`는 요구하지 않음). PR마다 Cursor 클라우드 에이전트 하나가 빌드, 첫 푸시, 자기 증명 전에 여는 준비 상태 PR, 실제 산출물에서의 자기 증명(`prove-it-works` 원칙(principle)), `../references/bugbot-triage.md`에 따른 회의적 Bugbot 분류, 슬롭 제거(cursor-team-kit의 `deslop`), `/no-comments`, 현재 트렁크로의 리베이스, 초록까지의 babysit 루프(`playbooks/babysit.md`), 병합 자체를 소유합니다. 약 15분 안에 모든 소유자는 `show-me-your-work`에 따라 `decisions.tsv` 기록을 시작하고, 첫 브랜치 스냅숏을 푸시하고, PR을 준비 상태로(초안 아님) 엽니다. 그 뒤 소유자는 검증 가능한 단위마다 브랜치를 다시 푸시합니다(훅을 켜 두고, WIP 커밋도 됩니다). 자기 증명 전에 PR을 열어 URL, 결정, 체크가 영속적 기록이 되게 합니다. `decisions.tsv`는 커밋하지 않고 보고와 함께 돌려줍니다. 서브에이전트가 시작하자마자 소유자는 그 id, 예상 실행 시간(적어도 그 종류의 과거 최장 실행), 상태를 같은 방식으로 유지하는 `children.tsv`에 더합니다. 소유자는 트렁크가 표류했든 아니든 code-ready 보고와 babysit 전에 첫 리베이스를 합니다. 수정 라운드에서는 그 병합 베이스를 유지합니다. 다시 리베이스하는 것은 병합 준비(5단계), 트렁크와의 `git merge-tree` 충돌, 트렁크 변경에서 온 CI 실패일 때뿐입니다. 출하할 코드가 최종이 되면(슬롭 제거와 `/no-comments` 뒤) code-ready 헤드 SHA를 보고하고, 패치를 바꾸는 이후의 푸시마다 그 SHA도 보고합니다. 그 뒤 자기 증명, CI, babysit이 swarm과 병렬로 돕니다. 자기 증명, CI, babysit이 끝나면 헤드 SHA와 함께 merge-ready를 보고합니다. 라운드를 시작하는 푸시 전에 저장소의 AGENTS.md와 규칙(rule)이 건드린 경로에 대해 이름 붙인 사전 리뷰 검사를 커밋된 헤드에서 돌립니다. 훅 통과는 증명이 아닙니다. 리베이스를 게시할 때는 `ls-remote` 확인 뒤 소유자 자신의 브랜치를 `git push --force-with-lease`로 푸시합니다. 공유 브랜치는 절대 강제 푸시하지 않습니다. 병합은 소유자가 혼자 할 수 없는 유일한 단계이고, 4단계가 그것을 관문으로 삼습니다.
3. **소유자를 진짜 병렬로 돌리고 스택하지 않습니다.** PR이 자체적으로 완결되면 소유자가 많이 동시에 돕니다. 브랜치당 작성자 하나, 겹치지 않는 파일, PR 사이의 표류는 리베이스로 흡수합니다. 정말 겹치는 작업만 직렬화합니다. 자체 완결 PR은 main에서 바로 분기하고, 순서가 있는 작업은 병합 뒤에 분기합니다. 한 가지 예외는 진짜 의존적인 변경을 쪼개야 하는 소유자가 짧은 비공개 베이스 브랜치 스택을 가질 수 있다는 것입니다.
4. **병합 전에 모든 라운드를 swarm으로 검증합니다.** 라운드는 소유자의 code-ready 헤드 SHA와, PR의 패치를 바꾸는 이후의 푸시마다 시작합니다. 그 SHA에서 `swarm` 스킬에 따라 병렬 독립 검증자를 팬아웃하고 하나의 판정으로 집계합니다. 병합에는 merge-ready 헤드와 패치가 일치하는 라운드의 깨끗한 판정이 필요합니다. 판정 전에 merge-ready 보고의 영수증을 감사합니다. 레인은 그 SHA에서 관문 다시 돌리기, 변경이 건드리는 실제 표면에서 핵심 동작을 라이브로 증명하기(맞는 control 스킬, 예를 들어 cursor-team-kit의 `control-cli`나 `control-ui`, 없으면 이름 붙인 드라이버), PR 본문을 못 믿는 태도로 diff 감사하기입니다. 감사는 완전한 브리프를 가진 둘 이상의 리뷰 레인으로 돌립니다. 레인마다 주된 초점 하나(트렁크와의 소비자 동등성, 수명과 경쟁, 데이터와 설정 안전성 등)를 줍니다. **Regression lane against trunk.** 같은 핵심 시나리오를 현재 트렁크에서 돌립니다. 트렁크에 기능이 없으면 그 사실을 기록하고 트렁크가 만들 수 있는 척하지 않고 diff가 더한 동작과 사용자가 기다리는 최종 상태를 관문으로 삼습니다. 라이브 레인은 바닥이고 그것이 없는 판정은 깨끗하지 않습니다. 루트의 깨끗한 판정 없이는 병합하지 않습니다. 레인이 돌아오면 PR에 대해 증명된 모든 발견을 한 번의 fix-forward로 소유자에게 보냅니다. 레인이 메모로 남긴 결함도 발견입니다. 동작 발견마다 같은 결함이 있는 모든 자리를 덮는 red 테스트를 요구합니다. 테스트가 결함을 보일 수 없는 곳에는 재현 영수증을 요구합니다. 그 결함을 다음 라운드의 리뷰 브리프에 더합니다. 새 헤드는 새 swarm과 새 판정을 받되, `playbooks/shipping.md`의 patch-id 규칙 아래 유효한 레인 결과는 예외입니다.
5. **깨끗한 판정에서 소유자가 병합하고, 새 소유자가 다음 항목을 잡습니다.** 소유자는 트렁크에 갓 리베이스된 헤드에서만 병합합니다. 병합 준비는 라운드의 레인이 시작되기 전에 오지 않고, 병합 직전 현재 트렁크로의 리베이스로 끝납니다. 병합 준비 리베이스 뒤에 새 헤드 SHA를 보고합니다. 병합 전에 그 헤드에서 CI가 통과해야 하고, patch-id 규칙이 라운드의 판정이 여전히 유효한지 정합니다. 그 헤드가 초록이고 판정의 patch-id와 `playbooks/shipping.md`의 규칙 아래 일치하면, 이후 트렁크가 움직여도 다시 리베이스하지 않아도 됩니다. 병합 직전에 트렁크를 가져와 헤드와 현재 트렁크의 `git merge-tree`가 깨끗한지 확인합니다. 또 `git diff --name-only $(git merge-base HEAD origin/main) origin/main`의 경로에 PR이 바꾸는 경로나, 그 PR의 CI를 정하는 경로(저장소의 CI 설정 경로 등)가 없는지 확인합니다. 둘 중 하나라도 실패하면 다시 리베이스하고 새 헤드 SHA를 보고하며, 그 헤드에서 CI가 통과할 때까지 이 검사를 반복합니다. patch-id가 바뀌지 않았으면 모를까, 새 헤드는 판정을 무효로 합니다. 소유자는 정해진 포지로 자기 PR을 스쿼시 병합하고 돌아갑니다. 대기열의 다음 자체 완결 항목은 `poteto-mode`의 Subagents 절에 따라 새 소유자가 잡습니다. 운영자의 완전 자율 부여와 루트의 깨끗한 판정이 babysit만으로는 절대 가질 수 없는 병합 권한입니다. 운영자가 이름 붙인 항목은 merge-ready에서 멈추고 운영자의 클릭을 기다립니다.
6. **루트 계층을 돌립니다.** 고정된 관문이나 예산 값(CI가 조이기만 허용하는 한계)을 진짜로 새로 올리려면 루트의 새 카운터사인이 필요하고, 검증자의 증명 뒤에만 줍니다. 운영자의 부여나 상시 지시가 승인을 덮는다면 그 카운터사인이 승인입니다. 소유자는 도구의 승인 계약이 허용하는 형태로 루트의 카운터사인을 가리키는 포인터와 함께 기록합니다. 레인이 그 기록을 카운터사인과 대조합니다. 루트는 포지가 강제하는 승인을 주거나 우회하지 않습니다. 이미 main에 랜딩된 값을 흡수하는 것은 상승이 아니라 표류입니다. 모든 소유자에 대해 한 시간마다 감사 tick을 돌립니다. 운영자의 승인에서 `/loop 1h`를 이 tick을 도는 프롬프트로 무장합니다. `/loop`는 로컬 루트와 클라우드 루트에서 모두 동작합니다. 주기를 기억이나 손실 있는 완료 알림에 맡기지 않습니다. tick마다 `git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-full.md`로 트렁크에서 이 플레이북을 다시 읽고 그것에 대해 운영을 감사하며 그 tick 안에서 표류를 고칩니다. 소유자마다 일반적인 생존이나 상태 검사로 조사하고 결정 기록을 수집합니다. 부수 효과(커밋, 푸시, PR이나 체크의 변화, 저장소 보고)만 진행으로 셉니다. 오류가 나거나 부수 효과 없이 예상 실행 시간을 넘긴 레인은 막힌 것으로 취급합니다. 내려놓고 즉시 대체를 배치합니다. 정중한 복귀를 기다리지 않습니다. tick은 소유자를 2단계가 요구하는 푸시된 브랜치와 결정 기록으로 판단하고, 턴을 시작할 수 없는 소유자의 에이전트는 교체합니다. tick마다 플랫폼이 에이전트 목록을 가진 곳에서는 그것과 모든 소유자의 `children.tsv`에 대해 막힌 레인 검사도 돌립니다. 정지가 통하든 아니든, 루트는 소유자가 각 막힌 서브에이전트를 막힌 것으로 기록하고 그 일이 아직 필요하면 대체하게 합니다. 소유자가 못하면 루트가 두 단계를 모두 합니다. 정체는 일을 증명하지도 버리지도 않습니다. 병합이 묶여 있으면 회고 패스와 병합 후 봇 댓글 스윕을 돌립니다. 마지막 병합 뒤에도 위임된 일이 남지 않을 때만 tick을 끝냅니다.
7. **운영자의 정지에서 즉시 서 있습니다.** 운영자의 보류나 스탠드다운은 쓰기 금지 명령으로 모든 소유자에게 즉시 닿습니다. 소유자는 운영자가 풀어 줄 때까지 브리프를 붙들고 있습니다.

### 응답

각 PR의 소유자, 상태, 헤드 SHA가 있는 대기열, 각 판정과 그것을 낸 swarm, 병합된 것과 각 새 소유자가 다음에 잡은 것, 부여한 카운터사인과 이유, 열린 운영자 관문, 수집한 결정 기록의 위치.

### 함정과 주의점

- 병합 전에 루트의 깨끗한 판정이 필요합니다. 소유자의 자기 판정만으로 병합하지 않습니다.
- 라이브 레인이 없는 판정은 깨끗하지 않습니다.
- 새 헤드는 patch-id가 바뀌지 않는 한 판정을 무효로 합니다.
- 운영자가 이름 붙인 항목은 병합하지 않고 merge-ready에서 멈춥니다.
- 공유 브랜치를 강제 푸시하지 않습니다.
- 병합 권한은 운영자의 완전 자율 부여와 루트의 깨끗한 판정이 합쳐진 것입니다. babysit만으로는 병합을 승인하지 않습니다.

### 흐름도

```flow Autopilot-full 플레이북의 흐름
start 독립된 PR 대기열을 병합까지
step 1. 운영자 몫을 표시하고 상태 후 대기
step 2. PR마다 소유자 하나
step 3. 진짜 병렬로, 쌓지 않음
step 4. 라운드마다 swarm 검증
  alt 증명된 발견이 있음 | 소유자에게 한 번에 고침 전달, 새 head는 새 판정
step 5. 깨끗한 판정에 소유자가 병합
  stop 운영자가 지명한 항목 | 병합 준비에서 멈추고 클릭을 기다림
  back 2 | 새 소유자가 다음 항목을 잡음
step 6. 루트 층
step 7. 운영자의 중지
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 운영자 몫 목록, 요청 시 프로토콜 진술 |
| 2 | PR마다 소유자, `decisions.tsv`와 `children.tsv`(커밋하지 않고 보고와 함께 반환), 첫 브랜치 스냅숏, ready PR, 검증 가능한 단위마다의 푸시, 코드 준비 head SHA 보고 |
| 3 | 독립적으로 도는 소유자들 |
| 4 | 라운드마다 집계된 swarm 판정(관문, 라이브, 회귀, 감사 레인) |
| 5 | 병합 준비 head SHA 보고, 병합된 PR |
| 6 | 감사 tick마다의 조정, 교체된 레인, 카운터사인과 소유자의 기록, 회고와 병합 뒤 봇 댓글 훑기 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "독립된 PR 여섯 개 대기열, 풀 오토파일럿으로 병합까지. PR 5는 내가 직접 클릭할게."
>
> 1. PR 5를 운영자 몫으로 표시합니다. 진술을 요청받았다면 진술하고 멈춘 뒤 명시적인 go에서 시작합니다.
> 2. PR마다 소유자를 하나씩 띄웁니다. 15분 안에 각 소유자가 `decisions.tsv`를 열고 첫 스냅숏을 푸시하고 ready PR을 엽니다. 이후 검증 가능한 단위마다 다시 푸시합니다.
> 3. PR은 서로 독립이라 병렬로 돕니다. 소유자가 코드 준비 head SHA를 보고하면 루트가 swarm으로 검증합니다.
> 4. PR 2의 라이브 레인이 실패하면 발견을 소유자에게 한 번에 보내고, 새 head는 새 swarm과 새 판정을 받습니다.
> 5. 깨끗한 판정이 나온 PR의 소유자는 최신 트렁크로 리베이스하고 CI와 `merge-tree`를 확인한 뒤 스스로 squash 병합하고 돌아갑니다. 다음 항목은 새 소유자가 잡습니다. PR 5는 병합 준비에서 멈춰 사용자의 클릭을 기다립니다.
> 6. 한 시간마다 `/loop 1h` 감사 tick으로 소유자들의 부수 효과(커밋, 푸시, PR 변화)를 확인하고, 아무 부수 효과가 없는 레인은 멈추게 하고 교체합니다.
> 7. 사용자가 멈추라고 하면 모든 소유자에게 쓰기 금지 명령이 즉시 갑니다.

### 실패, 중단, 모호할 때

- **운영자의 중지.** 홀드나 중단은 모든 소유자에게 즉시 쓰기 금지 명령으로 전달됩니다. 운영자가 풀 때까지 소유자는 브리프를 붙들고 있습니다.
- **사용자가 프로토콜이나 계획을 진술하라고 할 때.** 진술하고 멈춥니다. 명시적인 go에서만 시작합니다.
- **병합 직전에 트렁크가 움직일 때.** 헤드가 초록이고 판정의 patch-id와 일치하면 다시 리베이스하지 않아도 됩니다. 그래도 병합 직전에 `merge-tree`가 깨끗한지, 트렁크에서 움직인 경로가 PR이 바꾸는 경로나 CI를 정하는 경로와 겹치지 않는지를 확인합니다. 실패하면 다시 리베이스하고 CI를 기다립니다. 새 head는 patch-id가 그대로가 아닌 한 판정을 무효로 합니다.
- **레인이 오류를 내거나 예상 실행 시간을 넘기고도 부수 효과가 없을 때.** 멈춘 것으로 봅니다. 즉시 멈추게 하고 교체합니다. 정중한 반환을 기다리지 않습니다. 멈춤이 작업의 성공이나 폐기를 뜻하지는 않습니다.
- **고정된 관문이나 예산 값을 새로 올릴 때.** 검증자의 증명 뒤에만 루트가 새 카운터사인을 줍니다. 이미 main에 들어온 값을 흡수하는 것은 올림이 아니라 표류입니다. 포지가 강제하는 승인은 루트가 주거나 우회하지 않습니다.
- **운영자가 지명한 항목.** 소유자가 병합하지 않습니다. 병합 준비에서 멈춰 운영자의 클릭을 기다립니다.
- **쌓기.** 쌓지 않습니다. 진짜 의존적인 변경을 나눠야 하는 소유자만 짧은 비공개 베이스 브랜치 스택을 가질 수 있습니다.
- **tick의 끝.** 위임된 작업이 하나도 남지 않을 때만 끝납니다. 마지막 병합 뒤에도 마찬가지입니다.

## Autopilot-stack {#playbook-autopilot-stack}

원문: {{src:skills/poteto-mode/playbooks/autopilot-stack.md}} {{src:docs/guide/07-overnight.md}}

> 대기열을 완전 자율로 만들고 검증하되 랜딩은 하지 않고, 운영자가 리뷰하고 랜딩할 선형 베이스 브랜치 스택 하나를 넘깁니다.

### 언제 쓰는가

"autopilot-stack", "stack them, don't ship", "build the stack, I'll land it" 같은 요청입니다. Autopilot-full의 형제입니다. 안내서의 예입니다.

```text
/poteto-mode 이 변경 다섯 개를 autopilot으로 하되 스택으로 쌓기만 하고 배포하지는 마. 아침에 내가 스택을 랜딩할게.
```

원문의 선택 규칙은 이렇습니다. PR이 독립적이고 랜딩 권한이 부여되었으면 Autopilot-full, 운영자가 랜딩 전에 리뷰하고 싶거나 작업이 순서가 있거나 결합되었거나 병합 권한이 보류되었으면 Autopilot-stack입니다.

### 동작 방식

1. **소유자 루프를 그대로 돌립니다.** 프로그램 전체에서 포지를 한 번 정합니다. PR마다 Cursor 클라우드 에이전트 하나가 자기 변경을 처음부터 끝까지 소유합니다. 빌드, 첫 푸시, 자기 증명 전에 여는 준비 상태 PR, 자기 증명(관문, CI, 영수증), 회의적 Bugbot 분류, 슬롭 제거(cursor-team-kit의 `deslop`), `/no-comments`, 초록까지의 babysit입니다. 자체 완결이면 소유자는 병렬로 돕니다. 약 15분 안에 모든 소유자는 `decisions.tsv` 기록을 시작하고 첫 브랜치 스냅숏을 푸시하고 PR을 준비 상태로 엽니다. 그 뒤 소유자는 검증 가능한 단위마다 브랜치를 다시 푸시합니다(훅을 켜 두고, WIP 커밋도 됩니다). 기록은 커밋하지 않고 보고와 함께 돌려줍니다. 소유자는 Autopilot-full 2단계의 `children.tsv`도 유지합니다.
2. **진짜 루프로 감사합니다.** 루트는 한 시간마다 감사 tick을 돌립니다. 운영자의 승인에서 Autopilot-full 6단계대로 `/loop 1h`를 이 tick을 도는 프롬프트로 무장합니다. 주기를 기억이나 손실 있는 완료 알림에 맡기지 않습니다. tick마다 `git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-stack.md`로 이 플레이북을 다시 읽고 운영을 감사해 표류를 고칩니다. 소유자를 일반적인 생존이나 상태 검사로 조사하고, 부수 효과만 진행으로 세며, 부수 효과 없이 예상 시간을 넘긴 레인은 막힌 것으로 보고 내려놓고 대체를 배치합니다. 모든 서브에이전트를 조사하고 Autopilot-full 6단계대로 tick을 끝냅니다.
3. **운영자 관문을 지킵니다.** 먼저 말하고 기다립니다. 계획을 진술하라는 요청은 승인이 아닙니다. 운영자가 멈추라고 하면 모든 소유자가 즉시 쓰기 금지 보류에 들어갑니다.
4. **라운드마다 검증합니다.** 소유자는 출하할 코드가 최종이 되면 code-ready 헤드 SHA를, 루프가 초록이 되면 정확한 헤드 SHA와 함께 STACK-READY를 보고합니다. 루트는 merge-ready 대신 STACK-READY로 Autopilot-full 4단계대로 각 라운드를 검증합니다. 검증되지 않은 것은 스택에 들어가지 못합니다.
5. **깨끗한 판정에서 덧붙이고 배포는 하지 않습니다.** 어떤 소유자도 병합하거나 자동 병합을 무장하거나 닫지 않습니다. 깨끗한 판정은 PR을 검증된 순서나 운영자가 지정한 순서로 하나의 선형 베이스 브랜치 스택에 덧붙입니다.
6. **토폴로지는 작성자 하나, 빌드는 병렬 작성자.** 소유자는 자기 브랜치만 푸시하고 끝, 현재 베이스, 의도한 부모를 보고합니다. 루트만 토폴로지 작성자입니다. PR을 덧붙이려면 의도한 부모를 가져오고, 자식 브랜치를 그 정확한 부모 끝에 리베이스하고, `ls-remote` 확인 뒤에만 `--force-with-lease`로 푸시하고, PR의 베이스를 부모 브랜치로 설정합니다. `origin pr create --status open --base <parent-branch>` 또는 `gh pr create --base <parent-branch>`로 만들고, 기존 PR은 `origin pr edit <pr> --base <parent-branch>` 또는 `gh pr edit <pr> --base <parent-branch>`로 재지정합니다. 루트 PR만 트렁크를 대상으로 합니다. `gt`로 사슬을 제출하거나 등록하지 않습니다.
7. **루트에서 표류를 흡수하고 움직인 것을 다시 검증합니다.** 루트가 현재 트렁크를 가져와 사슬을 아래에서 위로 리베이스합니다. 리베이스가 소유자의 파일에서 충돌을 드러내면 그 소유자가 자기 조각을 고치고 루트가 결과를 푸시합니다. 리베이스는 그 위의 모든 SHA를 다시 쓰고 옛 SHA의 판정을 무효로 합니다. 판정 SHA마다 `playbooks/shipping.md`의 patch-id 규칙을 적용합니다. 더는 유효하지 않은 것은 배달 전에 이 플레이북의 4단계를 다시 거칩니다. patch-id가 바뀌지 않았어도 다시 쓴 푸시마다 병합 가능성과 CI를 다시 돌립니다. 카운터사인 규칙은 Autopilot-full과 같습니다. 진짜 새 고정은 루트의 새 카운터사인을 위해 정지를 올립니다. 랜딩된 값의 표류 흡수는 상승이 아닙니다.
8. **사슬을 배달합니다.** 산출물은 검증된 PR의 선형 사슬 하나이고, 정해진 포지에서 아래에서 위로 리뷰할 수 있으며, 모든 링크가 PR 본문이나 댓글에 검증자의 판정을 싣습니다. 운영자가 자기 클릭으로, 혹은 merge-when-ready를 무장해서 리뷰하고 랜딩합니다.

### 응답

스택 루트와 끝의 링크, 링크마다 한 줄의 판정 요약, 보류되거나 제외된 것과 이유.

### 함정과 주의점

- 어떤 소유자도 병합하거나 자동 병합을 무장하거나 닫지 않습니다.
- 토폴로지를 바꾸는 것은 루트 하나뿐입니다. 소유자는 자기 브랜치만 푸시합니다.
- 리베이스는 위의 모든 SHA를 다시 쓰므로 판정이 무효가 됩니다. patch-id 규칙으로 다시 확인합니다.
- `gt`로 사슬을 제출하지 않습니다.

### 흐름도

```flow Autopilot-stack 플레이북의 흐름
start 대기열을 만들어 검증하고, 착륙은 운영자가
step 1. 소유자 루프 그대로
step 2. 시간당 루프로 감사
step 3. 운영자 관문 유지
step 4. 라운드마다 검증
step 5. 깨끗한 판정에 스택에 덧붙임
step 6. 토폴로지 쓰기는 루트만
step 7. 표류 흡수와 재검증
  back 5 | 무효가 된 판정은 4단계로
step 8. 체인 전달
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | PR마다 소유자, `decisions.tsv`, `children.tsv`, 첫 스냅숏, ready PR |
| 2 | tick마다의 조정과 부수 효과 기반 진행 판단 |
| 3 | 운영자의 정지에 대한 쓰기 금지 |
| 4 | 코드 준비 head SHA와 STACK-READY 보고, 라운드별 swarm 판정 |
| 5 | 선형 베이스 브랜치 스택에 덧붙은 PR |
| 6 | 루트가 리베이스하고 base를 바꾼 PR(루트 PR만 트렁크가 base) |
| 7 | 흡수한 표류와 다시 검증한 판정 |
| 8 | 링크마다 검증자 판정이 PR 본문이나 댓글에 있는, 아래에서 위로 리뷰할 수 있는 선형 체인 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "이 변경 네 개를 서로 이어지는 스택으로 만들어서 검증까지 해 놔. 병합은 내가 리뷰하고 할게."
>
> 1. PR마다 소유자를 띄우고 각자 자기 브랜치에만 푸시합니다. 소유자들은 병합하지도 자동 병합을 장전하지도 않습니다.
> 2. 소유자가 STACK-READY와 head SHA를 보고하면 루트가 라운드를 swarm으로 검증합니다.
> 3. 깨끗한 판정이 나온 순서대로 루트가 부모 끝을 가져와 자식 브랜치를 그 위에 리베이스하고, `--force-with-lease`로 푸시하고, PR의 base를 부모 브랜치로 맞춥니다.
> 4. 트렁크가 움직이면 루트가 아래에서 위로 다시 리베이스합니다. 바뀐 SHA의 판정은 patch-id 규칙으로 유효 여부를 가리고, 무효가 된 것은 다시 검증합니다.
> 5. 링크마다 판정이 붙은 체인을 사용자에게 넘기고 착륙은 사용자에게 맡깁니다.

### 실패, 중단, 모호할 때

- **소유자가 병합하려 할 때.** 이 플레이북에서는 아무도 병합하지 않고 자동 병합을 장전하지 않으며 닫지 않습니다.
- **토폴로지 쓰기.** 루트가 유일한 토폴로지 작성자입니다. 소유자는 자기 브랜치에만 푸시하고 끝과 현재 base와 의도한 부모를 보고합니다. `gt`로 체인을 제출하거나 등록하지 않습니다.
- **리베이스가 소유자 파일에서 충돌할 때.** 그 소유자가 자기 조각을 고치고 루트가 결과를 푸시합니다.
- **리베이스 뒤의 판정.** 리베이스는 위쪽 모든 SHA를 다시 쓰고 옛 SHA의 판정을 무효로 만듭니다. Shipping의 patch-id 규칙을 적용하고, 유효하지 않은 것은 4단계로 되돌립니다. patch-id가 그대로여도 다시 쓴 푸시마다 병합 가능 여부와 CI는 다시 돌립니다.
- **카운터사인.** 규칙은 Autopilot-full과 같습니다. 새 핀은 루트의 카운터사인을 위해 멈춤을 일으키고, 이미 착륙한 값을 흡수하는 표류는 올림이 아닙니다.
- **운영자의 중지.** 모든 소유자가 즉시 쓰기 금지 상태로 들어갑니다.
- **둘 중 무엇을 쓸지.** 독립된 PR이고 착륙 권한이 주어졌으면 Autopilot-full입니다. 착륙 전에 리뷰를 원하거나, 일이 순서가 있거나 결합되어 있거나, 병합 권한이 보류되었으면 Autopilot-stack입니다.

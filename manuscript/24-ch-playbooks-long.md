# 장시간, 대규모 플레이북

원문 디렉터리: {{src:skills/poteto-mode/playbooks/autonomous-run.md}}

이 장은 한 번의 대화를 넘는 작업을 위한 플레이북 8개를 다룹니다. 하나의 작업을 끝까지 몰고 가는 Autonomous run, 이전 작업을 이어받고 안전하게 멈추는 Session pickup과 Pause safely, 디스크를 정리하는 Worktree and simulator cleanup, 계획서를 쓰는 Multi-phase or multi-PR plan, 그리고 여러 PR과 에이전트 무리를 다루는 Orchestrate, Autopilot-full, Autopilot-stack입니다. 밤새 맡기는 사용법은 [실전 부의 밤새 돌리기](overnight.md)에서 예와 함께 다룹니다.

## Autonomous run {#playbook-autonomous-run}

원문: {{src:skills/poteto-mode/playbooks/autonomous-run.md}} {{src:docs/guide/07-overnight.md}}

> 끝나는 조건을 먼저 정하고, 멈추지 않고 그 조건까지 몰고 갑니다.

### 언제 쓰는가

멈추지 않고 끝까지 가야 하는 긴 작업입니다("run until done", "/loop until X"). 며칠에 걸친 상시 프로젝트는 Orchestrate이고, 이것은 하나의 작업을 하나의 조건까지 몰고 가는 플레이북입니다.

### 동작 방식

부모는 종료 조건을 책임집니다.

1. 첫 반복 전에 종료 조건을 검사 가능한 술어로 밝힙니다(테스트 초록, 재현 수정됨, PR N개 모두 병합됨, 픽셀 diff 0).
2. Cursor의 `/loop` 명령(내장 기능이며 pstack 스킬이 아님)으로 깨우는 방식을 고릅니다. 지켜볼 이벤트(CI, 병합, 참조가 앞으로 감)가 있으면 이벤트에 깨우는 감시자 서브에이전트를 두고 긴 시간 기반 하트비트를 대비책으로 둡니다. 이벤트가 없으면 결과를 다시 확인할 가치가 생기는 때에 맞춘 고정 간격 하트비트를 씁니다. 띄울 때마다 그 일에 맞는 추론 강도와 일반 속도 또는 fast를 고릅니다. Subagents 절을 따릅니다.
3. 반복마다 증거가 정당화하는 가장 작은 변경을 하고, 술어에 대해 검증(verification)하고, 진전이 있으면 커밋하고, 도움이 되지 않은 변경은 버립니다. "도움이 될지도 모르는" 이중 안전장치는 되돌리고 그대로 두지 않습니다. `sequence-verifiable-units` 원칙(principle)에 따라 검사를 끝에 몰아서 하지 않고 단위마다 검증한 뒤 다음으로 갑니다.
4. 목표를 돕는 실행 중 발견은 자기 몫입니다. 고장난 스킬, 관련 버그, 불안정한 검증기(verifier), 리뷰 잡음, 도구 실패, 고아가 된 후속 작업, 고칠 수 있는 표류를 poteto-mode로 직접 처리합니다. 범위 밖 수정은 별도 PR로 냅니다. 되돌릴 수 있는 일을 사람에게 떠넘기거나 `AskQuestion`을 쓰지 않습니다. 올리는 것은 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 진짜 제품이나 취향 판단, 진짜 막다른 길뿐입니다. 술어를 주된 동력으로 삼고 곁가지 수정마다 술어로 돌아옵니다.
5. 반복마다 `show-me-your-work` 스킬로 체크포인트를 남깁니다. 무엇이 바뀌었고 술어가 움직였는지 한 행씩입니다.
6. 술어가 충족되면 멈춥니다. 정체는 멈춤이 아닙니다. 계속하면서 접근을 바꿔 뚫습니다. 진짜 막다른 길은 빙빙 돌지 말고 드러내고, 승리를 선언하려고 술어를 완화하지 않습니다.

### 응답

종료 조건, 실행한 반복, 랜딩된 것, 버린 것, 술어의 최종 상태.

### 함정과 주의점

기간은 종료 조건이 아닙니다. 안내서는 "4시간 동안 작업해"라고 하면 에이전트가 확인할 것이 없고 결과 대신 네 시간의 움직임을 얻는다고 경고합니다. `/loop`에 통과나 실패가 있는 술어를 줍니다.

### 흐름도

```flow Autonomous run 플레이북의 흐름
start 오래 걸리는 일을 멈추지 않고 끝까지
step 1. 종료 조건을 검사 가능한 술어로
step 2. 깨우는 장치 고르기
step 3. 반복
  alt 나아졌음 | 커밋
  alt 도움이 되지 않음 | 변경을 버림
step 4. 목표를 돕는 중간 발견은 스스로 처리
step 5. 반복마다 체크포인트
  back 4 | 술어가 충족될 때까지
step 6. 술어가 충족되면 멈춤
  stop 진짜 막다른 길 | 빙빙 돌지 않고 드러냄
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 검사 가능한 종료 술어 |
| 2 | 선택한 깨우는 장치(감시 서브에이전트와 긴 하트비트, 또는 고정 간격 하트비트) |
| 3 | 반복마다 커밋(나아졌을 때) 또는 폐기 |
| 4 | 별도 PR로 나간 범위 밖 수정 |
| 5 | 반복마다 결정 기록 한 행(무엇이 바뀌었고 술어가 움직였는지) |
| 6 | 술어 충족 확인 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "이 브랜치의 테스트가 전부 초록이 될 때까지 알아서 돌려 줘. 나는 자러 갈게."
>
> 1. 종료 조건을 "`bun test`가 실패 0으로 끝난다"로 적습니다.
> 2. 기다릴 이벤트는 CI이므로, 이벤트에서 깨우는 감시 서브에이전트와 긴 시간 기반 하트비트를 함께 씁니다.
> 3. 매 반복에서 실패 하나를 골라 그 증거가 정당화하는 가장 작은 변경을 하고 테스트를 돌립니다. 실패 수가 줄면 커밋하고, 그렇지 않으면 변경을 버립니다.
> 4. 반복 도중 깨진 린트 설정을 발견하면 그 수정은 별도 PR로 내보내고 술어로 돌아옵니다. 사용자에게 묻지 않습니다.
> 5. 매 반복 뒤 결정 기록에 한 행을 남깁니다.
> 6. 실패 0이 되면 멈춥니다. 중간에 정체하면 접근을 바꿔 밀고, 진짜 막다른 길이면 드러냅니다.

### 실패, 중단, 모호할 때

- **정체기.** 멈춤 조건이 아닙니다. 접근을 바꿔 밀고 나갑니다.
- **막다른 길.** 빙빙 돌지 않고 드러냅니다. 술어를 완화해 승리를 선언하지 않습니다.
- **도움이 되지 않은 변경.** 되돌립니다. "도움이 될지도 모르는" 변경을 남겨 두지 않습니다.
- **중간에 발견한 문제.** 목표를 돕는 발견이면 자기 몫입니다. 깨진 스킬, 관련 버그, 불안정한 검증기, 리뷰 잡음, 도구 실패, 남은 후속, 고칠 수 있는 표류는 스스로 처리하고, 범위 밖 수정은 별도 PR로 냅니다. 되돌릴 수 있는 일을 사람에게 미루거나 `AskQuestion`을 쓰지 않습니다.
- **사람에게 올리는 것.** 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 제품이나 취향의 결정, 진짜 막다른 길뿐입니다.

## Session pickup {#playbook-session-pickup}

원문: {{src:skills/poteto-mode/playbooks/session-pickup.md}} {{src:docs/guide/03-understand.md}}

> 이전 에이전트가 남긴 진행 중 작업을 이어받습니다. 이전 기록을 읽고, 다시 하지 않습니다.

### 언제 쓰는가

다른 에이전트(혹은 지난주의 자신)가 브랜치를 중간에 남겨 두었을 때입니다. 대화 기록, 클라우드 에이전트 URL, 푸시된 브랜치에서 이어받습니다.

```text
/poteto-mode 이 브랜치를 이어받아 줘. 결정 기록을 읽고, 무엇이 끝났는지 파악하고, 거기서부터 계속해 줘. 끝난 일은 다시 하지 마.
```

### 동작 방식

부모는 재개 지점을 책임집니다.

1. **이전 기록을 찾습니다.** 활성 워크스페이스의 `agent-transcripts/` 디렉터리 아래의 로컬 대화 기록(시스템 프롬프트가 경로를 알려 줌), 클라우드 에이전트 URL, 푸시된 브랜치입니다. `~/.cursor/projects/*/`를 글롭하지 않습니다. 워크스페이스 경계를 넘어 무관한 프로젝트의 비공개 채팅을 읽게 됩니다. 메타데이터 개요와 마지막 메시지를 먼저 읽고 결정 지점을 찾아 거슬러 올라갑니다. 긴 대화 기록은 서브에이전트에서 파싱하고 줄인 타임라인만 메인 스레드에 둡니다(`principle-guard-the-context-window`). 띄울 때마다 그 일에 맞는 추론 강도와 일반 속도 또는 fast를 고릅니다. Subagents 절을 따릅니다.
2. **운영 상태를 재구성합니다.** 브랜치와 워크트리, 이미 랜딩된 것(`git log`, 베이스 대비 `git diff`), 열린 할 일, 내려진 결정. 이전 기록은 권위 있는 입력입니다. 다시 도출하려는 편향에 저항합니다.
3. **끝난 것과 남은 것을 비교합니다.** 배포된 것과 계획된 것을 비교하고, 재개 지점에 이름을 붙이고, 이전 재현을 다시 돌리거나 완료된 작업을 다시 하지 않습니다. "처음부터 검증해 볼게요" 패스는 권위 있는 기록을 못 믿을 것으로 취급하고 있다는 뜻입니다.
4. **남은 작업을 맞는 플레이북으로 라우팅하고 판정을 고릅니다.** 실행 계속, 끝난 권고 배포, 이전 결론의 승인 또는 번복, 실패한 실행의 포스트모템. 이 플레이북은 여기서 끝나고 라우팅된 플레이북이 나머지를 맡습니다.
5. **물려받은 주장을 원래 목표에 대해 실제 산출물(artifact)로 검증합니다**(`principle-prove-it-works`). 통과한 이전 자기 보고는 증명이 아닙니다.

### 응답

이전 에이전트가 어디서 멈췄는지, 물려받은 것과 다시 한 것(이상적으로는 다시 한 것이 없음), 재개 지점, 결과.

### 함정과 주의점

- 재개할 특정 채팅 하나는 이 플레이북이고, 최근 채팅 여러 개에서 맥락을 모으는 것은 [`recall`](teach-recall.md#skill-recall)입니다. 이 채팅에서 사용자의 마지막 메시지 이후만 따라잡는 것은 [`ketchup`](teach-recall.md#skill-ketchup)입니다.
- 이전 기록을 못 믿어서 처음부터 다시 도출하지 않습니다. 단, 물려받은 주장은 실제 산출물로 검증합니다.

### 흐름도

```flow Session pickup 플레이북의 흐름
start 이전 에이전트의 작업을 이어받음
step 1. 이전 흔적 찾기
  alt 대본이 김 | 서브에이전트에서 파싱, 줄인 타임라인만 메인에
step 2. 운영 상태 재구성
step 3. 끝난 것과 남은 것을 대조
  alt 처음부터 다시 검증하고 싶어짐 | 흔적을 신뢰하지 않는 신호, 다시 하지 않음
step 4. 남은 일을 맞는 플레이북으로
step 5. 물려받은 주장을 실제 산출물로 검증
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 줄인 타임라인(메타데이터 개요, 마지막 메시지, 결정 지점) |
| 2 | 브랜치와 워크트리, 착륙한 것(`git log`, 기준(base)에 대한 `git diff`), 열린 할 일, 내린 결정 |
| 3 | 완료 대 미완료의 대조와 재개 지점 |
| 4 | 판정 하나(실행 이어가기, 끝난 권고를 배포, 이전 결론을 비준하거나 뒤집기, 실패한 실행의 사후 분석)와 라우팅 |
| 5 | 원래 목표에 대해 실제 산출물로 확인한 결과 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "어제 다른 에이전트가 하던 마이그레이션이야. 푸시된 브랜치가 있어. 이어서 끝내 줘."
>
> 1. 브랜치의 로그와 관련 대본이 있으면 메타데이터 개요와 마지막 메시지부터 읽고, 결정 지점만 거슬러 올라가 줄인 타임라인을 만듭니다. 대본이 길면 서브에이전트에서 파싱합니다.
> 2. 이미 착륙한 커밋과 열린 할 일을 정리합니다. 이전 흔적은 권위 있는 입력입니다.
> 3. 계획의 8개 단위 중 5개가 끝났다는 것을 확인하고 6번을 재개 지점으로 정합니다. 앞의 재현을 다시 돌리지 않습니다.
> 4. 남은 일은 Feature의 플레이북으로 라우팅하고 판정은 "실행 이어가기"입니다. 그 뒤는 라우팅한 플레이북이 맡습니다.
> 5. 마지막에 이전 에이전트가 낸 "통과" 보고를 믿지 않고 원래 목표에 대해 실제 산출물로 확인합니다.

### 실패, 중단, 모호할 때

- **처음부터 다시 검증하고 싶을 때.** 흔적을 신뢰할 수 없는 것으로 다루는 신호입니다. 이전 흔적은 권위 있는 입력이므로 다시 도출하려는 편향에 저항합니다.
- **이전 에이전트의 자기 보고가 통과일 때.** 증거가 아닙니다. 실제 산출물로 확인합니다.
- **대본을 어디서 찾을지.** 활성 작업공간의 `agent-transcripts/` 아래를 읽습니다. `~/.cursor/projects/*/` 전체를 글롭하지 않습니다. 작업공간 경계를 넘어 관계없는 프로젝트의 비공개 채팅을 읽게 되기 때문입니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 단계 |
| --- | --- | --- |
| [`guard-the-context-window`](principles.md#skill-principle-guard-the-context-window), [`prove-it-works`](principles.md#skill-principle-prove-it-works) | 원칙 | 본문의 각 단계 |
| `git log`, `git diff` | 명령 | 2 |
| 상황에 맞는 플레이북 | 플레이북 | 4 |

## Pause safely {#playbook-pause-safely}

원문: {{src:skills/poteto-mode/playbooks/pause-safely.md}}

> 진행 중인 작업을 나중에 이어 갈 수 있게 깨끗하게 멈춥니다. 콜드 스타트 에이전트가 재개할 수 있는 체크포인트를 남깁니다.

### 언제 쓰는가

명시적으로 일시 정지를 요청하거나, 오프라인이 되거나, Cursor를 재시작하거나, 컨텍스트 압축이 임박했을 때입니다. Session pickup의 짝입니다. 명시적일 때만 씁니다. "keep going", "going to bed, keep going", "don't stop"이면 멈추지 않습니다.

### 동작 방식

1. 안전한 경계에서 멈춥니다. 현재의 원자적 단계를 끝내거나 물립니다. 새로운 것을 시작하지 않고 중첩된 서브에이전트를 취소합니다.
2. 멈추려고 되돌릴 수 없는 행동을 하지 않습니다. 이미 내보낸 것이 없으면 PR도 푸시도 하지 않습니다.
3. 작업을 영속적으로 만듭니다. 커밋되지 않은 편집을 현재 브랜치에 명확한 `wip:` 커밋 하나로 커밋해 아무것도 잃지 않게 합니다. 트리가 깨져 있으면 커밋 본문에 한 줄로 밝힙니다.
4. 컨텍스트 밖에 재개 메모를 씁니다. 의도, 하던 일, 진행과 검증된 것, 현재 상태, 다음 단계, 핵심 파일, 함정을 담습니다. 압축 트리거이면 `/tmp/<slug>-resume.md` 같은 파일에 씁니다. show-me-your-work 기록이 있으면 복제하지 말고 그것을 가리킵니다.

### 응답

루프의 어디에 있는지, 디스크에 있는 것과 머릿속에만 있는 것(경로만, diff 덤프 없이), 만든 커밋과 트리가 깨끗한지, 재개할 때의 첫 행동. 최종 보고가 아니라 일시 정지입니다.

### 흐름도

```flow Pause safely 플레이북의 흐름
start 명시적으로 일시 중지를 요청받음
  stop 계속 진행하라는 말 | 멈추지 않음 (keep going, don't stop)
step 1. 안전한 경계에서 멈춤
step 2. 되돌릴 수 없는 행동을 하지 않음
step 3. 작업을 영속화
step 4. 재개 노트를 컨텍스트 밖에 작성
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 안전한 경계에서 멈춘 상태 |
| 2 | 없음(새 PR, 새 푸시 없음) |
| 3 | 현재 브랜치의 `wip:` 커밋 하나. 트리가 깨졌으면 커밋 본문 한 줄에 밝힙니다 |
| 4 | 재개 노트. 컴팩션 트리거라면 `/tmp/<slug>-resume.md` 같은 파일. `show-me-your-work` 기록이 있으면 복제하지 않고 가리킵니다 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "지금 노트북 닫아야 해. 안전하게 멈춰 줘."
>
> 1. 진행 중이던 테스트 실행을 마치고, 새 작업은 시작하지 않으며 돌던 서브에이전트를 취소합니다.
> 2. 이미 열린 PR이 없으므로 PR을 새로 열지 않고 푸시도 하지 않습니다.
> 3. 커밋되지 않은 편집을 `wip:` 커밋 하나로 남기고, 테스트 하나가 아직 실패하므로 커밋 본문에 한 줄로 적습니다.
> 4. 의도, 하던 일, 검증된 것, 다음 단계, 핵심 파일, 함정을 재개 노트에 적습니다.
> 5. 응답에는 지금 어디쯤인지, 디스크에 남은 것, 커밋, 다시 시작할 때의 첫 동작을 적습니다. 최종 보고가 아니라 일시 중지라고 밝힙니다.

### 실패, 중단, 모호할 때

- **명시적으로 요청할 때만 씁니다.** "계속해", "자러 갈 건데 계속해", "멈추지 마" 같은 말에는 멈추지 않습니다.
- **트리가 깨져 있을 때.** 그렇게 커밋 본문에 한 줄로 밝힙니다.
- **일시 중지의 계기.** 명시적 일시 중지, 오프라인 전환, Cursor 재시작, 임박한 컨텍스트 컴팩션이 있습니다. 컴팩션이면 재개 노트를 파일로 씁니다.
- **PR과 푸시.** 이미 낸 것이 없으면 새로 PR을 열거나 푸시하지 않습니다. 일시 중지는 되돌릴 수 없는 행동으로 이루어지지 않습니다.

## Worktree and simulator cleanup {#playbook-worktree-cleanup}

원문: {{src:skills/poteto-mode/playbooks/worktree-cleanup.md}} {{src:skills/poteto-mode/scripts/worktree-audit.sh}}

> 병합되었거나 버려진 git 워크트리와 오래된 iOS 시뮬레이터를 정리해 디스크를 되찾습니다.

### 언제 쓰는가

"what's using my disk", "clean up worktrees", "prune safe-to-prune worktrees", "free up space", "delete old simulators" 같은 요청입니다. 안내서의 예입니다.

```text
/poteto-mode 디스크를 뭐가 먹고 있어? 지워도 안전한 워크트리는 정리해 줘.
```

이 플레이북은 코드 리뷰가 실수를 잡아 주지 않는 채로 사용자 상태를 지우는 유일한 플레이북이라서, 아래의 관문(gate)이 곧 리뷰입니다.

### 동작 방식

삭제는 되돌릴 수 없으므로 모든 단계가 사용 중이거나 커밋되지 않은 작업이 있는 것을 지우지 않도록 지킵니다.

1. **스냅숏과 감사.** `df -h /`를 기록한 뒤 `scripts/worktree-audit.sh [-b <pr-base-ref>] [repo-path]`를 돌립니다(`principle-build-the-lever`). `-b`가 없으면 `MERGED`는 `origin/HEAD`를 기준으로 하므로, PR이 다른 브랜치를 대상으로 하면 `-b origin/<branch>`를 넘깁니다. 경로는 손으로 입력하지 않고 `git worktree list`에서 읽습니다. 손으로 쓴 `myrepo-worktrees/x`는 `.cursor/worktrees/myrepo/x`에 있는 것을 놓치기 때문입니다(`principle-encode-lessons-in-structure`). 이 스크립트는 워크트리마다 크기, 나이, 병합 상태, 커밋되지 않은 작업, PR 상태, 그것을 건드린 가장 최근 채팅을 분류하고 버킷을 제안합니다. 대화 기록 스캔은 느리므로 백그라운드로 돌립니다.
2. **버킷은 조언이지 허가가 아닙니다.** 고정된 채팅과 활성 채팅이 진짜 산출물입니다(`principle-prove-it-works`). 그 집합을 사용자나 사이드바에서 받아 모든 후보와 교차 확인합니다. 지렛대(스크립트)가 사용자가 고정해 둔 워크트리를 `safe`로 표시한 적이 있으므로, 고정 집합이 이깁니다.
3. **삭제 전에 사용 여부를 검증합니다.** 모든 `verify-recent-chat` 행이나 의심스러운 것은 서브에이전트를 팬아웃해 대화 기록을 읽고 그 채팅이 고정되었거나 진행 중인지, 어느 워크트리를 건드리는지 보고하게 합니다(`principle-guard-the-context-window`, 대화 기록은 대용량입니다). 고정된 채팅은 백그라운드 서브에이전트로 arena와 재현 트리를 형제 워크트리에 만들고, 그 이름이 사이드바에 나타나지 않아도 사용 중입니다. 띄울 때마다 그 일에 맞는 추론 강도와 일반 속도 또는 fast를 고릅니다. Subagents 절을 따릅니다.
4. **되돌릴 수 없는 손실 앞에서 멈춥니다.** `wip:N`은 추적되는 커밋되지 않은 편집 N개입니다. 깨끗한 워크트리는 브랜치에서 복구할 수 있지만 커밋되지 않은 작업은 사라지므로 diff를 보여 주고 결정을 먼저 받습니다. `scratch:N`은 추적되지 않는 일회용이라 버려도 안전하지만 파일 이름을 밝힙니다. Autonomy에 따라 깨끗하고 병합되었고 사용 중이 아니면 진행하고, `wip`와 사용 중이면 멈춥니다.
5. **확정된 집합을 정리합니다.** 경로마다 `git worktree remove --force <path>`. 무시된 빌드 산출물 때문에 디렉터리가 남으면 `rm -rf`한 뒤 `git worktree prune`. 브랜치 참조는 남으므로 커밋은 잃지 않습니다. `df -h /`로 확인하고 다시 나열합니다.
6. **시뮬레이터와 그 밖의 회수 대상.** 시뮬레이터가 보통 그다음으로 큰 이득입니다. `xcrun simctl --set testing delete all`(XCTestDevices 복제본), `xcrun simctl delete unavailable`, `xcrun simctl runtime list` 뒤에 `runtime delete <id>`로 오래된 런타임. 더 필요하면 Xcode `DerivedData`와 `iOS DeviceSupport`, `~/Library/Application Support/Cursor`(`state.vscdb.backup`, 그리고 작업 공간으로 연 폴더 이름이 붙은 `<root>`가 부풀어 오르는 `snapshots/roots/<root>`), 패키지 캐시(pnpm, uv, brew, yarn). 사용자가 남기라고 하지 않은 캐시만 지웁니다.

### 응답

`df -h /`의 전과 후와 되찾은 공간, 정리한 워크트리, 보류한 것마다 한 줄 이유(어느 채팅이 쓰는 중인지, 혹은 커밋되지 않은 작업).

### 보조 자료: worktree-audit.sh

이 스크립트는 모든 git 워크트리를 감사하고 제안 버킷이 붙은 표를 출력합니다. 헤더 주석은 "아무것도 지우지 않는다"고 말합니다. 사용법은 `worktree-audit.sh [-b|--base <ref>] [repo-path]`이고 경로 기본은 `git rev-parse --show-toplevel`입니다. `-b`는 `MERGED` 열이 대조하는 참조입니다. 없으면 기준은 `origin/HEAD`, 그다음 `origin/main`, 그다음 `origin/master`입니다. `origin/HEAD`는 원격의 기본 브랜치이지, PR이 들어가는 브랜치와 다를 수 있으므로 다를 때는 `-b`를 넘깁니다. `-b`를 주지 않으면 stderr에 `MERGED`가 어떤 기준을 쓰는지 경고합니다. git 저장소가 아니면 종료 코드 1로 "not in a git repo; pass a repo path"를 냅니다. 메인 워크트리(`git worktree list --porcelain`의 첫 항목)는 건너뜁니다. 실행할 때 기준이 `origin/*`이면 그 참조를 fetch하고(실패하면 경고), PR 목록을 한 번 가져옵니다. Origin CLI가 이 저장소의 PR을 읽을 수 있으면 `origin pr list --author "@me" --state all --limit 1000`이고, 아니면 `gh pr list`입니다. 둘 다 안 되면 목록은 비어 있습니다. 내 PR만 보입니다.

출력은 탭으로 구분되고 헤더는 `SIZE AGE MERGED DIRTY REMOTE PR LAST_CHAT BUCKET WORKTREE`이며 크기순(큰 것이 위)으로 정렬됩니다.

| 열 | 뜻 |
| --- | --- |
| `SIZE` | `du -sh` |
| `AGE` | HEAD 커밋 이후 일수(`12d` 형식), 모르면 `?` |
| `MERGED` | HEAD가 기준 참조(`-b` 또는 `origin/HEAD`)의 조상이면 `YES`, 아니면 `no`. 스쿼시 병합은 놓치므로 PR 상태가 더 강한 신호입니다 |
| `DIRTY` | `clean`, `wip:N`(추적되는 변경 N개), `scratch:N`(추적되지 않는 항목만 N개) |
| `REMOTE` | `detached`, `pushed`, `ahead<N>`, `no-remote` |
| `PR` | `#<number>/<STATE>` 또는 `-` |
| `LAST_CHAT` | 워크트리 경로를 언급하는 대화 기록 파일 중 가장 최근에 수정된 것의 날짜, 없으면 `-`. `~/.cursor/projects/<repo-path-slug>/agent-transcripts` 아래를 `rg`로 검색하며, 경로 뒤에 `/`나 `"`가 와야 일치하므로 `glint-482`는 `glint-482-r37`과 일치하지 않습니다 |

버킷 규칙(bucket)은 순서대로 적용됩니다. (1) DIRTY가 `wip:`로 시작하면 `hold-wip`. (2) PR이 `*/open`이거나 `*/draft`이면 `hold-open-pr`. 초안은 열린 PR과 같이 붙듭니다. (3) 최근 4일 안에 채팅이 있으면 `verify-recent-chat`. (4) `MERGED=YES`이거나 PR이 하나라도 있으면(CLOSED 포함) `safe`. (5) 그 밖은 `review`. `git`, `jq`, `rg`, `awk`, `sed`, `du`, `xargs`, `sort`, `mktemp`이 필요하고, Origin 또는 `gh` 중 하나가 PR 목록을 채웁니다. 대화 기록의 수정 시각은 GNU coreutils면 `stat -c`와 `date -d`, 아니면 `stat -f`와 `date -r`입니다. 한 번 골라 씁니다. 부수 효과는 기준 `origin/*` 원격 참조 갱신과 임시 파일뿐이고 아무것도 지우지 않습니다.

### 함정과 주의점

- 버킷 `safe`를 삭제 허가로 읽지 않습니다. 고정된 채팅의 집합이 우선합니다.
- `wip:N`은 diff를 보여 주고 결정을 받은 뒤에만 지웁니다.
- 경로를 손으로 입력하지 않고 `git worktree list`에서 읽습니다.
- PR이 원격 기본 브랜치가 아닌 브랜치를 대상으로 하면 `-b origin/<branch>`를 넘깁니다. 없으면 `MERGED`는 `origin/HEAD`를 봅니다.

### 흐름도

```flow Worktree and simulator cleanup 플레이북의 흐름
start 디스크를 되찾고 싶음
step 1. 스냅숏과 감사
step 2. 버킷은 조언일 뿐
step 3. 삭제 전에 사용 여부 검증
step 4. 되돌릴 수 없는 손실 앞에서 멈춤
  stop wip:N (추적되는 미커밋 편집) | diff를 보이고 결정을 받음
  alt scratch:N (추적되지 않는 임시) | 파일 이름을 밝히고 버려도 됨
step 5. 확정된 집합을 정리
step 6. 시뮬레이터와 기타 회수 대상
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | `df -h /` 기록, 감사 표(크기, 나이, 병합 상태, 미커밋 작업, PR 상태, 마지막으로 닿은 채팅, 제안된 버킷) |
| 2 | 고정된 채팅과 활성 채팅의 집합, 후보별 교차 대조 |
| 3 | `verify-recent-chat` 행마다 채팅이 고정 또는 진행 중인지, 어떤 워크트리를 건드리는지에 대한 보고 |
| 4 | `wip`이면 보여 준 diff와 받은 결정, `scratch`이면 이름을 밝힌 파일 목록 |
| 5 | 정리된 워크트리. 브랜치 참조는 남습니다 |
| 6 | 정리된 시뮬레이터 등 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "디스크가 꽉 찼어. 안 쓰는 워크트리 정리해 줘."
>
> 1. `df -h /`를 기록하고 감사 스크립트를 돌립니다. 대본 스캔이 느리므로 백그라운드로 돌립니다.
> 2. 스크립트가 `safe`로 표시한 워크트리 중에 사용자가 고정해 둔 채팅이 쓰는 것이 있어 고정된 쪽이 이깁니다. 사용자에게서 고정 채팅 목록을 받아 후보를 하나씩 대조합니다.
> 3. `verify-recent-chat` 행은 서브에이전트에게 대본을 읽혀 채팅이 진행 중인지 확인합니다.
> 4. `wip:2`인 워크트리는 diff를 보여 주고 결정을 받을 때까지 손대지 않습니다. 깨끗하고 병합되었고 쓰이지 않는 것만 진행합니다.
> 5. 확정된 경로마다 `git worktree remove --force`를 실행하고 `git worktree prune`을 돌린 뒤 `df -h /`로 회수량을 확인합니다.

### 실패, 중단, 모호할 때

- **미커밋 작업.** `wip:N`은 추적되는 미커밋 편집 N개입니다. 깨끗한 워크트리는 브랜치에서 복구할 수 있지만 미커밋 작업은 사라지므로 diff를 보이고 결정을 먼저 받습니다. `scratch:N`은 추적되지 않는 임시라 버려도 안전하지만 파일 이름을 밝힙니다.
- **버킷과 사용자의 고정 목록이 어긋날 때.** 고정된 집합이 이깁니다. 버킷은 조언이고 허가가 아닙니다.
- **이름이 사이드바에 없어도 쓰이는 워크트리.** 고정된 채팅이 배경 서브에이전트로 arena와 재현 트리를 형제 워크트리에 만들기 때문에, 그것들은 사용 중입니다.
- **디렉터리가 남을 때.** 무시된 빌드 산출물 때문에 디렉터리가 살아남으면 `rm -rf`한 뒤 `git worktree prune`을 합니다.
- **자율 규칙(Autonomy section).** 깨끗하고 병합되고 쓰이지 않는 것은 진행합니다. `wip`와 사용 중은 멈춥니다.
- **다른 회수 대상.** 사용자가 보관하라고 하지 않은 캐시만 비웁니다.
- **경고.** 코드 리뷰가 실수를 잡아 주지 않는 상태에서 사용자 상태를 지우는 유일한 플레이북이므로, 위의 관문들이 곧 리뷰입니다.

## Multi-phase or multi-PR plan {#playbook-multi-phase-plan}

원문: {{src:skills/poteto-mode/playbooks/multi-phase-plan.md}} {{src:skills/poteto-mode/scripts/check-plan.mjs}}

> 여러 단계나 스택된 PR에 걸친 작업의 계획서를 씁니다. 계획서가 산출물이고 구현은 하지 않습니다.

### 언제 쓰는가

단계나 스택된 PR에 걸친 작업입니다. 원문 README의 예는 "이 스킬들을 플러그인으로 오픈소스화해 줘. 내부 정보가 새면 안 되고, 임시 디렉터리에서 작업하고, 의존성 그래프를 먼저 보여 줘"입니다.

### 동작 방식

부모는 계획을 책임지고 코드는 책임지지 않습니다. 계획서는 소유자가 상자 하나씩 실행하고 운영자가 증거로 감사하는 체크리스트입니다.

1. 변경이 파일 한두 개에 접근이 뻔하면 계획을 건너뜁니다. 그렇다고 말하고 멈춥니다.
2. 글을 쓰기 전에 열린 질문을 프로토타입으로 정리합니다. 질문마다 `playbooks/prototype.md`를 돌립니다. 브랜치, SHA, 스크린숏을 부록 A용으로 보관합니다. 어떤 실행으로도 풀 수 없는 제품이나 취향 판단에 한해서만 운영자에게 묻고 선택지를 줍니다(`never-block-on-the-human` 원칙).
3. `subagent_type: "poteto-agent"`와 명시된 모델로 서브에이전트에서 탐색합니다(`guard-the-context-window` 원칙). 띄울 때마다 그 일에 맞는 추론 강도와 일반 속도 또는 fast를 고릅니다. Subagents 절을 따릅니다. 각자 파일 포인터, 관례, 테스트 명령, 진입점을 돌려줍니다. 덤프를 붙여 넣지 않습니다.
4. 아래 뼈대(skeleton)를 계획서 파일에 복사하고 모든 자리표시자를 채웁니다. 운영자가 경로를 지정하지 않으면 에이전트 저장소의 `docs/` 아래에 씁니다. 모든 제목과 하위 블록을 보인 순서대로 유지합니다. PR마다 절 하나, PR 하나는 자기 증거가 있는 변경 하나입니다(`sequence-verifiable-units` 원칙). **How to read this**에 실행 플레이북을 명시합니다. 실행이 병합해도 되면 `playbooks/autopilot-full.md`를 고르고, 운영자가 PR을 랜딩하면 `playbooks/autopilot-stack.md`를 고릅니다. 상시 프로그램이면 `playbooks/orchestrate.md`를 씁니다.
5. `/technical-writing` 전체로 쓴 뒤 `/unslop`을 적용합니다. 본문은 Diátaxis 모드 하나, how-to입니다. 부록에 설명과 참조를 둡니다. 각 제목은 과업이나 발견을 말합니다. 긴 줄표도, 문장 중간 콜론도 쓰지 않습니다.
6. `node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`를 돌리고 출력되는 모든 줄을 고칩니다(`encode-lessons-in-structure` 원칙).
7. 넘깁니다. 계획서 경로와 스크립트 출력을 게시하고 멈춥니다. 실행은 운영자의 명시적 승인에서 시작하며, 계획서가 지정한 실행 플레이북 아래에서 합니다.

**검증 규칙.** 테스트만으로는 충분한 검증이 아닙니다. PR은 단위, 라이브, 성능 상자가 모두 체크되어야만 검증된 것입니다(`prove-it-works` 원칙(principle)). 이 문장이 검증 규칙(rule)이고 모든 검증 블록이 이것으로 시작합니다. 라이브 블록은 필수입니다. PR 헤드에서 열 개의 레인이 control 스킬로 실제 표면을 구동하며, `swarm` 스킬에 따라 `swarm workers` 모델(기본 `grok-4.7-xhigh-fast`)로 돌립니다. 레인마다 상자 하나이고 구체적 시나리오, 저장하는 스크린숏, 통과 술어가 있습니다. 레인 하나는 **Regression lane against trunk**입니다. 같은 핵심 시나리오를 트렁크와 헤드에서 돌립니다. 트렁크에 기능이 없으면 그 사실을 기록하고, 트렁크 결과를 지어내지 않고 diff가 더한 동작과 사용자가 기다리는 최종 상태를 관문으로 삼습니다. 성능 관문은 양쪽입니다. 트렁크와 헤드가 모두 지정된 지표를 내야 합니다. 트렁크에 기능이 없으면 diff가 더한 작업을 분리해서 그 작업과 사용자가 기다리는 종단 상태에 절대 예산을 정합니다. 서로 다른 시나리오 사이의 비율은 주장하지 않습니다. 성능 블록은 지표, 교차 실행하는 프로브, 먼저 측정한 트렁크 기준선, 실패하는 수치가 있는 규칙을 밝힙니다. 상호작용을 바꾸는 PR은 리뷰 관문이 걸립니다. 운영자가 병합 전에 채팅에서 스크린숏과 영상으로 검토합니다. 상호작용을 바꾸지 않는 PR은 `**Review gate.** None. <PR id> is not review-gated.`를 쓰고 그 아래에 상자를 두지 않습니다.

**Control 스킬.** 표면에 따라 고릅니다. 브라우저, Electron, 웹 UI는 cursor-team-kit의 `control-ui`, CLI와 TUI는 cursor-team-kit의 `control-cli`, 네이티브 모바일은 저장소가 가진 시뮬레이터 구동 스킬을 씁니다. 두 표면을 건드리는 PR은 양쪽에 레인을 둡니다. control 스킬이 없는 표면은 부록 C의 위험이고, 그 라이브 블록도 각 레인이 어떻게 구동하는지 이름을 밝힙니다.

#### 계획서 뼈대

계획서는 다음 구조를 따릅니다. 원문이 코드 블록으로 제공하는 뼈대의 골격입니다.

| 부분 | 내용 |
| --- | --- |
| `# <Program> plan` | 열 줄 미만. 무엇이 바뀌고 누구를 위한 것이며 프로그램이 강제하는 규칙과 순서 있는 PR id |
| `## How to read this` | 상자 하나는 작업 단위 하나이고 모든 상자는 자기를 확인하는 증거를 이름 붙입니다. 중첩된 상자는 위 상자의 하위 단계. 증거(파일, 로그 줄, 스크린숏, 테스트 실행, SHA)가 있을 때만 상자를 체크합니다. 본문은 how-to이고 부록은 설명하고 기록합니다. 실행 플레이북, 누가 병합하는지, 검증 규칙 문장 |
| `## Program checklist` | `### Arm the program`(프로토콜과 계획을 진술한 뒤 멈추고, 운영자의 명시적 승인에서만 시작, 트렁크에서 플레이북과 스킬을 읽기, 운영자의 승인에 `/loop 1h`로 감사 tick과 그 프롬프트, 정지 명령), `### Spawn owners`(PR마다 소유자 하나, 의존성 그래프, 파일 경계, 리뷰 관문), `### PR mechanics, for every PR`(포지 정하기, Opening a PR대로 준비 상태로 열기. 내장 PR 도구가 있으면 그 도구, 없으면 정한 포지의 `origin`이나 `gh`. 린트와 타입 검사, `/deslop`과 `/no-comments`, Bugbot 분류. 리베이스는 코드 준비 보고 전에 현재 트렁크로 하고, 그 뒤로는 병합 준비, 트렁크와의 `git merge-tree` 충돌, 트렁크 변경에서 온 CI 실패, 같은 파일에 대한 알려진 동시 변경이 들어올 때만 다시), `### Verdict and merge, for every PR`(전체 swarm은 코드 준비 헤드에서 한 번. 새 동작, 재설계, 큰 새 diff일 때만 다시 전체 swarm. 리베이스, 병합 충돌 해결, 작은 수정은 새 헤드에서 검증자 하나이고, 문구만 바꾼 변경은 검증자가 없음. 관문 레인 하나, 라이브 레인 열 개, 성능 레인, 감사 레인 둘 이상. 발견마다 실행 플레이북의 막는 규칙으로 판단. 마지막 상자는 병합 또는 넘김 규칙의 자리표시자), `### Boot recipe, for every live lane` |
| PR 절 | PR마다 `**Depends on.**`, `**Files.**`, `**Build.**`, `**You see.**`, `**Verify, unit.**`, `**Verify, live.**`(레인 1에서 10), `**Verify, perf.**`(Metric, Probe, Baseline, Rule), `**Review gate.**`, `**Merge.**` 순서 |
| `## Close the program` | 모든 상자가 증거와 함께 체크됨, 운영자에게 실행 플레이북이 이름 붙인 보고서 |
| 부록 | A. Prototype evidence, B. Alternatives rejected, C. Risks, D. Links and reading list |

모든 발견은 실행 플레이북의 막는 규칙으로 판단하고, 막는 발견이 없을 때 판정이 깨끗합니다. `Regression lane against trunk.`로 표시한 레인에서 트렁크 동작이 실패하면 트렁크에 기록하고 PR을 막지 않습니다. 새 헤드는 새 판정을 받되, `playbooks/shipping.md`의 patch-id 규칙 아래 유효한 결과는 예외입니다. `### Verdict and merge, for every PR`의 마지막 상자에는 실행 플레이북의 병합 규칙이나 넘김 규칙을 Shipping의 patch-id 규칙과 함께 적습니다.

원문의 감사 tick 프롬프트는 이렇게 요약됩니다. 트렁크에서 실행 플레이북만 다시 읽고, 그것에 대해 운영을 감사해 표류를 그 tick에서 고치고, 모든 활성 레인을 부수 효과로만 진행을 판단해 조사한 뒤 막힌 레인은 내려놓고 대체를 즉시 배치합니다. 그다음 이전 상태 메시지가 보고하지 않은 추적된 변경(열린 PR, 코드 준비 헤드, 열리거나 닫힌 라운드, 판정, 병합, 막힌 에이전트와 취한 조치, 더해지거나 풀린 막힘, 운영자만 할 수 있는 결정)이 있을 때만 운영자에게 채팅으로 짧은 상태를 게시합니다. 그런 변경마다 이름을 붙이고 그 밖은 적지 않으며, 표나 병합 목록이나 그대로인 막힘을 되풀이하지 않습니다. 감사가 그런 변경을 찾지 못하면 응답 텍스트 없이 턴을 끝냅니다. 어느 쪽이든 그 tick의 행을 결정 기록에 남기고, 행은 보고한 항목 또는 없음을 이름 붙입니다.

### 응답

계획서 경로, 의존성과 리뷰 관문 집합이 있는 PR id들, 프로토타입이 증명한 것과 증명되지 않은 것, 검사 스크립트의 출력.

### 보조 자료: check-plan.mjs

`node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`는 이 계획서 형식을 검사합니다. 종료 코드는 인자가 없으면 2(stderr에 사용법), 문제가 있으면 1, 깨끗하면 0입니다. 출력은 stdout에 PR 절마다 요약 한 줄과 `<n> PR sections, <m> problems`, stderr에 문제마다 `file:line: message` 한 줄입니다. 검사 내용은 다음과 같습니다.

- **문체(코드가 아닌 줄).** 긴 줄표(en dash, em dash), 곡선 따옴표, 문장 중간 콜론(`: ` 뒤에 공백이 아닌 글자)을 보고합니다. 인라인 코드, 이미지, 링크 대상은 먼저 벗깁니다. 인라인 코드는 같은 길이의 열림과 닫힘 백틱만 벗깁니다. 펜스 코드 블록(`` ``` `` 또는 `~~~`, CommonMark 열림/닫힘) 안의 줄은 문체 검사를 건너뜁니다. 백틱 세 개로 시작하는 모든 줄을 토글하지 않고, 정보 줄에 백틱이 있는 열림은 펜스로 보지 않습니다.
- **최상위 구조.** H1 제목이 있어야 하고, H1과 첫 `## How to read this` 사이에 비어 있지 않은 줄 10개 미만, `## How to read this`(필수 문구 포함: "One box is one unit of work", "names the evidence", "Check a box only when its evidence exists", `playbooks/`, 그리고 검증 규칙 문장), `## Program checklist`, PR 절 하나 이상, `## Close the program`.
- **Program checklist.** `###` 제목이 `Arm the program`, `Spawn owners`, `PR mechanics`, `Verdict and merge`, `Boot recipe`로 이 순서로 시작해야 하고, 본문에 `git show origin/main:`, `/loop 1h`, `status message`가 글자 그대로 들어 있어야 합니다.
- **PR 절.** 위의 아홉 개 굵은 하위 블록이 정확히 이 순서로 있어야 합니다. `Depends on.`은 무언가를 밝혀야 하고, `Files.`, `Build.`, `You see.`, `Verify, unit.`, `Merge.`에는 체크박스가 하나 이상 있어야 합니다. 세 `Verify` 블록은 검증 규칙 문장으로 시작해야 합니다. `Verify, live.`는 "Ten lanes on `<model>` at the PR head"와 채워진 모델, 1에서 10까지 번호가 붙은 레인(`Lane N. `)이 필요하고 레인마다 ``Save `<file>` ``과 `Pass when`이 있어야 합니다. `Verify, perf.`의 상자는 정확히 `Metric.`, `Probe.`, `Baseline.`, `Rule.` 순서입니다. `Review gate.`는 `None.`으로 시작하고 상자가 없거나, 아니면 상자가 하나 이상 있고 `screenshot`, `video`, `operator`를 담아야 합니다.
- **Close 뒤.** `## Appendix...` 절만 허용되고 그중 하나에 "Prototype evidence"가 있어야 합니다.

### 함정과 주의점

- 계획서만 쓰고 구현하지 않습니다. 실행은 운영자의 명시적 승인 뒤입니다.
- 테스트만으로 검증되었다고 하지 않습니다. 단위, 라이브, 성능 상자가 모두 필요합니다.
- 서로 다른 시나리오 사이의 성능 비율을 주장하지 않습니다.
- `check-plan.mjs`가 출력하는 모든 줄을 고칩니다.

### 흐름도

```flow Multi-phase or multi-PR plan 플레이북의 흐름
start 단계나 PR 여럿에 걸친 일
step 1. 계획이 필요한가
  stop 뻔한 변경 | 그렇게 말하고 멈춤
step 2. 열린 질문은 프로토타입으로
  alt 제품이나 취향의 결정 | 옵션과 함께 운영자에게 물음
step 3. 서브에이전트로 탐색
step 4. 골격을 계획 파일에 채움
step 5. technical-writing 후 unslop
step 6. check-plan.mjs 실행
step 7. 계획 경로와 스크립트 출력을 넘기고 멈춤
end 운영자의 명시적인 go 이후에 실행이 시작됨
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 건너뛴다는 말 하나, 또는 계획 작성 시작 |
| 2 | 부록 A용 브랜치, SHA, 스크린숏 |
| 3 | 서브에이전트마다 파일 포인터, 관례, 테스트 명령, 진입점 |
| 4 | 계획 파일. 프로그램 체크리스트와 PR마다 하나의 절, 닫는 절, 부록 A~D(프로토타입 증거, 기각한 대안, 위험, 링크와 읽을거리) |
| 5 | `/technical-writing`과 `/unslop`을 거친 본문 |
| 6 | `check-plan.mjs`의 출력(PR 절마다 상자 수 요약과 문제 개수) |
| 7 | 계획 경로와 스크립트 출력 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "인증을 세션 쿠키에서 토큰으로 옮기는 일을 PR 다섯 개로 쪼개서 계획서로 만들어 줘. 구현은 하지 마. 병합은 내가 직접 할게."
>
> 1. 한두 파일짜리가 아니므로 계획을 씁니다.
> 2. "토큰 갱신을 클라이언트에서 할 것인가"는 관찰로 풀리는 질문이므로 Prototype 플레이북으로 확인하고, 그 브랜치와 SHA를 부록 A에 남깁니다.
> 3. 서브에이전트를 시켜 인증 관련 파일 포인터, 테스트 명령, 진입점을 모읍니다.
> 4. 골격을 채워 PR마다 절 하나(의존, 파일, 빌드, 관찰 결과, 단위/라이브/성능 검증, 리뷰 관문, 병합)를 씁니다. 상호작용을 바꾸는 PR은 리뷰 관문이 걸립니다. 운영자가 PR을 랜딩하므로 실행 플레이북으로 `autopilot-stack`을 지목합니다.
> 5. `/technical-writing`, `/unslop`을 적용합니다.
> 6. `check-plan.mjs`가 출력한 줄을 모두 고칩니다.
> 7. 계획 경로와 출력을 넘기고 멈춥니다. 실행은 사용자의 명시적인 go 뒤에 시작됩니다.

### 실패, 중단, 모호할 때

- **계획이 필요 없을 때.** 파일 한두 개에 접근이 뻔하면 계획을 건너뛰고 그렇게 말한 뒤 멈춥니다.
- **열린 질문이 있을 때.** 프로토타입으로 풀 수 있는 것은 먼저 프로토타입으로 풉니다. 어떤 실행으로도 풀 수 없는 제품이나 취향의 결정에만 운영자에게 묻고, 옵션을 함께 줍니다(`never-block-on-the-human`).
- **검사 스크립트가 문제를 출력할 때.** 출력된 모든 줄을 고칩니다. 종료 코드가 0이 아니면 문제가 남은 것입니다.
- **검증 규칙.** 테스트만으로는 검증이 아닙니다. PR은 단위, 라이브, 성능 상자가 모두 체크되어야 검증된 것입니다. 라이브 상자는 필수입니다. 트렁크에 기능이 없으면 그 사실을 기록하고, 차이가 더하는 동작과 사용자가 기다리는 최종 상태를 게이트합니다.
- **표면에 control 스킬이 없을 때.** 부록 C의 위험으로 올리되, 라이브 상자는 각 레인이 어떻게 구동하는지를 여전히 적습니다.
- **실행.** 운영자의 명시적인 go가 있어야 시작합니다. 이 플레이북은 구현하지 않습니다.

## Orchestrate {#playbook-orchestrate}

원문: {{src:skills/poteto-mode/playbooks/orchestrate.md}} {{src:docs/guide/07-overnight.md}}

> 프로그램을 맡고 코드는 맡지 않습니다. 일마다 어느 에이전트가 할지 정하고, 각 에이전트가 만든 것을 확인합니다.

### 언제 쓰는가

조정자 채팅 하나에 맡기는 상시 프로젝트입니다. 며칠에 걸치고, 스택된 PR이 많고, 서브에이전트가 수십에서 수백이며, 사람의 턴은 적습니다("run this whole project", "own this migration until it lands"). 하나의 작업을 술어까지 몰고 가는 것은 Autonomous run이고, 맞춤 워크플로가 필요한 야심찬 한 번의 실행은 `figure-it-out`입니다. 에이전트 하나가 세션 예산 안에 끝낼 수 있는 일은 프로그램이 아닙니다. 안내서의 예입니다.

```text
/poteto-mode 스토어 마이그레이션을 orchestrate해 줘. 모든 패키지가 변환되고 병합될 때까지 맡아. 하루 두 번 확인할게.
```

### 동작 방식

조정자(이 채팅)는 자기 도구로 프로그램을 돌립니다. 작업자는 `Task`로 띄웁니다. 프로그램의 상태는 Project tracker(`notes.md`)와 Project store에 둡니다. 하네스에 PR과 CI 이벤트 구독이 있으면 그것으로 PR마다 지켜봅니다. 스크립트를 부르지 않고, 폴링 루프를 돌리지 않고, 에이전트 사이에 메시지나 상태를 대신 전하지 않습니다.

#### 배치

- **PR마다 소유자 하나.** 소유자는 그 PR 브랜치의 유일한 작성자이고 PR을 빌드에서 병합까지 몰고 갑니다. 그 브랜치를 푸시하고, 리베이스하고, 재지정하는 것은 소유자뿐입니다. 베이스 PR을 닫거나 재지정하면 그 위의 모든 PR이 고아가 되므로, 소유자는 조정자가 정할 때만 그렇게 합니다. 조정자는 코드를 쓰거나 고치지 않습니다. 충돌이 있는 병합, 사슬 리베이스, 수정은 소유자에게 갑니다.
- **독립된 작업마다 새 작업자 하나.** 킥오프는 작업자를 띄울 때 주는 첫 지시이고, 작업자에게 필요한 모든 것을 싣습니다. 작업이 의존하는 상위 보고서는 전문을 붙여 넣습니다. 작업자는 형제를 볼 수 없기 때문입니다. 작업이 이 머신을 필요로 하지 않는 한 새 클라우드 VM(`environment: "cloud"`)에서 돌립니다. 이 머신이 필요한 경우는 cursor-team-kit의 `control-ui`나 `control-cli` 런타임 검사, 로컬 대화 기록, 시뮬레이터, 여기에만 있는 인증입니다. 서브에이전트마다 그 일에 맞는 추론 강도와 일반 속도 또는 fast를 고릅니다. Subagents 절을 따릅니다.
- **하위 조정자는 한 영역에 병렬 작업자가 많을 때만 둡니다.** 하위 조정자는 그 영역의 작업자와 킥오프를 소유하고, 조정자에게 작업자의 원시 보고가 아니라 집계 하나를 보냅니다. 깊이는 셋에서 멈춥니다. 조정자, 하위 조정자, 작업자입니다. 조정자마다 작업자를 열 개쯤 진행 중으로 두고, 배치 전체를 기다리지 않고 하나가 끝날 때마다 다음 것을 띄웁니다.
- **새 일에 작업자가 쌓은 상태가 필요하면 포크합니다.** 그 작업자의 체크아웃, 커밋되지 않은 변경, 돌고 있는 프로세스 같은 것입니다. 작업자에게 메시지를 보내는 것은 같은 일의 후속일 때뿐입니다. 상태를 확인하려고 메시지를 보내지 않습니다. 메시지는 놀고 있는 에이전트를 다시 시작하기 때문입니다.
- **PR마다 작성자가 아닌 검증자를 둡니다.** 검증자는 다른 모델 계열에서 돕니다. 소유자는 현재 헤드에서 그 검증자가 통과를 냈을 때만 병합합니다.
- **단위 하나로 시작합니다.** 팬아웃하기 전에 단위 하나를 킥오프, 소유자, 검증자, 병합까지 통과시킵니다. 그래야 킥오프의 결함이 에이전트 쉰 개가 아니라 하나의 비용으로 끝납니다. 값싸고 거의 같은 단위들에서는 첫 단위가 그 시험입니다.

#### 감독

- **킥오프마다 일이 끝났음을 증명할 증거를 이름 붙입니다.** 명령과 그 기대 출력, control 스킬 검사, 산출물 같은 것입니다. 목표, 작업자가 쓸 수 있는 경로와 쓸 수 없는 경로, 하면 안 되는 행동도 이름 붙입니다. 증거를 이름 붙일 수 없으면 그 단위는 아직 범위가 정해지지 않은 것입니다.
- **작업자의 요약만이 아니라 diff나 산출물을 읽습니다.** 초록 CI는 판정의 입력이지 판정이 아닙니다. 동작을 바꾸는 일에는 타입 검사보다 많은 것이 필요합니다. 판정은 헤드 SHA 하나를 덮으므로 새 푸시에는 새 판정이 필요합니다. 하위 조정자의 작업자가 도는 동안 그 하위 조정자의 킥오프를 표본으로 읽고, 하나가 실패하면 그 하위 조정자의 지시를 고칩니다.
- **범위에서 벗어나거나 요청보다 커진 일은 돌려보냅니다.** 프로그램을 막는 수정만 남기고 나머지는 후속으로 보관합니다.
- **PR을 보고하기 전에 살아 있는 상태를 확인합니다.** 작업자의 마지막 보고가 아니라 `gh pr view`와 `gh pr checks`, 또는 쓰는 포지의 같은 명령으로 봅니다. 띄운 작업자는 모두 끝남, 교체됨, 다른 작업자의 범위로 흡수됨 중 하나로 정산합니다.
- **정체하거나 같은 자리를 맴도는 작업자는 멈추거나 교체합니다.** 상태 글이 아니라 푸시와 PR 활동으로 판단합니다. 원인에 따라 재시도합니다. 컨텍스트나 메모리 한계 뒤에는 더 작은 범위로, 연결이 끊긴 뒤에는 같은 킥오프로, 도구 오류 뒤에는 다른 모델로 다시 띄웁니다. 재시도 두 번 뒤에는 단위를 버리고 그 둘레로 재계획합니다. 멈춘 작업자가 늦게 돌아오면 그 결과를 PR의 현재 상태와 대조하고, 고유한 발견은 새 작업자에게 넘깁니다.
- **사용자에게는 진짜 결정이나 막힘만 묻습니다.** 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 제품이나 취향 판단, 재계획을 견딘 막다른 길 같은 것입니다. 리베이스 절차, 재시도, CI flake, 리뷰 분류, "계속할까요"는 사용자에게 가지 않습니다.

### 응답

목표에 대해 랜딩한 것, PR마다 살아 있는 상태와 판정과 링크, 버린 것과 이유, 사용자를 기다리는 결정.

### 함정과 주의점

- 에이전트 하나가 세션 예산 안에 끝낼 수 있는 일은 프로그램이 아닙니다. Autonomous run으로 갑니다. 안내서는 그런 일이면 플레이북 자체가 밤새 맡기는 계약으로 돌려보낸다고 적습니다.
- 조정자는 코드를 쓰거나 고치지 않습니다. 충돌 병합, 사슬 리베이스, 수정은 소유자에게 맡깁니다.
- 스크립트를 부르지 않고, 폴링 루프를 돌리지 않고, 에이전트 사이에 메시지나 상태를 대신 전하지 않습니다.
- 상태를 확인하려고 작업자에게 메시지를 보내지 않습니다. 메시지는 놀던 에이전트를 다시 시작합니다.
- 초록 CI와 작업자의 요약은 판정이 아닙니다. 판정은 헤드 SHA 하나를 덮습니다.

### 흐름도

이 플레이북은 번호 붙은 단계 대신 Topology와 Supervision 두 묶음으로 되어 있습니다. 아래 그림은 "단위 하나로 시작합니다"가 말하는 순서(킥오프, 소유자, 검증자, 병합, 팬아웃)에 두 묶음의 내용을 배치한 것이고, 원문에 없는 단계는 넣지 않았습니다.

```flow Orchestrate 플레이북의 흐름
start 조정자 채팅 하나에 맡긴 상시 프로젝트
  stop 에이전트 하나가 세션 예산 안에 끝냄 | Autonomous run으로
step 킥오프에 증거, 목표, 경로, 금지 행동
step PR마다 소유자, 독립 작업마다 새 작업자
  alt 한 영역에 작업자가 많음 | 하위 조정자, 깊이는 셋까지
  alt 작업자가 쌓은 상태가 필요함 | 포크
step 작성자가 아닌 검증자, 다른 모델 계열
step diff와 PR의 살아 있는 상태를 읽음
  alt 범위를 벗어남 | 돌려보내고 나머지는 후속으로
  alt 정체하거나 맴돎 | 원인별 재시도, 두 번 뒤 단위를 버림
  stop 진짜 결정이나 막힘 | 사용자에게 물음
step 현재 헤드의 통과로 소유자가 병합
  back 2 | 첫 단위가 통과하면 팬아웃
end 응답
```

### 단계별 산출물

| 규칙 | 산출물 |
| --- | --- |
| PR마다 소유자 하나 | PR마다 그 브랜치의 유일한 작성자 |
| 독립된 작업마다 새 작업자 | 필요한 것과 상위 보고서 전문을 실은 킥오프, 기본은 새 클라우드 VM의 작업자 |
| 하위 조정자 | 영역마다 조정자에게 가는 집계 하나 |
| 포크 | 작업자의 체크아웃, 미커밋 변경, 프로세스를 이어받은 새 일 |
| 작성자가 아닌 검증자 | 현재 헤드에서 다른 모델 계열이 낸 판정 |
| 단위 하나로 시작 | 킥오프, 소유자, 검증자, 병합을 통과한 첫 단위 |
| 킥오프의 증거 | 명령과 기대 출력, control 스킬 검사, 또는 산출물. 목표, 쓸 수 있는 경로와 없는 경로, 금지 행동 |
| diff나 산출물 읽기 | 헤드 SHA 하나에 대한 판정, 하위 조정자 킥오프의 표본 검토 |
| 범위 이탈 | 돌려보낸 일과 보관한 후속 |
| 살아 있는 상태 | `gh pr view`와 `gh pr checks`의 결과, 끝남, 교체됨, 흡수됨으로 정산한 작업자 |
| 정체와 맴돎 | 원인별 재시도, 또는 두 번 뒤 버린 단위와 재계획 |
| 사용자에게 묻기 | 진짜 결정이나 막힘만 담은 질문 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "조직 전체의 API 호출 120곳을 새 클라이언트로 옮기는 프로젝트를 맡아. 내가 하루 두 번 확인할게."
>
> 1. 에이전트 하나가 세션 예산 안에 끝낼 수 없는 규모이므로 이 플레이북이 맞습니다. 프로그램의 상태는 Project tracker(`notes.md`)와 Project store에 둡니다.
> 2. 호출 지점 한 곳을 첫 단위로 골라 킥오프를 씁니다. 목표, 쓸 수 있는 경로와 없는 경로, 금지 행동, 그리고 끝났음을 증명할 증거로 테스트 명령과 기대 출력을 적습니다.
> 3. 소유자 하나가 PR을 열고, 다른 모델 계열의 검증자가 현재 헤드에서 통과를 내면 소유자가 병합합니다. 거의 같은 값싼 단위들이므로 이 첫 단위가 킥오프의 시험입니다.
> 4. 첫 단위가 통과하면 팬아웃합니다. 호출 지점이 많은 영역에는 하위 조정자를 두고, 조정자마다 작업자를 열 개쯤 진행 중으로 두며 하나가 끝날 때마다 다음 것을 띄웁니다. 작업자는 기본으로 새 클라우드 VM에서 돕니다.
> 5. 작업자의 요약 대신 diff를 읽고, PR을 보고하기 전에 `gh pr view`와 `gh pr checks`로 살아 있는 상태를 봅니다. 범위 밖 리팩터를 섞은 PR은 돌려보내고 그 리팩터는 후속으로 보관합니다.
> 6. 두 번 재시도해도 정체하는 단위는 버리고 그 둘레로 재계획합니다. 사용자에게는 되돌릴 수 없는 행동이나 실험으로 풀 수 없는 결정만 올립니다.
> 7. 응답에는 목표에 대해 랜딩한 것, PR마다 살아 있는 상태와 판정, 버린 것과 이유, 결정을 기다리는 것을 적습니다.

### 실패, 중단, 모호할 때

- **작업자가 정체하거나 맴돌 때.** 상태 글이 아니라 푸시와 PR 활동으로 판단해 멈추거나 교체합니다. 컨텍스트나 메모리 한계면 더 작은 범위로, 연결이 끊겼으면 같은 킥오프로, 도구 오류면 다른 모델로 재시도합니다. 두 번 재시도해도 안 되면 단위를 버리고 그 둘레로 재계획합니다.
- **멈춘 작업자가 늦게 돌아올 때.** 그 결과를 PR의 현재 상태와 대조하고, 고유한 발견은 새 작업자에게 넘깁니다.
- **작업자의 상태가 궁금할 때.** 메시지를 보내지 않습니다. 메시지는 놀던 에이전트를 다시 시작합니다. 푸시와 PR 활동, `gh pr view`와 `gh pr checks`로 봅니다.
- **킥오프에 증거를 적을 수 없을 때.** 그 단위는 아직 범위가 정해지지 않았습니다.
- **일이 범위를 벗어났을 때.** 돌려보냅니다. 프로그램을 막는 수정만 남기고 나머지는 후속으로 보관합니다.
- **하위 조정자의 킥오프가 실패할 때.** 그 하위 조정자의 지시를 고칩니다.
- **사람에게 올리는 것.** 되돌릴 수 없는 행동, 어떤 실험으로도 풀 수 없는 제품이나 취향 판단, 재계획을 견딘 막다른 길입니다. 리베이스 절차, 재시도, CI flake, 리뷰 분류, "계속할까요"는 올리지 않습니다.

### 호출하는 스킬과 스크립트

| 이름 | 종류 | 부르는 곳 |
| --- | --- | --- |

| `gh pr view`, `gh pr checks` | 명령줄 | 보고 전 PR의 살아 있는 상태. 다른 포지면 그 포지의 같은 명령 |

## Autopilot-full {#playbook-autopilot-full}

원문: {{src:skills/poteto-mode/playbooks/autopilot-full.md}} {{src:docs/guide/07-overnight.md}}

> 루트는 판정을 소유하고 PR은 소유하지 않습니다. PR마다 소유자 하나가 빌드에서 병합까지 몰고 가고, 코드를 쓰지 않은 루트의 swarm이 착륙하는 코드를 증명하기 전에는 아무것도 병합되지 않습니다.

### 언제 쓰는가

"autopilot this queue", "full autopilot", PR마다 소유자 하나의 프로그램입니다. 독립된 PR 대기열을 완전 자율로 병합까지 돌립니다. 각 PR의 소유자가 병합까지 전체 수명 주기를 몰고 가고, 루트는 소유자가 병합하기 전에 PR마다 swarm으로 검증하며 그 밖에는 카운터사인과 감사만 합니다. 며칠에 걸쳐 조정자 채팅 하나가 운영하는 상시 프로그램은 Orchestrate입니다. 안내서의 예입니다.

```text
/poteto-mode 이 대기열에 full autopilot 해 줘. 각 항목은 독립적이야. 아침까지 전부 병합해 줘.
```

판정은 패치 하나를 덮고, 초록 CI는 헤드 하나를 덮습니다. 4단계는 전체 swarm을 한 번 돌리고, 큰 변경일 때만 다시 돕니다. `playbooks/shipping.md`의 patch-id 규칙(rule)이 레인 결과를 살릴 수 있고, 새 헤드마다 그 헤드의 초록 CI가 필요합니다.

### 동작 방식

1. **운영자의 관문이 먼저입니다.** 부여는 대기열의 항목만 덮습니다. 운영자가 자기 것이라고 이름 붙인 항목과 대기열 밖의 PR은 merge-ready에서 멈춥니다. 계획을 진술하라는 요청은 go가 아닙니다.
2. **PR마다 소유자 하나를 띄우고, 대체가 찾을 수 있는 곳에 일을 둡니다.** 프로그램 전체에서 포지를 한 번 정합니다. GitHub CLI(`gh`)가 기본입니다. `command -v origin`이 성공하고 Origin이 저장소를 인식하면 모든 PR 작업에 `origin pr`을 씁니다. 아니면 `gh`에 머물고 그 대체를 기록합니다. Graphite(`gt`)는 요구하지 않습니다. 소유자마다 Cursor 클라우드 에이전트이고, 빌드하고, `playbooks/opening-a-pr.md`대로 PR을 열고, 실제 산출물에서 변경을 증명하고, `playbooks/babysit.md`대로 초록까지 babysit하고, 4단계와 5단계가 통과하면 병합합니다.

   PR을 일찍 열어 CI와 봇이 일과 나란히 돌게 합니다. 슬롭 제거(cursor-team-kit의 `deslop`)와 `/no-comments` 뒤에야 코드가 준비이므로, 전체 swarm은 끝난 코드에서 돕니다. 그다음 현재 트렁크로 리베이스하고 자기 증명 전에 코드 준비 헤드를 보고해, 검증이 패치가 착륙하는 베이스에서 돌게 합니다. 이후의 헤드마다 보고하고, 자기 증명과 CI와 babysit이 끝나면 merge-ready를 보고합니다. 수정 라운드는 트렁크와 충돌하거나, 트렁크가 CI를 깨거나, 같은 파일에 대한 알려진 동시 변경이 트렁크에 들어오지 않는 한 그 베이스에 머뭅니다. 리베이스마다 CI가 다시 시작되기 때문입니다. 코드 준비 푸시 전과, 검증자가 필요한 이후 푸시 전에, 건드린 경로에 대해 저장소의 검사를 커밋된 헤드에서 돌립니다.

   VM이 죽는다고 가정합니다. 시작한 뒤 곧 푸시하고, 시스템 프롬프트에 있는 루트 에이전트 저장소에 [`show-me-your-work`](personal.md#skill-show-me-your-work) 스킬대로 결정 기록을 시작한 뒤, 끝난 단위마다 다음 단위를 시작하기 전에 푸시합니다. 서브에이전트를 띄운 쪽이 그 id와 상태와, 그 종류의 과거 실행에서 온 막힘 기준 실행 시간을 그 저장소에 적어, 부모가 죽어도 루트가 조사할 수 있게 합니다. 강제 푸시는 자기 브랜치만, 마지막으로 푸시했거나 이어받은 SHA에 `--force-with-lease`를 핀하고, 자기가 하지 않은 푸시가 있으면 멈추고 루트에 보고합니다.
3. **소유자를 트렁크에서 진짜 병렬로 돌리고 쌓지 않습니다.** 각 PR이 혼자 착륙하게 합니다.
4. **swarm으로 한 번 검증합니다.** 전체 swarm은 코드 준비 헤드에서 한 번 돕니다. 새 동작, 재설계, 큰 새 diff일 때만 다시 전체 swarm을 돌립니다. 리베이스, 병합 충돌 해결, 작은 수정은 새 헤드에서 검증자 하나만 두고, 문구만 바꾼 변경은 검증자를 두지 않습니다. 코드 준비 SHA에서 [`swarm`](arena-swarm.md#skill-swarm) 스킬대로 독립 검증자를 팬아웃합니다. 관문을 다시 돌리고, 실제 표면에서 control 스킬(cursor-team-kit의 `control-ui`나 `control-cli`)이나 이름 붙인 드라이버로 핵심 동작을 라이브로 증명하고, diff를 감사합니다. 라이브 레인이 없거나 merge-ready 보고의 영수증을 감사하기 전의 판정은 깨끗하지 않습니다. 어떤 레인도 확인하지 않은 주장을 믿지 않기 때문입니다.

   PR을 막는 것은 보여 줄 수 있는 문제뿐입니다. 보여 주는 증거는 헤드에서 실패하는 실행이나 PR이 틀리게 만든 문서 줄입니다. PR의 베이스가 이미 가진 문제는, 그 베이스가 트렁크든 스택에서 그 PR 아래의 PR이든, PR이 그것을 복사하거나 새로 닿지 않는 한 PR을 막지 않습니다. 막는 것은 사용자가 겪을 버그, 실패한 관문, 틀린 채 나가는 문서뿐이고, 나머지는 모두 후속으로 갑니다.
5. **소유자는 검증한 것만, 착륙하는 트렁크에서 시험한 것만 병합합니다.** CI 초록만으로 병합을 승인하지 않습니다. swarm의 레인이 시작된 뒤, 병합 준비는 현재 트렁크로 리베이스하고 새 헤드를 보고한 뒤 초록 CI를 기다립니다.

   병합 직전에 트렁크를 가져와, 트렁크의 변경이 패치에 영향을 줄 수 있는지 묻습니다. 트렁크가 움직일 때마다 리베이스하면 끝나지 않기 때문입니다. 착륙할 코드가 한 번도 시험되지 않았을 때, 충돌이거나 양쪽이 바꾼 파일이거나 PR에 어떤 체크가 도는지가 바뀌었을 때는 리베이스하고 CI를 기다립니다. 양쪽이 바꾼 lockfile은, 동결된 설치가 병합 결과에서 통과하고 PR이 바꾸는 패키지가 헤드에서와 같이 그 결과에서 해석되면 리베이스가 필요 없습니다. 그 설치가 착륙할 lockfile을 시험하기 때문이고, 설치가 실패하면 리베이스가 고쳐야 합니다. 트렁크가 패치의 호출자나 패치가 의존하는 것(호출하는 코드나 의존성 버전)을 바꿨으면, 병합 결과에서 패치의 검사를 돌리고 통과하면 병합합니다. 아니면 병합합니다. 병합 준비 뒤로 트렁크가 세 번째 리베이스를 강제하면 멈추고 루트에 보고합니다. 루트가 충돌하는 일을 순서 짓습니다.
6. **루트 계층을 돌립니다.** 예산을 올리거나 허용 목록에 항목을 더하는 것처럼 관문을 느슨하게 하는 것은 검증자의 증명과 루트의 새 카운터사인이 필요합니다. 초록을 원하는 쪽이 소유자이기 때문입니다. 승인을 덮는 부여 아래에서는 그 카운터사인이 승인이고, 소유자의 기록은 레인이 확인할 그 카운터사인을 가리킵니다. 꺼지거나 부드럽게 실패한 체크는 항상 밖으로 나갑니다. 모든 경우를 지키지 못하게 되기 때문입니다. 포지가 강제하는 승인은 주거나 우회하지 않습니다. 어떤 카운터사인도 그것을 덮지 않기 때문입니다.

   운영자의 go에서, 위임된 일이 남지 않을 때까지 감사하도록 `/loop 1h`를 무장합니다. 긴 실행은 표류하고 에이전트는 조용히 멈추기 때문입니다. tick마다 트렁크에서 이 플레이북을 다시 읽고, 보고하지 않은 헤드나 기록하지 않은 에이전트처럼 표류를 그 소유자가 적게 해서 고칩니다. 표류는 정체가 아니라 기록의 빈틈이기 때문입니다. 잎 레인까지 모든 에이전트를 조사하고, 부수 효과로만 판단합니다. 상태 글과 요약은 막힌 자식을 숨길 수 있기 때문입니다. 에이전트는 오류를 내거나, 턴을 시작하지 못하거나, 막힘 기준 실행 시간을 넘기고도 새것이 없으면 막힌 것이고, 첫 tick까지 푸시도 기록 행도 없는 소유자도 그렇습니다. 루트나 운영자를 기다리는 것은 막힌 것이 아니므로 답합니다. 막힌 에이전트는 정지가 닿기를 기다리지 않고 즉시 교체합니다. 운영자에게 무언가 바뀐 tick은 [`ketchup`](teach-recall.md#skill-ketchup) 스킬대로 따라잡히고, 바뀐 것이 없는 tick은 조용합니다.
7. **운영자의 정지에서 즉시 서 있습니다.** 보류는 모든 소유자에게 쓰기 금지 명령으로 닿습니다. 각자 어디에 서 있는지를 보고하고, 운영자가 풀어 줄 때까지 브리프를 붙듭니다.

### 응답

[`ketchup`](teach-recall.md#skill-ketchup) 스킬대로 운영자를 따라잡힙니다. 각 PR의 상태와 판정, 병합된 것, 카운터사인과 이유, 열린 운영자 관문, 보관한 후속을 담고, PR과 기록마다 링크를 둡니다.

### 함정과 주의점

- 병합 전에 루트의 깨끗한 판정이 필요합니다. 소유자의 자기 판정만으로 병합하지 않습니다.
- 라이브 레인이 없거나 영수증을 감사하기 전의 판정은 깨끗하지 않습니다.
- 전체 swarm은 코드 준비 헤드에서 한 번입니다. 리베이스와 작은 수정은 검증자 하나이고, 문구만 바꾼 변경은 검증자가 없습니다.
- 보여 줄 수 없는 문제로 PR을 막지 않습니다. 베이스에 이미 있던 문제도 PR이 복사하거나 새로 닿지 않으면 후속으로 보냅니다.
- CI 초록만으로 병합하지 않습니다. 착륙할 코드가 시험되지 않았으면 리베이스하고, 세 번째 리베이스는 멈춥니다.
- 강제 푸시는 자기 브랜치만, 마지막 푸시 SHA에 `--force-with-lease`를 핀합니다.
- 운영자가 이름 붙인 항목은 병합하지 않고 merge-ready에서 멈춥니다.

### 흐름도

```flow Autopilot-full 플레이북의 흐름
start 독립된 PR 대기열을 병합까지
step 1. 운영자 관문이 먼저
step 2. PR마다 소유자 하나, 찾을 수 있는 기록
step 3. 트렁크에서 병렬, 쌓지 않음
step 4. 코드 준비에서 swarm 한 번
  alt 큰 변경 | 다시 전체 swarm
  alt 리베이스나 작은 수정 | 검증자 하나
  alt 문구만 바뀜 | 검증자 없음
  alt 보여 줄 수 없거나 베이스에 있던 문제 | 막지 않고 후속으로
step 5. 검증한 것만, 착륙 트렁크에서 시험한 것만 병합
  stop 세 번째 리베이스 | 멈추고 루트에 보고
  stop 운영자가 지명한 항목 | 병합 준비에서 멈추고 클릭을 기다림
step 6. 루트 층, 바뀐 tick은 ketchup
step 7. 운영자의 중지
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | 운영자 몫과 대기열 밖 PR 목록. 진술 요청이면 진술 후 대기 |
| 2 | PR마다 소유자, 루트 저장소의 결정 기록, 이른 ready PR, 끝난 단위마다의 푸시, 코드 준비 head SHA, `--force-with-lease`로 핀한 자기 브랜치 |
| 3 | 트렁크에서 독립적으로 도는 소유자들 |
| 4 | 코드 준비 헤드의 전체 swarm 판정. 작은 후속은 검증자 하나의 판정. 막지 않는 발견은 후속 목록 |
| 5 | 병합 준비 head SHA, 병합 결과에서 돌린 검사, 병합된 PR 또는 세 번째 리베이스에서 멈춘 보고 |
| 6 | 감사 tick마다의 조정, 교체된 레인, 카운터사인, 바뀐 tick의 ketchup 응답 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "독립된 PR 여섯 개 대기열, 풀 오토파일럿으로 병합까지. PR 5는 내가 직접 클릭할게."
>
> 1. PR 5를 운영자 몫으로 표시합니다. 계획을 진술하라는 요청은 없으므로 요청의 실행 지시가 go입니다.
> 2. PR마다 소유자를 띄웁니다. 각 소유자는 곧 푸시하고 루트 저장소에 결정 기록을 열고 ready PR을 엽니다. 끝난 단위마다 다음 단위 전에 푸시합니다. 강제 푸시는 자기 브랜치만, 마지막 푸시 SHA에 `--force-with-lease`를 핀합니다.
> 3. PR은 서로 독립이라 트렁크에서 병렬로 돕니다. 쌓지 않습니다.
> 4. 소유자가 슬롭 제거와 `/no-comments` 뒤 코드 준비 헤드를 보고하면 루트가 전체 swarm을 한 번 돌립니다. PR 2의 라이브 레인이 헤드에서 실패하는 실행을 보여 주므로 PR 2를 막습니다. PR 4의 감사 레인이 지적한 문제는 트렁크에 이미 있고 PR 4가 복사하거나 새로 닿지 않으므로 막지 않고 후속으로 보관합니다. 작은 수정은 새 헤드에서 검증자 하나만 두고, 주석 문구만 고친 새 헤드에는 검증자를 두지 않습니다.
> 5. 깨끗한 판정이 나온 PR의 소유자는 트렁크로 리베이스하고 초록 CI를 기다립니다. 병합 직전 트렁크가 패치에 영향을 줄 수 있는지만 묻고, 아니면 병합합니다. 세 번째 리베이스가 필요하면 멈추고 루트에 보고합니다. PR 5는 merge-ready에서 사용자의 클릭을 기다립니다.
> 6. 운영자의 go에서 `/loop 1h`를 무장합니다. tick마다 트렁크에서 이 플레이북을 다시 읽고 부수 효과로만 판단합니다. 바뀐 것이 있는 tick은 `/ketchup`으로 따라잡고, 없으면 조용합니다.
> 7. 사용자가 멈추라고 하면 모든 소유자에게 쓰기 금지 명령이 즉시 갑니다.

### 실패, 중단, 모호할 때

- **운영자의 중지.** 보류는 모든 소유자에게 즉시 쓰기 금지 명령으로 닿습니다. 각자 어디에 서 있는지를 보고하고, 운영자가 풀 때까지 브리프를 붙듭니다.
- **계획을 진술하라는 요청.** go가 아닙니다. 진술하고 멈춥니다.
- **발견이 PR을 막는지 애매할 때.** 헤드에서 실패하는 실행이나 PR이 틀리게 만든 문서 줄로 보여 줄 수 있어야 막습니다. 베이스에 이미 있던 문제는 PR이 복사하거나 새로 닿을 때만 막습니다. 사용자가 겪을 버그, 실패한 관문, 틀린 채 나가는 문서가 아니면 후속으로 보냅니다.
- **수정 라운드 중에 트렁크가 움직일 때.** 충돌, 트렁크가 깬 CI, 같은 파일에 대한 알려진 동시 변경이 아니면 그 베이스에 머뭅니다.
- **병합 직전에 트렁크가 움직일 때.** 착륙할 코드가 시험되지 않았으면 리베이스하고 CI를 기다립니다. 충돌, 양쪽이 바꾼 파일, 어떤 체크가 도는지의 변화가 그런 경우입니다. lockfile만 양쪽이 바뀌었고 동결된 설치가 병합 결과에서 통과하면 리베이스하지 않습니다. 트렁크가 패치의 호출자나 의존성을 바꿨으면 병합 결과에서 패치의 검사를 돌립니다. 세 번째 리베이스는 멈추고 루트에 보고합니다.
- **레인이 오류를 내거나 막힘 기준 실행 시간을 넘기고도 새것이 없을 때.** 막힌 것으로 보고 즉시 교체합니다. 정지가 닿기를 기다리지 않습니다. 루트나 운영자를 기다리는 것은 막힌 것이 아닙니다.
- **관문을 느슨하게 할 때.** 검증자의 증명 뒤에만 루트가 새 카운터사인을 줍니다. 꺼지거나 부드럽게 실패한 체크는 항상 밖으로 나갑니다. 포지가 강제하는 승인은 주거나 우회하지 않습니다.
- **운영자가 지명한 항목과 대기열 밖 PR.** merge-ready에서 멈춥니다.
- **쌓기.** 쌓지 않습니다. 각 PR이 트렁크에서 혼자 착륙합니다.
- **tick의 끝.** 위임된 일이 하나도 남지 않을 때만 끝납니다. 바뀐 tick은 ketchup으로 따라잡고, 바뀌지 않은 tick은 응답 없이 끝납니다.

## Autopilot-stack {#playbook-autopilot-stack}

원문: {{src:skills/poteto-mode/playbooks/autopilot-stack.md}} {{src:docs/guide/07-overnight.md}}

> Autopilot-full 플레이북을 돌리되 병합하지 않습니다.

### 언제 쓰는가

Autopilot-full에서 병합을 뺀 것입니다. PR 대기열을 완전 자율로 빌드하고 검증한 뒤, 랜딩은 운영자에게 넘깁니다. PR은 그것이 바탕으로 삼는 PR 위에만 쌓습니다. "autopilot-stack", "autopilot, don't merge", "stack them, don't ship", "build the stack, I'll land it" 같은 요청입니다. 안내서는 무엇이든 병합되기 전에 직접 보고 싶을 때 Autopilot-full 대신 이것을 고르라고 합니다. 안내서의 예입니다.

```text
/poteto-mode 이 변경 다섯 개를 autopilot으로 돌려 줘. 병합은 하지 마. 아침에 내가 랜딩할게.
```

### 동작 방식

[Autopilot-full](#playbook-autopilot-full)을 그대로 돌리되 아래 두 가지만 다릅니다.

1. **5단계 대신, 검증된 곳에서 멈춥니다.** PR마다 현재 헤드에서 검증되고 초록이면 멈추고, PR을 운영자에게 넘깁니다. 넘긴 뒤에는 운영자의 go 없이 아무도 푸시하지 않습니다. 루프의 tick 프롬프트마다 이 파일을 이름으로 적어, tick마다 병합하지 않는다는 규칙을 보게 합니다.
2. **PR은 다른 PR 위에 지어질 때만 쌓습니다.** Autopilot-full 3단계의 유일한 예외입니다. 그 PR은 트렁크 대신 다른 PR의 브랜치를 베이스로 둡니다. [Opening a PR](playbooks-pr.md#playbook-opening-a-pr)의 **Size and stacks**를 따릅니다. 2단계의 트렁크 리베이스 대신, PR마다 부모 PR의 브랜치로 리베이스하고 스택의 루트만 트렁크로 리베이스합니다. 아래 PR에 새 헤드가 생기면 그 위의 PR들을 다시 쌓고, 다시 쌓아도 `git patch-id`가 바뀌지 않은 PR은 판정을 유지합니다.

### 응답

Autopilot-full의 응답과 같되, 병합된 것 대신 PR마다 그 판정을 나열합니다.

### 함정과 주의점

- 어떤 PR도 병합하지 않습니다. 현재 헤드에서 검증되고 초록인 곳에서 멈추고 운영자에게 넘깁니다.
- 넘긴 뒤에는 운영자의 go 없이 아무도 푸시하지 않습니다.
- tick 프롬프트마다 이 파일을 이름으로 적습니다. 그래야 tick마다 병합 금지 규칙을 봅니다.
- 쌓는 것은 다른 PR 위에 지어지는 PR뿐입니다. 나머지는 Autopilot-full처럼 트렁크에서 병렬로 돕니다.

### 흐름도

```flow Autopilot-stack 플레이북의 흐름
start PR 대기열을 검증까지, 랜딩은 운영자
step Autopilot-full 1에서 4단계
  alt 2. 다른 PR 위에 지어지는 PR | 부모 PR의 브랜치를 베이스로, 그 브랜치로 리베이스
  alt 아래 PR의 새 헤드 | 위의 PR을 다시 쌓음, patch-id가 같으면 판정 유지
step 1. 5단계 대신 검증된 곳에서 멈춤
  stop 운영자에게 넘김 | 그 뒤로는 운영자의 go 없이 푸시하지 않음
end 응답
```

### 단계별 산출물

| 단계 | 산출물 |
| --- | --- |
| 1 | PR마다 현재 헤드에서 검증되고 초록인 상태, 운영자에게 넘긴 PR, 이 파일을 이름으로 적은 tick 프롬프트 |
| 2 | 부모 PR의 브랜치를 베이스로 둔 PR, 다시 쌓은 PR마다 `git patch-id` 대조 |

### 예시

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 요청: "이 변경 네 개를 autopilot으로 돌려서 검증까지 해 놔. 병합은 하지 마. 내가 리뷰하고 랜딩할게."
>
> 1. Autopilot-full처럼 PR마다 소유자를 띄우고, 코드 준비 헤드에서 swarm으로 검증합니다. 루프의 tick 프롬프트에는 이 파일을 이름으로 적습니다.
> 2. 네 변경 중 셋은 서로 독립이므로 트렁크에서 병렬로 돕니다. 넷째는 둘째 PR이 더하는 API를 쓰므로 둘째 PR의 브랜치를 베이스로 두고 그 브랜치로 리베이스합니다.
> 3. 둘째 PR에 수정이 들어가 새 헤드가 생기면 넷째를 다시 쌓습니다. `git patch-id`가 그대로이므로 넷째의 판정은 유지됩니다.
> 4. 네 PR이 모두 현재 헤드에서 검증되고 초록이면 멈추고 운영자에게 넘깁니다. 병합하지 않습니다. 그 뒤로는 운영자의 go 없이 아무도 푸시하지 않습니다.
> 5. 응답에는 병합된 것 대신 PR마다 판정을 적습니다.

### 실패, 중단, 모호할 때

- **병합할 차례처럼 보일 때.** 이 플레이북은 병합하지 않습니다. 검증되고 초록인 곳에서 멈추고 넘깁니다.
- **넘긴 뒤에 고칠 것이 생겼을 때.** 운영자의 go 없이 아무도 푸시하지 않습니다.
- **PR을 쌓을지 애매할 때.** 다른 PR 위에 지어질 때만 쌓습니다. 나머지는 Autopilot-full 3단계대로 트렁크에서 병렬입니다.
- **아래 PR이 바뀌었을 때.** 위의 PR을 다시 쌓습니다. `git patch-id`가 바뀌지 않은 PR은 판정을 유지합니다. 판정은 패치 하나를 덮으므로 패치가 바뀐 PR은 새 판정이 필요합니다.
- **둘 중 무엇을 쓸지.** Multi-phase plan의 고르는 기준대로, 실행이 병합해도 되면 Autopilot-full이고 운영자가 PR을 랜딩하면 Autopilot-stack입니다.

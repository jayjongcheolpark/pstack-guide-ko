# interrogate: 여러 모델이 diff를 깨뜨린다

## interrogate {#skill-interrogate}

원문: {{src:skills/interrogate/SKILL.md}} {{src:skills/arena/SKILL.md}} {{src:docs/guide/04-design.md}} {{src:docs/guide/10-recipes-and-pitfalls.md}} {{src:README.md}}

> 적대자가 변경이나 설계를 깨뜨리려 시도하고, 실행으로 증명된 발견만 남깁니다. 발견을 보고하고 수정은 적용하지 않습니다.

### 언제 쓰는가

원문의 `description`은 트리거로 "interrogate", "adversarial review", "multi-model review", "challenge this", "stress test this code", "find blind spots", "tear this apart"를 듭니다. 적대자가 변경이나 설계를 깨뜨리려 시도하고, 실행으로 증명된 발견만 살아남습니다. `disable-model-invocation: true`입니다. `poteto-mode`는 논쟁적인 설계에 배포 전 이 스킬을 부르고, Feature 플레이북도 설계가 논쟁적이면 배포 전에 이 스킬을 돌립니다. `architect`는 구현 전에 설계에 적대적 압력이 필요하면 종합된 스케치에 이 스킬을 돌리라고 합니다. README가 이 스킬을 요약하는 문장은 "diff가 있고 서로 다른 모델이 그것을 깨뜨려 보기를 원할 때, 실행으로 증명된 발견만 남기면서"입니다.

안내서가 이 스킬을 설명하는 방식은 이렇습니다. 변경과 그 의도를 설정된 모델의 적대자들에게 주고, 각 적대자는 실제 코드에 대한 실행으로 그것을 깨뜨리려 합니다. 적대자마다 찾는 실패가 다릅니다. 발견은 그 명령을 다시 돌렸을 때 의도를 깨뜨리는 실패가 보일 때만 살아남습니다. 보고는 검증(verification)된 발견을 그것을 찾은 적대자와 함께 모두 적고, 이어서 적대자마다 무엇을 왜 버렸는지 적으며, 아무것도 적용하지 않습니다. 안내서는 Dropped 목록도 읽으라고 하고, 사용자가 판정을 뒤집을 수 있다고 합니다.

### 동작 방식

적대자가 변경이나 설계를 깨뜨리려 시도합니다. 발견은 실행이 증명할 때만 살아남습니다. 스킬은 발견을 보고하고 수정은 적용하지 않습니다. 단계는 Frame, Fan out, Verify, Output 넷입니다.

**Frame. 범위와 의도를 정합니다.** 범위는 사용자가 지정한 것입니다. 지정하지 않으면 베이스 브랜치와 갈라진 지점(merge base)부터 작업 트리까지의 브랜치 diff입니다. 커밋한 변경과 아직 커밋하지 않은 변경이 함께 듭니다. 의도는 [`in-your-own-words`](setup.md#skill-in-your-own-words) 스킬로 밝힙니다. 사용자의 메시지, 커밋, PR 설명에서 의도를 읽어 자기 말로 다시 말합니다. 의도가 불분명하면 사용자에게 묻습니다.

**Fan out. 적대자를 띄웁니다.** [`arena`](arena-swarm.md#skill-arena)의 A단계 3, 4번과 B단계를 돌립니다. A단계 3번은 러너를 고르는 단계입니다. 4번은 후보마다 자기 출력 위치를 주는 단계로, 가능하면 git 워크트리이고 아니면 `/tmp/arena-<slug>/candidate-<n>/`입니다. B단계는 모든 서브에이전트를 한 메시지에 `run_in_background: true`로 띄우고, 출력을 내지 못한 서브에이전트가 있으면 나머지로 진행하고 탈락을 적는 단계입니다. 여기에 네 가지를 바꿉니다.

1. `arena runners` 줄 대신 `~/.cursor/rules/pstack-models.mdc`의 `interrogate reviewers` 줄을 읽습니다. 규칙(rule)이나 그 줄이 없으면 arena A단계 3번대로 `claude-opus-5-5-xhigh`와 `grok-4.7-xhigh-fast`를 하나씩 씁니다. `auto`나 `inherit-parent` 항목은 `model`을 생략해 부모 모델로 돌리고, Task 도구가 거부한 항목의 대체도 arena A단계 3번을 따릅니다. 띄울 때마다 추론 강도와 일반 속도 또는 fast는 [`poteto-mode`](poteto-mode.md#skill-poteto-mode)의 Subagents 절대로 고릅니다.
2. 범위의 커밋하지 않은 변경을 각 워크트리에 복사합니다.
3. 적대자마다 `generalPurpose` 서브에이전트로 띄웁니다.
4. arena의 과업과 근거 대신 범위, 의도, 아래 브리프를 줍니다.

브리프가 적대자에게 요구하는 것은 이렇습니다.

- 이 변경을 깨뜨립니다.
- 발견마다 실제 코드에 대한 실행으로 증명합니다. 실패하는 테스트, 재현 스크립트, 잘못된 동작을 보여 주는 명령 출력 같은 것입니다. 설계나 계획이면 프로토타입을 돌리거나 현재 트리를 실행해 살펴봅니다.
- 재현은 자기 워크트리에 둡니다.
- 발견마다 제목, 정확한 명령, 그 명령이 출력한 것, 의도가 요구하는 출력을 보고합니다.
- 돌리지 않은 것은 뺍니다. 스타일, 이름, 구조, 그리고 앞으로의 변경이 있어야 문제가 되는 위험이 여기에 듭니다.
- 발견이 없는 것도 유효한 결과입니다.

**Verify. 발견을 다시 돌립니다.** 발견마다 그 명령을 다시 돌려 arena F단계대로 검증합니다. F단계는 `prove-it-works` 원칙(principle)에 따라 실제 산출물(artifact)을 직접 확인하는 단계입니다. 출력이 실패를 보여 주고 그 실패가 의도를 깨뜨리면 발견을 남깁니다. 나머지는 버립니다. 근본 원인이 같은 발견은 하나로 합칩니다. arena의 C, D, E단계(교차 심사, 기준안 선택, 이식)는 건너뜁니다. 적대자마다 찾는 실패가 다르므로 판정은 한 적대자의 목록이 아니라 검증된 발견을 모두 담습니다.

**Output. 보고합니다.** 보고는 세 부분입니다.

- **Intent**: Frame에서 다시 말한 의도.
- **Findings**: 검증된 발견마다 명령, 그 출력, 그것이 의도를 어떻게 깨뜨리는지, 그 발견을 찾은 적대자들. 남은 발견이 없으면 "no verified findings"라고 씁니다.
- **Dropped**: 적대자마다 버린 발견의 수와 그 이유.

### 사용 예

안내서의 예입니다.

```text
/interrogate 브랜치 전체를, 회의적으로. 실제 버그나 회귀가 아니면 사소한 지적은 하지 마.
```

레시피는 이렇습니다.

```text
/interrogate 브랜치 전체를 회의적으로. 아직 아무것도 바꾸지 마. 동작의 실제 버그나 회귀가 아니면 사소한 지적은 하지 마.
```

한정어가 실제로 일합니다. "아무것도 바꾸지 마"는 수정을 적용하지 않고, 사소한 지적 규칙은 잡음을 미리 걸러서 검증된 발견이 시간을 쓸 가치가 있게 합니다. 재현은 적대자 워크트리에 둡니다. 안내서는 작고 끝난 변경이 미덥지 않을 때 `/interrogate`만 쓰고, 되돌리기 비싼 논쟁적 설계는 `/architect` 뒤 배포 전에 `/interrogate`를 쓰라고 권합니다. README의 짧은 예는 `/interrogate review this pr.`입니다.

> **예시 (이 책의 저자가 만든 것, 원본에 없음)**
>
> 상황: 브랜치가 결제 웹훅 처리에 멱등 키를 더했고, 작업 트리에는 아직 커밋하지 않은 테스트 수정이 있습니다. `interrogate reviewers` 줄은 기본값 그대로이고, `/interrogate review this pr.`를 칩니다.
>
> 1. Frame. 범위는 베이스 브랜치와 갈라진 지점부터 작업 트리까지이므로 커밋하지 않은 테스트 수정도 듭니다. 의도는 "같은 웹훅이 재시도로 여러 번 와도 주문은 한 번만 만든다"로 다시 말합니다.
> 2. Fan out. `claude-opus-5-5-xhigh`와 `grok-4.7-xhigh-fast` 적대자를 각자의 워크트리에 띄우고, 커밋하지 않은 테스트 수정을 두 워크트리에 복사합니다.
> 3. Verify. 두 적대자가 같은 키로 요청 두 개를 동시에 보내는 재현 스크립트를 따로 썼습니다. 다시 돌린 `node scripts/race-webhook.mjs`가 `orders created: 2`를 찍었고 의도는 `orders created: 1`을 요구하므로 남깁니다. 두 발견은 확인과 삽입 사이의 경쟁이라는 같은 근본 원인이라 하나로 합칩니다. `grok-4.7-xhigh-fast` 적대자의 다른 발견 하나는 다시 돌리자 통과해서 버립니다. `claude-opus-5-5-xhigh` 적대자가 낸 함수 이름 지적은 돌린 명령이 없어서 버립니다.
> 4. Output. Intent에 위 의도를, Findings에 합친 발견 하나(명령, `orders created: 2`, 주문이 두 번 만들어진다는 점, 두 적대자)를, Dropped에 적대자마다 버린 발견 하나와 그 이유를 적습니다. 경쟁은 고치지 않습니다.

### 함정과 주의점

- 수정을 적용하지 않습니다. 발견을 보고하는 것까지입니다.
- 의도가 불분명하면 사용자에게 묻습니다.
- 실행으로 증명하지 않은 발견은 남지 않습니다. 스타일, 이름, 구조, 앞으로의 변경이 있어야 문제가 되는 위험은 브리프가 처음부터 빼라고 합니다. 실행으로 보인 실패라도 의도를 깨뜨리지 않으면 버립니다.
- 한 적대자의 목록을 판정으로 고르지 않습니다. 검증된 발견은 누가 냈든 모두 남깁니다.
- 안내서는 추상 계획에 적대자를 쓰지 말라고 합니다. 이 스킬은 실행이 증명하지 않은 발견을 모두 버리므로 코드가 없는 계획은 깨뜨릴 것이 적습니다. 레시피도 코드가 없는 계획을 적대적으로 리뷰하면 일어나지 않을 위험을 지어낸다고 합니다. 프로토타입으로 질문을 정한 뒤 만들어진 것을 리뷰합니다.
- 안내서가 꼽은 흔한 실수는 모든 리뷰 댓글을 수용하는 것입니다. 봇과 사람은 진짜 발견과 잡음을 한 목록에 올립니다. `/interrogate`는 다시 돌려 증명된 발견만 남기고 무엇을 왜 버렸는지 적으며, 사용자는 어느 쪽으로든 판정을 뒤집을 수 있습니다. 그래서 Dropped 목록도 읽습니다.

### 관련 스킬

[`architect`](architect.md#skill-architect)가 종합된 스케치에 이 스킬을 돌립니다. 팬아웃과 검증은 [`arena`](arena-swarm.md#skill-arena)의 단계를 빌려 씁니다. 의도를 다시 말하는 것은 [`in-your-own-words`](setup.md#skill-in-your-own-words)입니다. 판정과 별개로 PR 댓글을 분류하는 방법은 [Bugbot 분류 기준](playbooks-pr.md#ref-bugbot-triage)에 있습니다.

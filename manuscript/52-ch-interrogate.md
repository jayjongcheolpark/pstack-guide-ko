# interrogate: 여러 모델이 diff를 깨뜨린다

## interrogate {#skill-interrogate}

원문: {{src:skills/interrogate/SKILL.md}} {{src:skills/interrogate/references/reviewer-prompt.md}} {{src:skills/interrogate/references/rubric.md}} {{src:skills/interrogate/references/lead-judgment.md}} {{src:skills/interrogate/references/code-quality-review.md}} {{src:docs/guide/04-design.md}} {{src:docs/guide/10-recipes-and-pitfalls.md}}

> 설정된 모델마다 리뷰어 하나를 띄워 변경을 적대적으로 리뷰하고, 종합한 판정을 냅니다. 변경을 자동으로 적용하지 않습니다.

### 언제 쓰는가

원문의 `description`은 트리거로 "interrogate", "adversarial review", "multi-model review", "challenge this", "stress test this code", "find blind spots", "tear this apart"를 듭니다. 여러 LLM 리뷰어가 독립된 각도에서 변경에 도전합니다. `disable-model-invocation: true`입니다. `poteto-mode`는 논쟁적인 설계에 배포 전 이 스킬을 부르고, Feature 플레이북은 설계가 논쟁적이면 배포 전에, PR을 여는 서브에이전트는 `interrogate`를 돌리고 URL을 게시합니다. `architect`는 구현 전에 종합된 스케치에 적대적 압력이 필요할 때 이 스킬을 권합니다. README가 이 스킬을 요약하는 문장은 "diff가 있고 서로 다른 모델이 그것을 깨뜨리려 하기를 원할 때, 엄격한 코드 품질 관점을 포함해서"입니다.

안내서가 이 스킬을 설명하는 방식은 이렇습니다. 같은 diff, 의도, 루브릭을 서로 다른 모델 계열의 리뷰어에게 보냅니다. 모델 다양성이 핵심입니다. 모델마다 사각지대가 다르므로 두 모델이 독립적으로 낸 발견은 신뢰도가 높은 신호입니다. 리드는 모든 것을 `Act on`, `Consider`, `Noted`, `Dismissed`로 나누고 기각마다 이유를 달며, 자동으로 적용하는 것은 없습니다. 안내서는 기각도 읽으라고 권합니다. 리드는 실용적인 시니어 엔지니어이지 신탁이 아니고, 사용자가 뒤집을 수 있기 때문입니다.

### 동작 방식

설정된 모델마다 리뷰어 하나씩 적대적으로 코드 변경을 리뷰합니다. 각 모델은 같은 프롬프트와 루브릭을 받습니다. 적대적 신호는 배정된 페르소나가 아니라 모델 다양성에서 나옵니다. 산출물(deliverable)은 종합된 판정이고 변경을 자동으로 적용하지 않습니다.

1. **범위를 정합니다.** 맥락에서 리뷰할 대상을 식별합니다. 사용자가 특정 파일이나 diff를 가리키면 그것, 기능 브랜치라면 전체 변경 집합으로 `git diff main...HEAD`(또는 알맞은 베이스 브랜치), 사용자의 메시지가 최근 작업을 가리키면 관련 파일을 모읍니다. diff(또는 파일 내용)와 리뷰어가 코드를 이해하는 데 필요한 주변 맥락 파일을 포장합니다.
2. **의도를 밝힙니다.** 리뷰어를 띄우기 전에 의도를 명시적으로 밝힙니다. 사용자의 메시지, 커밋 메시지, PR 설명(있으면), 코드 자체에서 도출합니다. 명확한 한 문단을 씁니다. 의도가 불확실하면 진행하기 전에 사용자에게 묻습니다.
3. **리뷰어를 띄웁니다.** Task 도구로 모든 리뷰어를 한 메시지에 띄웁니다. `~/.cursor/rules/pstack-models.mdc`의 `interrogate reviewers` 줄을 씁니다. 항목마다 리뷰어 하나이고, 아래 Reviewer A/B 라벨을 설정된 항목 수에 맞춰 늘리거나 줄입니다. 규칙(rule)이나 그 줄이 없으면 표의 기본값을 씁니다.

   | 서브에이전트 | 기본 모델 |
   | --- | --- |
   | Reviewer A | `claude-opus-5-5-xhigh` |
   | Reviewer B | `grok-4.7-xhigh-fast` |

   리뷰어마다 `subagent_type: generalPurpose`, 모델은 설정된 `interrogate reviewers` 항목(설정된 줄이 없으면 표의 기본값, `auto`나 `inherit-parent` 항목이면 `model`을 생략해 그 리뷰어가 부모 모델로 돎), `readonly: true`입니다. Task 도구가 설정된 항목을 거부하면 그 리뷰어를 그 계열의 표 기본값으로 돌리고 그렇다고 말합니다. 계열은 접두사(`claude-*`, `grok-*`)로 나누고, 일치하는 계열이 없으면 Reviewer A의 기본값을 씁니다. 표 기본값이 거부되면 Task 도구의 오류 메시지에서 유효한 슬러그를 확인하고 가장 가까운 동등물(같은 계열과 추론 등급 선호)을 골라 띄우고, 기본값 표를 갱신하는 별도 PR을 엽니다. 슬러그 문제로 리뷰를 막지 않습니다. 별칭 항목을 거부된 슬러그로 취급하거나 어느 대체책도 적용하지 않습니다.

   `references/reviewer-prompt.md`를 읽고 템플릿에 (1) 밝힌 의도, (2) diff나 파일 내용, (3) `references/rubric.md`의 리뷰 루브릭, (4) `references/code-quality-review.md`의 코드 품질 렌즈를 채웁니다. 같은 채운 템플릿이 모든 리뷰어에게 가므로 모든 모델이 코드 품질 렌즈를 적용합니다.
4. **종합합니다.** 결과가 돌아오는 대로 하나의 그림을 만듭니다. (1) 리뷰어들의 모든 발견을 파싱합니다. (2) 합의를 식별합니다. 둘 이상의 모델이 독립적으로 낸 발견이 가장 강한 신호입니다. (3) 한 모델만 낸 발견을 식별합니다. 읽을 가치는 있지만 그만큼 가중합니다. (4) 중복을 제거합니다. 모델마다 같은 문제를 다르게 서술할 수 있으므로 합치고 어느 모델이 냈는지 적습니다. (5) 불일치를 적습니다. 한 모델이 무언가를 지적하는데 다른 모델이 명시적으로 반대를 말하면 판정에 유용한 맥락입니다.
5. **리드의 판단.** 리드 리뷰어는 중립적 집계자가 아니라 실용적인 시니어 엔지니어입니다. `references/lead-judgment.md`의 틀에 따라 모든 발견을 네 개의 통에 나눕니다.

   | 통 | 뜻 |
   | --- | --- |
   | Act on | 실제 목표에 비추어 정확성, 보안, 유지보수성에 영향을 주는 진짜 문제. 진짜 PR을 막았을 것들 |
   | Consider | 정당한 지적이지만 지금 처리하는 비용을 넘는지 확신하지 못함. 사용자가 볼 가치가 있음 |
   | Noted | 기술적으로 타당하지만 실행할 수 없음. 맥락에 따라 다르거나 성급한 최적화이거나 현 단계에서 영향이 작음 |
   | Dismissed | 틀렸거나 사소하거나 맥락이 빠짐. 이유를 간단히 설명 |

   발견마다 어느 모델(들)이 냈는지, 통, 그 분류의 한 줄 근거를 담습니다.

#### 출력 형식

판정은 이 구조로 제시합니다. **Intent**(2단계의 의도 문단을 인용), **Reviewers**(리뷰어마다 라벨, 모델 이름, 발견 수), **Act On**(처리해야 할 발견. 서술, 어느 모델이 냈는지, 왜 중요한지), **Consider**(생각해 볼 발견. 서술, 모델, 트레이드오프), **Noted**(타당하지만 우선순위가 낮은 것의 간단한 목록), **Dismissed**(기각한 발견과 간단한 근거), **Agreement Map**(모델들이 어디서 일치하고 어디서 갈렸는지, 그 패턴이 무엇을 알려 주는지).

#### 리뷰어 프롬프트

리뷰어는 "적대적 코드 리뷰어"로 설정됩니다. 아래 코드에서 실제 문제(버그, 설계 결함, 보안 문제, 유지보수 우려)를 찾습니다. 도움이 되거나 격려하려고 있는 것이 아니라 스트레스를 주려고 있습니다. 작성자가 밝힌 의도가 주어지고, 코드가 그 의도를 잘 달성하는지 리뷰합니다. 의도 자체는 의심하지 않고 목표는 옳다고 가정한 채 실행에 도전합니다. 루브릭의 모든 렌즈와 코드 품질 렌즈 중 관련 있는 것을 통해 리뷰하되, 해당하지 않는 렌즈를 억지로 쓰지 않습니다. 단순한 버그 수정에 아키텍처 온전함에 대한 문단은 필요 없습니다.

발견마다 네 가지를 줍니다. **Severity**(`critical`은 버그, 데이터 손실, 보안 문제, 근본적으로 깨진 동작을 일으킬 것, `warning`은 당장 깨지지는 않지만 고통을 줄 설계 우려나 정확성 문제, `nit`은 스타일이나 이름 같은 작은 개선), **Finding**(구체적인 문제, 특정 줄과 함수를 언급), **Evidence**(왜 문제라고 믿는지, 주장만 하지 말고 추론을 보임), **Suggestion**(선택. 구체적 대안이 있을 때만). 좋은 발견은 특정 코드를 가리키고, 왜 문제인지 설명하고, "이것은 깨졌다"와 "나라면 다르게 했을 것"을 구분하고, 밝힌 의도를 고려합니다. 피할 것은 문제를 짚지 않고 코드가 하는 일을 되풀이하는 것, 코드를 칭찬하는 것입니다. 리뷰어는 적수이지 응원단이 아닙니다. 아무것도 잘못된 것이 없으면 "no findings"라고 말하고 멈춥니다. 빈 리뷰도 유효한 결과입니다.

#### 리뷰 루브릭

관련 있는 렌즈로 리뷰합니다. 모든 렌즈가 모든 변경에 적용되지는 않으므로 판단을 씁니다. 여섯 렌즈가 있습니다.

| 렌즈 | 묻는 것 | 대표 항목 |
| --- | --- | --- |
| Correctness | 코드가 의도가 말하는 대로 하는가 | 엣지 케이스(빈 입력, nil/undefined, 경계값, 동시 접근), 오류가 잡히고 전파되는지 조용히 삼켜지는지, off-by-one과 타입 강제 변환, 상태 관리(경쟁 조건, 낡은 클로저, 매달린 참조), 행복한 경로와 슬픈 경로, 멱등성(두 번 돌거나 이전 실행이 중간에 죽으면), 동시성(같은 가변 상태를 여럿이 건드리면 접근이 구조적으로 직렬화되는가, 유지되지 않을 관례인가). 잠재 버그를 찾으면 실행 경로를 추적하고 "이것이 nil일 수 있다"고만 하지 말고 nil이 되는 호출 사슬을 보입니다 |
| Root Causes vs. Symptoms | 실제 문제를 고치는가, 증상을 덮는가 | 변경된 파일 밖을 봐야 답할 때가 많습니다(호출자, 피호출자, 타입 정의, 형제 모듈을 읽음). 더 깊은 불변식 위반을 가리는 가드 절, 깨진 계약을 숨기는 재시도 로직, 모델링 오류를 침묵시키는 타입 캐스트, 우회책을 보면 "왜 우회책이 필요한가?"를 묻고, 모듈 B의 계약에서 고쳐야 할 것을 모듈 A에서 고치는지 봅니다. 수정이 "X를 하지 마라"는 주석이나 누가 기억해야 하는 관례라면 타입 제약, 린트 규칙, 런타임 검사로 바꿀 수 있는지 묻습니다 |
| Structural Integrity | 시스템에 잘 들어맞는가 | 경계 규율(검증(validation)이 시스템 경계에 있는가, 비즈니스 로직에 흩어졌는가), 추상화 수준(고수준 오케스트레이션과 저수준 세부의 혼합), 결합, 데이터 모델의 적합성, 덧붙인 것 대 통합된 것(새 요구가 처음부터 알려졌다면 코드가 이런 모습일까), 레거시 이중 경로(옛 API를 살려 둔 채 새 API를 도입하는가. 외부 소비자가 없으면 같은 웨이브에서 호출자를 옮기고 옛 경로를 지웁니다). 단순한 코드를 추상화가 없다고 벌하지 않습니다. 성급한 추상화가 중복보다 나쁩니다 |
| Verification | 읽는 것만으로 이 코드가 동작한다고 알 수 있는가 | 테스트가 있는가, 동작을 시험하는가 구현 세부를 시험하는가, 회귀를 잡을 단언이나 불변식이 있는가, 버그 수정이면 그 버그의 테스트가 있는가, 통합 경계를 건드리면 전체 경로가 시험되는가, 대리물이 아니라 실제를 확인하는가(파일 mtime이나 캐시된 상태로 생존을 확인하는 것은 검증(verification)의 빈틈), 위임이나 비동기 작업이면 실제 산출물을 검증하는가 자기 보고와 요약을 믿는가 |
| Complexity Budget | 복잡도가 코드가 이루는 것으로 정당화되는가 | 정확성과 명료함을 잃지 않고 더 단순할 수 있는 코드, 호출 지점 하나에만 봉사하는 추상화, 아직 없는 경우를 위한 설정이나 매개변수화, 죽은 코드와 안 쓰는 임포트와 흔적 매개변수, 현재 호출자가 없는 "혹시 몰라" 경로, 전환기 안정성을 위해 살려 두었으나 더는 필요 없는 호환 경로(마이그레이션이 끝났으면 뼈대(scaffold)를 지움), 사용자 경험이 복잡도를 정당화하는가(반쯤 끝난 기능은 없는 것보다 나쁨). 단순한 것이 틀리지 않는 한 더 낫고, 중복 세 줄이 성급한 추상화보다 낫습니다 |
| Security | 입력에서 위험한 지점까지 경로 | 발견마다 입력 경로를 코드 안에서 추적해 보입니다. 사용자 입력이 정화 없이 위험한 싱크(SQL, 셸, eval, innerHTML)로 흐르는지, 새 엔드포인트의 인증과 인가의 빈틈, 코드나 로그나 오류 메시지의 비밀, 보안에 중요한 경로의 TOCTOU |

#### 리드 판단의 틀

리드는 설정된 리뷰어들이 낸 발견에 실용적 엔지니어링 판단을 적용합니다. 집계하지 말고 거르고, 맥락을 붙이고, 결정합니다. 적대적 리뷰어는 공격적이라서 유용하지만 맥락 없는 공격성은 잡음을 만듭니다. 리뷰어는 코드베이스의 일부와 한 문단의 의도만 봤고, 이미 시도되어 기각된 것, 코드 밖의 제약(일정, 의존성, 마이그레이션 계획), 어느 부분이 임시 뼈대이고 어느 부분이 영구 아키텍처인지, 스택의 다음 PR이 무엇을 다룰지 모릅니다. 리드는 전체 대화 맥락을 갖고 있으므로 그것을 씁니다. 걸러내는 원칙(principle)은 다음과 같습니다.

- **Nitpick Gravity.** 리뷰어, 특히 적대적인 리뷰어는 리뷰를 채우는 경향이 있습니다. 치명적 문제를 못 찾으면 사소한 것을 부풀립니다. 한 리뷰어의 발견이 모두 사소한 것이나 스타일 선호라면 코드는 아마 괜찮습니다. 그렇게 말합니다.
- **Hypothetical vs. Actual.** "여기에 null을 넘기면?"은 호출자가 실제로 null을 넘길 수 있을 때만 발견입니다. 호출 지점을 추적합니다. 입력이 상류에서 검증(validation)되거나 타입 시스템이 막으면 기각합니다.
- **Premature Abstraction Warnings.** 리뷰어는 함수 추출, 인터페이스 추가, 추상화 생성을 자주 제안합니다. 이 코드가 두 번째 방식으로 바뀌어야 하는가? 아니라면 그 추상화는 성급합니다.
- **"I Would Have Done It Differently."** 코드 리뷰에서 가장 흔한 오탐입니다. "나는 다른 접근을 선호한다"는 발견은 버그도 설계 결함도 아니고, 리뷰어가 현재 접근의 구체적 문제를 보이지 않는 한 실행할 수 없습니다. 기각하고 이유를 말합니다.
- **Missing Context Signals.** 리뷰어가 맥락을 이해하지 못했음을 드러내는 발견을 조심합니다. 작성자가 쓰거나 고치지 않은 코드에 대한 변경 제안, 코드베이스의 나머지와 일관된 패턴(리뷰어가 모를 뿐)을 지적하는 것, 아는 제약과 충돌하는 접근 권고. 정직한 실수이므로 점잖게 기각합니다.

**리뷰어가 옳을 때.** 불편하다고 발견을 기각하지 않습니다. 적대적 리뷰의 요점은 놓쳤을 것을 잡는 것입니다. 주의를 기울일 만한 신호는 여러 모델이 독립적으로 같은 문제를 지적하는 것(합의 신호), 가설이 아니라 구체적 실행 경로를 지목하는 것, 코드에 대한 자기 멘탈 모델의 빈틈을 드러내는 것, 읽고 "...그래, 사실 그렇네"라는 생각이 드는 것입니다. 보안 발견과 정확성 버그는 한 모델에서 나왔더라도 더 정밀하게 살피며 기각에 특히 조심합니다.

**판정 보정.** 좋은 판정은 포괄적이지 않고 유용합니다. 사용자가 "Act On" 절을 읽고 그것들을 고치고 자신 있게 배포할 수 있어야 합니다. "Act On" 목록이 다섯 항목을 넘으면 아마 충분히 거르지 않은 것입니다. "Dismissed" 절은 잡일이 아니라 신뢰 장치입니다. 무엇을 왜 기각했는지 보여 주면 사용자가 동의하지 않는 곳에서 판단을 뒤집을 수 있습니다.

#### 코드 품질 렌즈

각 리뷰어는 루브릭에 더해 이 렌즈를 적용합니다. 구현 품질, 유지보수성, 추상화 품질, 코드베이스 건강에 초점을 둔 엄격한 기준(standard)입니다. 무엇보다 코드 구조에 야심을 가집니다. 지역적 정리를 찾는 데 그치지 않고 "code judo" 수를 적극적으로 찾습니다. 동작을 보존하면서 구현을 극적으로 단순하고 작고 직접적이고 우아하게 만드는 재구성입니다. 기본 프롬프트는 "현재 브랜치의 변경에 대해 깊은 코드 품질 감사를 하라. 동작에 영향을 주지 않고 코드 품질을 의미 있게 개선하도록 변경을 어떻게 구조화하고 구현할지 다시 생각하라. 추상화와 모듈성을 개선하고 스파게티 코드를 줄이고 간결함과 가독성을 높이라. 야심적이 되라. 코드베이스의 일부를 재구조화하는 분명한 개선 경로가 있으면 그렇게 하라. 극도로 철저하고 엄밀하게. 두 번 재고 한 번 자르라"입니다. 차원은 0번부터 7번까지 여덟 개이고 해당하는 것만 적용합니다.

| 번호 | 차원 |
| --- | --- |
| 0 | 구조적 단순화에 야심을 가집니다. "조금 더 깔끔해질 수 있다"에서 멈추지 않고 분기, 헬퍼, 모드, 조건문, 계층 전체가 사라지는 재구성을 찾습니다. 지우는 대신 재배열하는 것이 아니라 복잡도를 지울 수 있으면 강하게 밀어붙입니다 |
| 1 | PR이 파일을 1천 줄 미만에서 1천 줄 넘게 밀어 올리면 아주 강한 이유가 필요합니다. 강한 냄새로 취급합니다. 결과 파일이 분명히 정돈된 채 남는 강력한 구조적 이유가 있을 때만 면제합니다. 헬퍼, 하위 컴포넌트, 모듈을 추출하는 쪽을 선호합니다 |
| 2 | 기존 코드에서 스파게티가 자라는 것을 허용하지 않습니다. 무관한 흐름에 끼어드는 새 임시 조건문, 흩어진 특수 사례, 일회성 분기를 의심합니다. "아무 데나 있는 이상한 if문"은 스타일 지적이 아니라 설계 문제입니다 |
| 3 | 동작하는 코드를 받아들이는 것만이 아니라 설계를 깨끗이 하는 쪽으로 기웁니다. 동작을 유지하면서 구조가 의미 있게 깨끗해질 수 있으면 깨끗한 쪽을 밀어붙입니다 |
| 4 | 해키하거나 마법 같은 코드보다 직접적이고 지루하고 유지보수 가능한 코드를 선호합니다. 단순한 데이터 모양 가정을 숨기는 범용 메커니즘을 경계하고, 명료함을 사지 못하는 얇은 추상화, 항등 래퍼, 통과 헬퍼를 지적합니다 |
| 5 | 유지보수성에 영향을 줄 때 타입과 경계의 깨끗함을 밀어붙입니다. 불필요한 선택성, `unknown`, `any`, 캐스트가 많은 코드를 의심하고, 느슨한 임시 객체보다 명시적 타입 모델을 선호합니다. 불명확한 불변식을 조용한 폴백으로 덮는 분기가 있으면 경계를 명시적으로 만들어야 하는지 묻습니다 |
| 6 | 로직을 정본 계층에 두고 기존 헬퍼를 재사용합니다. 공유 경로로 새는 기능 로직, API로 새는 구현 세부를 지적합니다. 맞춤 일회성 유틸보다 기존 정본 유틸을 선호하고, 표류를 정상화하지 않고 코드를 알맞은 패키지, 서비스, 모듈로 옮깁니다 |
| 7 | 더 깨끗한 구조가 분명할 때 불필요한 순차적 오케스트레이션과 비원자적 갱신을 설계 냄새로 취급합니다. 독립된 일이 이유 없이 직렬화되어 있으면 병렬로 돌려야 하는지 묻고, 관련 갱신이 상태를 반쯤 적용된 채 남길 수 있으면 더 원자적인 구조를 밀어붙입니다. 미시 최적화에 지나치게 매달리지는 않습니다 |

출력 기대는 이렇습니다. 구조적 코드 품질 회귀와 놓친 단순화를 먼저, 그다음 스파게티와 분기 복잡도, 그다음 경계, 타입, 파일 크기 우려, 그다음 더 작은 모듈성과 가독성 문제 순입니다. 승인 기준(bar)도 엄격합니다. 동작이 옳아 보인다는 이유만으로 승인하지 않습니다. 작성자가 정당화하지 못하는 한 다음은 사실상의 차단 요소로 취급합니다. code judo 한 수가 지울 수 있는 부수적 복잡도를 많이 남기는 PR, 파일을 1000줄 미만에서 1000줄 넘게 밀어 올리는 것, 기존 흐름을 엉키게 하는 임시 분기를 더하는 것, 공유 코드에 기능 검사를 흩뿌리는 것, 불필요한 추상화, 래퍼, 캐스트가 많은 계약을 더하는 것, 기존 헬퍼를 복제하거나 분명한 정본 자리가 있는데 로직을 잘못된 계층에 두는 것입니다. 리뷰 어조는 직접적이고 진지하고 품질을 요구하되 무례하지 않게 하며, 큰 유지보수성 문제를 부드러운 제안으로 눅이지 않습니다.

### 사용 예

안내서의 예입니다.

```text
/interrogate 브랜치 전체를, 회의적으로. 실제 버그나 동작 회귀가 아니면 사소한 지적은 하지 마.
```

레시피는 이렇습니다.

```text
/interrogate 브랜치 전체를 회의적으로. 아직 아무것도 바꾸지 마. 동작의 실제 버그나 회귀가 아니면 사소한 지적은 하지 마.
```

한정어가 실제로 일합니다. "아무것도 바꾸지 마"는 읽기 전용을 유지하고, 사소한 지적 규칙은 잡음을 미리 걸러서 `Act on` 발견이 시간을 쓸 가치가 있게 합니다. 안내서는 이 스킬을 작은 완성된 변경이 미덥지 않을 때(`/interrogate`만으로), 논쟁적이고 되돌리기 비싼 설계일 때(`/architect` 뒤 배포 전 `/interrogate`) 쓰라고 권합니다. 짧게 `/interrogate review this pr.`로도 충분합니다.

### 함정과 주의점

- 변경을 자동으로 적용하지 않습니다. 산출물은 판정입니다.
- 의도를 모르면 진행하기 전에 사용자에게 묻습니다.
- 리뷰어가 모두 사소한 지적만 하면 코드가 아마 괜찮은 것입니다. 그렇게 말합니다.
- "Act On"이 다섯 개를 넘으면 충분히 거르지 않은 것입니다.
- 안내서가 꼽은 흔한 실수는 모든 리뷰 댓글을 수용하는 것입니다. 봇과 사람은 진짜 발견과 잡음을 한 목록에 올립니다. `/interrogate`는 발견을 이유가 있는 act-on과 dismissed 통으로 나누고 사용자가 양쪽 어느 쪽으로든 뒤집을 수 있습니다.
- 보안 발견과 정확성 버그는 한 모델이 냈더라도 함부로 기각하지 않습니다.

### 관련 스킬

[`architect`](architect.md#skill-architect)가 종합된 스케치에 이 스킬을 권합니다. 여러 모델의 패널을 쓰는 다른 스킬은 [`arena`](arena-swarm.md#skill-arena)입니다. 판정의 형식과 별개로 PR 댓글을 분류하는 기준은 [Bugbot 분류 기준](playbooks-pr.md#ref-bugbot-triage)에 있습니다.
